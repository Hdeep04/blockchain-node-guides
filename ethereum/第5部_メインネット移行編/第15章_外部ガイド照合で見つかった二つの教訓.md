## 1. きっかけ：外部ガイドとの照合作業

これまでの構築・運用は、自分の手を動かした一次情報を軸に記録してきました。本章では趣向を変え、**他の運用ガイド（第三者が公開しているEthereumホームステーキングの体系的ガイド）**と、自分の運用を照らし合わせる作業を行いました。

対象としたのは、ガイドの「Best practices」セクション（Slashing prevention・Maximising uptime and performance・Optimising security・Managing your withdrawal wallet）を中心とした7ページです。多くの項目は既存の運用で対応済みでしたが、以下2点で明確なギャップが見つかりました。

1. **Doppelganger Protectionが未有効化だった**
2. **vm.swappinessがデフォルト値（60）のままだった**

後者（swappiness）は、調査を進める中で当初の想定より深い背景があることが判明したため、本章では両方をあわせて記録します。

## 2. Doppelganger Protectionの有効化

### 2-1. これは何を防ぐ機能か

同じバリデータ鍵が、意図せず2箇所で同時に稼働してしまうケース（旧環境の停止が不完全なまま新環境を起動した、バックアップ機を誤って並行稼働させた等）を、Validator Client起動時に検知し、警告・一時停止する機能です。第2部で経験した「二重署名→スラッシング」リスクに対する、恒久的な安全装置という位置づけになります。

### 2-2. 現状確認

```bash
systemctl cat lighthouse-vc | grep -i doppelganger
```

出力なし。つまり未有効化であることを確認しました。

### 2-3. 有効化のタイミング判断

この機能は起動時に数エポック分「様子見」してから署名を開始するため、有効化した状態でサービスを再起動すると、その間は一時的にアテステーションを行いません。

```
Activation前（Pending activation中）に設定 → 様子見期間の影響なし
Activation後に設定変更            → 待機時間分がミス（miss）として実際に記録される
```

現在バリデータはPending activation中（Activation見込み9/28）のため、実害なく設定できるタイミングと判断し、その場で対応しました。

### 2-4. 設定変更

`/etc/systemd/system/lighthouse-vc.service`の`ExecStart`に、以下のフラグを追加しました。

```diff
   --secrets-dir /var/lib/lido-csm/secrets \
   --builder-proposals \
+  --enable-doppelganger-protection \
   --metrics \
```

```bash
sudo systemctl daemon-reload
sudo systemctl restart lighthouse-vc
```

### 2-5. 反映確認

```bash
sudo journalctl -u lighthouse-vc -f --since "1 minute ago"
```

```
INFO  Doppelganger detection service started
INFO  Listening for doppelgangers    doppelganger_detecting_validators: 1
```

正常に監視サービスが起動し、対象バリデータ1件の監視が開始されたことを確認しました。`Enabled validator`・`Initialized validators`のログも問題なく、鍵の再読み込みも正常でした。

## 3. swappinessの発見：記憶と実態の齟齬

### 3-1. 現状確認

```bash
cat /proc/sys/vm/swappiness
cat /etc/sysctl.conf | grep swappiness
cat /etc/sysctl.d/*.conf 2>/dev/null | grep swappiness
```

結果は`60`（Ubuntuのデフォルト値）。恒久化ファイルへの記載もなし。外部ガイドは`1`を推奨しており、明確なギャップとして浮上しました。

### 3-2. 「あれ、10に設定した記憶があるが」

ここで違和感がありました。過去のテストネット期の引き継ぎ記録には、確かに`vm.swappiness=10`という記述があったためです。記憶と実態が食い違っていたため、過去の記録を遡って原因を確認しました。

### 3-3. 過去記録の確認：第4部第11章に、既に検証・設定履歴があった

第4部第11章（2026年7月1〜2日、テストネット期）を確認したところ、swappinessは**既に一度、明確な根拠を持って検証・設定されていた**ことが判明しました。

> 32GBという制約・複数の重量級プロセス（Geth・Lighthouse BN/VC・MEV-Boost・SSV）同時稼働・高速NVMe、という3つの観点から、デフォルト値60ではなく`10`を選定。「メモリスパイク時の安全弁としてスワップは残しつつ、不要な先回り退避だけを防ぐ」というバランスを取った判断だった。

この時点で、`sysctl vm.swappiness=10`の一時反映と、`/etc/sysctl.conf`への恒久化コマンドの両方が、手順として明記されていました。

### 3-4. 決定的な一文：第11章自身が残していた未消化のTODO

さらに第11章の末尾「今後の課題」に、次の一文がそのまま残っていました。

> `vm.swappiness=10` の永続化をセットアップ手順（第2部）に追記する（初期設定として明示的に記録しておく）

つまり構造はこうです。

```
① テストネット期：swappiness=10を実機に設定（第11章）
② しかし「この設定を第2部の正式な構築手順書に昇格させる」という
   宿題（TODO）が、そのまま積み残された
③ TODOが解消されないまま、8月のメインネットサーバー構築（第7章）を迎える
④ 第7章は「第2部の手順に従って」構築 → 第2部にswappinessの記載が
   そもそも存在しないため、当然引き継がれない
⑤ 今回、外部ガイドとの照合で約2ヶ月越しに発覚
```

### 3-5. これまでの「移植漏れ」との違い

第5部ではこれまで、chrony設定（第7章）・BIOS電源管理設定（第12章）・ネットワーク帯域監視（第14章）と、3件の「移植漏れ」を発見してきました。いずれも「正式な手順書に書かれていたのに、構築時に実施を見落とした」というパターンでした。

今回のswappinessは、これとは質的に異なります。

| | 移植漏れ（chrony・BIOS・vnstat） | 今回（swappiness） |
|---|---|---|
| 手順書への記載 | されていた | **されていなかった**（記載する予定がTODOのまま止まっていた） |
| 見落としの本質 | チェックリスト運用の甘さ | **「今後の課題」に積んだ宿題を、次の大きな節目（メインネット移行）が来る前に消化できなかったこと** |

「載せると決めたのに、載せていなかった」という一段手前の見落としであり、いわば**移植漏れの一歩手前にある、TODO管理の見落とし**です。

## 4. 値の再検討：`10`（過去の根拠）か`1`（外部ガイド推奨）か

外部ガイドは`1`を推奨していますが、第11章が`10`を選んだ根拠（32GB・重量級プロセス同時稼働・高速NVMe）と単純に比較すると、方向性がやや異なります。`1`は「本当に限界までRAMに頼る」設定で、第11章が重視した「メモリスパイク時の緩衝材」という考え方より一段厳しい側に振れています。

一方で、条件も変化しています。

```
第11章が想定していた環境：SSVノードを含む重量級プロセス同時稼働（テストネット期）
現在のメインネット環境　：SSVノードは非稼働。Geth・Lighthouse BN/VC・MEV-Boostのみ
```

SSVという1プロセス分の負荷が現状の構成には存在しないため、第11章の前提がそのまま今も当てはまるとは限りません。今回は「先に設定して様子を見る」方針のもと`1`を適用しましたが、**`10`への回帰も含めた最終判断は、実測データを見てから改めて行う**、という位置づけとしています。

### 実施内容

```bash
sudo sysctl vm.swappiness=1
echo "vm.swappiness=1" | sudo tee -a /etc/sysctl.conf
```

即時反映・恒久化（`/etc/sysctl.conf`への追記）ともに完了しました。

### 観察結果（設定直後）

```
設定前：Swap used 2.2Gi
設定直後：Swap used 2.1Gi（ほぼ横ばい）
```

swappinessは「これから新たに退避する際の積極度」を決める設定であり、既にSwapへ退避済みのページを自動的にRAMへ戻す機能ではないため、この横ばいは想定通りの挙動です。今後、新規のメモリ圧迫が発生した際に、より物理RAM側で粘るようになるという形で効果が表れてきます。

## 5. まとめ

| 知見 | 内容 |
|---|---|
| Doppelganger Protectionは未有効化だった | 第2部で経験した二重署名リスクへの恒久的な安全装置。Pending activation中の今、実害なく有効化できた |
| swappinessは「移植漏れ」ではなく「TODO未消化」だった | 第11章で既に検証・設定・根拠づけまで完了していたが、「手順書への昇格」という宿題が2ヶ月間放置され、メインネット構築時に引き継がれなかった |
| 値の選定自体も再検討課題に | 外部ガイドの`1`と、第11章の根拠ある`10`は、想定環境（SSV稼働有無）が異なる。現在は`1`で様子見中、最終値は実測を見てから判断する |
| 「今後の課題」は次の節目より前に消化する運命にある | 積み残したTODOは、次の大きな構築イベント（今回で言えば8月のメインネット移行）を迎えると同時に「機会喪失」に変わる。棚卸しのタイミングを事前に決めておく必要がある |
| 外部ガイドとの照合は、自分の記録の裏取りとして機能した | 一次情報（自分の実測・構築記録）を軸にしつつ、体系化された第三者ガイドと突き合わせることで、記憶と実態の齟齬（swappiness）や、単純な未対応（Doppelganger Protection）の両方を発見できた |

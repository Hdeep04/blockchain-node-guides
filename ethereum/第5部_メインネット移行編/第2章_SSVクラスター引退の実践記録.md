## 1. なぜ最初にSSVから手をつけたのか

第5部第1章のロードマップ通り、テストネット手じまいの第一歩として、SSVクラスターの引退を選びました。理由は明快で、クラスターのOwnerウォレットは運用者自身が保有しており、単独の判断で実行できるためです。他のクラスター参加者（Operator A・B・C）への事前連絡は、組成自体がパーミッションレスな仕組みの中で一方的に選んだものであるため、不要と判断しました。

## 2. 「Exit」と「Remove」は別物——公式ドキュメントで整理した基本構造

作業前に、SSV公式ドキュメントで手順を確認したところ、重要な事実が分かりました。**「Exit」と「Remove」は、それぞれ別のレイヤーに対する、別の操作**だという点です。

| 操作 | 対象 | 意味 |
|---|---|---|
| Exit Validators | Ethereumビーコンチェーン | 恒久的に検証を停止し、ステーク元本を引き出し可能にする |
| Remove Validators | SSVネットワーク | SSVの管理台帳からバリデータ登録を抹消する |

この2つには**絶対に守るべき順序**があります。もしRemoveを先にやってしまうと、SSV経由でのExitができなくなり、Ethereum Launchpad側で別途Exitメッセージを送るという面倒な代替手段が必要になります。さらに、Exitが完全に終わる前にRemoveすると、Ethereum上ではまだアクティブなのにSSV上では署名業務から外れてしまい、ペナルティにつながるリスクがあります。

> 💡 **「Exit＝辞表を出して受理を待つ」「Remove＝退職者リストから名前を消す」**とイメージすると分かりやすいと思います。辞表が受理される前に名簿から消すと、不整合が起きます。

## 3. 実施フロー

```
① SSV App（app.ssv.network）→ Exit Validators
② Exitキュー処理を待つ
③ beaconcha.inで完全にExited確認
④ SSV App → Remove Validators
⑤ クラスター残高の引き出し
⑥ オペレーター登録自体の解除（Remove Operator）
⑦ SSVノード（Docker）の停止
```

### 3-1. Exit Validators

`app.ssv.network` のクラスター詳細画面から、Actions → Exit Validators を選択。確認画面には、次のような重要な一文がありました。

> 「Exitキューに入っている間はバリデータをアクティブに保つ必要があり、完了後にSSVネットワークから削除するのは自分自身の責任である」

これはまさに、事前に確認した「Exit後もSSVノードを止めてはいけない」という認識を、公式画面でも裏付けるものでした。

署名後、「Your request to exit the validator has been successfully broadcasted to the network」と表示され、無事Exitキューに入りました。

### 3-2. beaconcha.inでの状況確認

beaconcha.inで確認すると、ステータスは以下の通りでした。

```
Status: Withdrawing
Exited since: 2026年8月13日 8:28
Withdrawable: 2026年8月14日 11:46（約27時間後）
推定最終着金まで: 約10日3時間
```

ここで一つ疑問が浮かびました。「32 ETHがすぐに返ってこないのはなぜか」という点です。調べたところ、Ethereumの出金プロセスは実は3段階に分かれていることが分かりました。

1. Exitキュー通過（数時間〜数日）
2. Withdrawableになるまでの固定待機（256エポック＝約27時間）
3. Withdrawal Sweep（掃き出し処理、キューの混雑状況により数時間〜10日超）

つまり「Exit完了」と「資金の実際の着金」は、まったく別のタイムラインで動いています。今回は3段階目の掃き出し待ちで約10日を要する見込みですが、これは異常ではなく、ネットワーク全体のバリデータ数に応じた正常な待機列です。

### 3-3. Remove Validatorsは「32ETH返却待ち」不要、Exited確認後すぐ実行可

もう一つ、実施前に確認しておいて良かった点があります。「32 ETHの返却を待ってからRemoveすべきか」という疑問です。SSV公式ドキュメントで確認したところ、**Remove Validatorsの実行条件は「完全にExitしたこと」のみで、32 ETHの着金完了は無関係**でした。

> バリデータが完全にExitすると、duty（署名業務）を受け取らなくなる。その時点で、避けられるはずのペナルティを発生させることなく、安全にRemove Validatorsへ進むことができる。32 ETHのステークは、Ethereum上でExitと出金プロセスが完了した後に、withdrawableになる。

ExitとRemoveはSSV側の話、32 ETHの着金はEthereum本体の出金スイープの話——この2つは完全に独立したタイムラインだと分かったことで、着金を待たずにその日のうちにRemoveまで完了させることができました。

### 3-4. Remove Validators実施

Actions → Remove Validators。確認画面には「この操作はネットワークからの削除のみに適用され、ビーコンチェーンからのExitではない」という一文があり、Exitとの役割の違いが公式にも明記されていました。署名後、Etherscanでトランザクションのステータス「Success」を確認しました。

### 3-5. クラスター残高の引き出し

クラスターには、運用手数料の前払い分の残り（0.0317 ETH）が残っていました。これは報酬ではなく、**バリデータがいなくなったことで不要になった前払い金の返金**です。Withdrawボタンで引き出しました。

> 💡 全額引き出した結果、クラスターは残高不足と判定され「Liquidated（清算済み）」という警告表示が出ました。一見驚きますが、これは「稼働中のバリデータを保護できなくなる状況を防ぐための保護機構」であり、Validators数が0の状態では実害はありません。

### 3-6. Operator Statusの「Inactive」表示について

クラスターのバリデータをExitさせた後、SSV Explorer上でOperator自体のStatusが「Inactive」（赤字）になりました。念のためサーバー側の稼働状況も確認しましたが、

```bash
docker ps
docker logs --tail 100 ssv-node
```

エラーは一切なく、バリデータのステータスが正しく`exiting`として認識されているログが確認できました。

```
Controller  recording validator status  {"status": "exiting", "count": 1, ...}
```

担当する署名業務（duty）がなくなったことによる、想定内の表示変化と判断し、深追いはしませんでした。

### 3-7. Remove Operator（オペレーター登録自体の解除）

最後に、Operator自体の登録も解除しました。これはバリデータのRemoveとは別の、もう一段階の操作です。

> 削除されたオペレーターは、将来的に再度有効化したり、同じオペレーターとして再登録したりすることはできない。同じ秘密鍵で再登録しようとするとエラーになる。

この不可逆性を踏まえた上で、「メインネットで必要になれば、その時に新しく構築すればよい」という判断のもと、実施しました。確認画面のチェックを入れ、署名。Operators一覧から該当行が消えたことを確認し、完了としました。

### 3-8. SSVノード（Docker）の停止

最後に、サーバー側でDockerコンテナを停止しました。

```bash
cd /opt/ssv && docker compose down
```

ここで一点、正確に理解しておくべきことがありました。**`docker compose down`は、OS再起動後の自動再起動を防ぐと同時に、鍵ファイル等のデータは一切削除しない**という点です。

docker-compose.yamlのvolumes設定は、名前付きVolumeではなく、ホスト側の実パス（`/opt/ssv/data`等）を直接コンテナにマウントする**bind mount**方式でした。このため、`down`でコンテナを削除しても、`encrypted_private_key.json`等のファイルは`/opt/ssv/`配下にそのまま残ります。ファイル自体を消したい場合は、別途手動での削除が必要です。

実行後、`docker ps -a`で`ssv-node`が表示されないことを確認しました。

### 3-9. 最終確認（node_check）

作業完了後、`node_check`を実行し、以下を確認しました。

```
[12] SSV Node (DVT) Status
 - Container : Not installed or not running
```

本業10鍵側（geth/lighthouse/mev-boost/lighthouse-vc）はすべてactiveのままで、SSVの停止作業による影響は一切ないことを確認できました。

## 4. 今日の学び

```
① 「Exit」と「Remove」は完全に別レイヤーの操作であり、
   順序を間違えると復旧が面倒になる
② Remove Validatorsは「32 ETHの着金完了」を待つ必要はなく、
   「Exit完了」のみが条件
③ クラスター残高を全額引き出すと「Liquidated」表示になるが、
   バリデータ数0の状態では実害はない
④ docker compose down は、コンテナを削除するが、
   bind mountされた実ファイルは一切削除しない
⑤ Operator削除は不可逆。同じ秘密鍵での再登録は
   二度とできない
```

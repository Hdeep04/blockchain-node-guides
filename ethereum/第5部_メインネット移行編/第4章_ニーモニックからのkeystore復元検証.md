## 1. なぜこの検証をしたのか

第5部第3章のVoluntary Exit作業中、ふと疑問が浮かびました。「今回はkeystoreファイルとパスワードでExitを実行したが、もしこれらを失っていたら、ニーモニックだけで同じことができたのか？」

第2部以来、「ニーモニックこそが最終防衛ライン」という原則を掲げてきましたが、実際に手を動かして確かめたことはありませんでした。10鍵すべて引退が完了し、実運用への影響を気にせず心置きなく検証できるタイミングだったため、代表として1本の鍵で実施しました。

## 2. 検証の設計

本番ディレクトリ（`/var/lib/lido-csm/`）を一切触らず、独立した作業ディレクトリで実施しました。

```bash
mkdir -p ~/mnemonic-recovery-test
cd ~/mnemonic-recovery-test

lighthouse account validator recover \
  --datadir ~/mnemonic-recovery-test \
  --network hoodi
```

対象は、インデックス1280904（2026年8月14日、10鍵の中で最初にExitした鍵）に対応するニーモニックとしました。

## 3. 実行結果

```
No logfile path provided, logging to file is disabled
Running account manager for hoodi network
validator-dir path: "/home/<your_user>/mnemonic-recovery-test/validators"
secrets-dir path: "/home/<your_user>/mnemonic-recovery-test/secrets"

Enter the mnemonic phrase:
```

> ⚠️ 表示される警告文について：「鍵の復元は、バリデータ鍵の重複稼働（＝Slashingリスク）につながる可能性がある」という、一般的な注意書きです。稼働中の鍵に対してこの検証を行うと、同じ鍵が2箇所で同時に署名しようとしてしまう危険がありますが、今回はExit済みの鍵かつ独立ディレクトリでの検証のため、この懸念には当たりません。

ニーモニック（24単語）を入力すると、次のように表示されました。

```
Valid mnemonic provided.
1/1     Index: 0        0xb4f66315352f4715feebaecf9b4bb2185a1a9a6e44daf6c808563a1516a2a1aa677cdb0ff588f0a6dd8da4d29bc58e4a
```

再生成された公開鍵は、**元のバリデータ（インデックス1280904）の公開鍵と、1文字も違わず完全に一致しました。**

## 4. 「Valid mnemonic provided」は何を確認しているのか

この検証を通じて、当初混同しがちだった点も整理できました。

「Valid mnemonic provided」は、**ニーモニックがBIP-39規格のチェックサムを満たしている**、つまり「24単語が一字一句正確に入力された」ことの確認であり、**そのバリデータが現在Active/Exitedかどうかとは無関係**です。ニーモニックからの鍵の再計算は、ネットワークに一切問い合わせない、ローカル完結の純粋な数学計算だからです。

今回の検証で本当に確認できたことは、次の2点です。

1. 保管していたニーモニックの書き写しに、一切の誤りがなかったこと（Validという結果）
2. そこから計算し直した公開鍵が、実際に半年間運用してきたバリデータの公開鍵と完全一致したこと

## 5. 事前に把握していた注意点（今回は再現せず）

検証前、Lighthouseの過去のissueで、「deposit-cliで生成した鍵と、`recover`コマンドで復元した鍵が一致しない」という報告（2020年）を見つけていました。導出パス（m/12381/3600/0/0/0）は正しいのに結果が食い違う、という内容でしたが、**今回の環境・バージョンでは再現せず、期待通り一致しました。**

## 6. 後片付け

検証で生成された新しいkeystore・パスワードは不要なため、作業ディレクトリごと削除しました。

```bash
rm -rf ~/mnemonic-recovery-test
```

## 1. なぜ監視を拡張するのか

第10章でPrometheus/Grafanaの基盤とダッシュボードを構築した翌朝、ディスク容量の「日々どのくらい増えているか」を確認したいという要望が生まれた。`node_check`は「今この瞬間」のスナップショットしか見せてくれない。傾向を追うには、時系列で可視化する仕組みが別途必要だった。

これに加えて、前夜から積み残していた課題がもう一つあった。第4部第9章で構築した「プッシュ型のAlerting（Telegram通知）」は、テストネット環境と共に失われており、メインネットにはまだ存在していなかった。

本章は、この2つ——**プル型の監視強化（傾向の可視化）**と**プッシュ型の監視再構築（Alerting）**——を、1日を通して実施した記録である。

## 2. ディスク予測パネルの追加

まず、Node Exporterが標準で公開しているファイルシステム関連メトリクスの実在を確認した。

```bash
curl -s http://127.0.0.1:9100/metrics | grep "node_filesystem_avail_bytes\|node_filesystem_size_bytes" | grep 'mountpoint="/"'
```

```
node_filesystem_avail_bytes{...,mountpoint="/"} 4.96518443008e+11
node_filesystem_size_bytes{...,mountpoint="/"}  1.954104868864e+12
```

`node_check`の実測値（463G空き）とほぼ一致しており、正しいデータであることを確認した上で、2つのパネルを作成した。

### 2-1. 使用量の推移

```promql
(node_filesystem_size_bytes{mountpoint="/"} - node_filesystem_avail_bytes{mountpoint="/"}) / 1024 / 1024 / 1024
```

Time seriesパネルとして追加し、GB単位に変換した。過去24時間で、じわじわと右肩上がりに増加する様子がそのままグラフに現れた。

### 2-2. 残り日数の予測

```promql
(node_filesystem_avail_bytes{mountpoint="/"} / (-deriv(node_filesystem_avail_bytes{mountpoint="/"}[6h]))) / 86400
```

最初、傾きの計算窓を`6h`に設定したところ、予測値が12日〜268日の間で激しく上下した。窓が短いほど、その時間帯だけの増加ペースに引きずられ、ノイズの影響を強く受けてしまうためである。

窓を`24h`に広げたところ、予測値は79.1日という、より安定した値に落ち着いた。

```promql
(node_filesystem_avail_bytes{mountpoint="/"} / (-deriv(node_filesystem_avail_bytes{mountpoint="/"}[24h]))) / 86400
```

> 💡 **短い窓と長い窓、それぞれの用途。** 短い窓（数時間）は「今まさに何が起きているか」を鋭敏に捉えるのに向くが、予測値の算出のように「安定した傾向」を知りたい場面では、長い窓（24時間以上）の方がノイズに強い。用途に応じて使い分ける必要があることを、数値の暴れ方から実地で学んだ。

## 3. メモリ・スワップパネルの追加

ディスクパネルの完成後、前日確認していた「スワップ使用量が10Mi→1.4Giに増えていた」という懸念にも、同じ手法で応えることにした。

```promql
# Memory Usage (GB)
(node_memory_MemTotal_bytes - node_memory_MemAvailable_bytes) / 1024 / 1024 / 1024

# Swap Usage (GB)
(node_memory_SwapTotal_bytes - node_memory_SwapFree_bytes) / 1024 / 1024 / 1024
```

追加した結果、スワップの増加は「じわじわ」ではなく、**特定の時刻に階段状に一段上がって、その後は横ばいになる**という、独特のパターンを描いていることが分かった。連続的な漏出（リーク）ではなく、何らかのイベント（プロセスの負荷変動等）を境に、一段階シフトする挙動であると考えられる。

> 💡 **`node_check`では見えなかったもの。** 数字の「今の値」は`node_check`で常に見えていたが、「いつから、どんなペースで」増えたのかは、時系列パネルを作って初めて分かった。これは第2節冒頭で述べた、本章の出発点そのものである。

## 4. 凡例表示の改善

パネル作成直後、グラフ下部の凡例に

```
{instance="127.0.0.1:9100", job="node_exporter"}
```

という、Prometheusのラベル情報がそのまま表示される問題が生じた。これは、クエリが単一系列（1本の線）しか返さない場合に、Grafanaが自動的にラベル情報全体を表示するデフォルト挙動である。

各パネルのクエリオプションで「Legend」を明示的に指定することで解決した。

```
Disk Usage Trend  → Legend: "Disk Used"
Memory Usage      → Legend: "Memory Used"
Swap Usage        → Legend: "Swap Used"
```

## 5. Telegram Bot連携の再構築

ここから、本章のもう一つの柱であるAlertingの再構築に入る。第4部第9章の記録を確認したところ、当時の設計（3階層のアラートルール、専用Telegram Bot、通知テンプレート）がそのまま残っていた。

まず、当時作成した`Lide_CSM_Alert_Bot`が今も生きているか確認した。

```bash
curl -s "https://api.telegram.org/bot<TOKEN>/getMe"
```

```json
{"ok":true,"result":{"id":<Bot ID>,"is_bot":true,"first_name":"Lide_CSM_Alert_Bot",...}}
```

Bot自体（Telegram側の登録）は生きていた。削除しない限り半永久的に存続するTelegram Botの性質上、これは想定通りである。

次にChat IDを取得しようとしたが、`getUpdates`が空配列を返した。

```bash
curl -s "https://api.telegram.org/bot<TOKEN>/getUpdates"
# → {"ok":true,"result":[]}
```

> 💡 **API TokenとChat IDは別物。** Tokenは「Bot自身を証明する鍵」、Chat IDは「どの会話に送るかの宛先」である。`getUpdates`は「Botが過去に受信したメッセージの履歴」を返す仕組みのため、一度もメッセージを送っていないBotに対しては空の結果が返る。Botとのチャット画面で何かメッセージ（`test`等）を送信してから再実行することで、Chat IDが取得できた。

## 6. Contact Pointの作成でのつまずき

取得したToken・Chat IDを使い、Grafanaの「Contact points」でTelegram統合を作成した。

しかし、最初の「Test」ボタンでエラーになった。原因は、Chat ID欄に誤ってTokenに含まれる数字（BotのID部分）を入力していたことだった。Chat IDとAPI Tokenを混同していたためである。正しいChat IDに修正したところ、テスト通知が届いた。

```

Value: [no value]

- alertname = TestAlert
```

デフォルトテンプレートの内部情報がそのまま出力される形だったが、Bot連携自体は成功した。

## 7. 3つのアラートルールの再構築

第4部第9章の設計思想——**根本原因・中間的な異常・結果**という3階層の監視——をそのまま踏襲し、メインネット向けに構築した。ただし、当時のクエリをそのまま使えるかどうかは、1件ずつ実在確認が必要だった。

| 階層 | ルール名 | クエリ | 実在確認の結果 |
|---|---|---|---|
| 根本原因 | Service Down (Geth/Lighthouse) | `min(up{job=~"geth\|lighthouse_bn\|lighthouse_vc"})` | ✅ Prometheus標準機能、そのまま使用可能 |
| 中間的な異常 | Beacon Node Not Synced | `vc_beacon_nodes_synced_count` | ✅ 現行Lighthouseにも存在、そのまま使用可能 |
| 結果 | Attestation Readiness Low | ~~`vc_signed_attestations_total`~~ | ❌ 現行Lighthouseに存在せず、代替クエリへ変更 |

3番目のクエリのみ、第9章のプルーニング検証時に発見していた代替メトリクスに差し替えた。

```promql
sum(rate(validator_monitor_attestation_simulator_head_attester_hit_total[5m]))
/
(sum(rate(validator_monitor_attestation_simulator_head_attester_hit_total[5m])) + sum(rate(validator_monitor_attestation_simulator_head_attester_miss_total[5m])))
* 100
```

> ⚠️ **ルール名も実態に合わせて変更した。** 当時の「Attestation Success Rate Low（成功率）」という名前をそのまま使うと、実際には「シミュレーション値」を見ているという実態と乖離する。「Attestation Readiness Low（準備状況）」という、実態に即した名前に改めた。

各ルールとも、「データがない場合のアラート状態」をデフォルトの`No Data`から`Alerting`に変更した。これは第4部第9章で確立した設計原則——サーバー完全停止時にメトリクス自体が取得できなくなるケースを、確実に検知するための設定——をそのまま踏襲している。

## 8. 実機検証：発火・解決タイムライン

3つのルールが実際に機能するか、`node_stop`/`node_start`を使って実地で検証した。

### 8-1. 発火時のタイムライン（実測）

```
20:54  Firing: Service Down (Geth/Lighthouse)
20:58  Firing: Attestation Readiness Low（4分遅れ）
20:59  Firing: Beacon Node Not Synced（5分遅れ）
```

第4部第9章の実測（Service DownとBeacon Node Not Syncedが同時発火、Attestation関連のみ5分遅れ）とは、発火順序が一部異なった。今回は「Beacon Node Not Synced」が最後になった。

原因は、監視対象メトリクスの取得元にある。`vc_beacon_nodes_synced_count`はLighthouse VC自身（5064番ポート）が公開するメトリクスであり、そのプロセス自体が完全に停止すると、Prometheusがターゲットへのスクレイプ自体に失敗し、「NoData」と判定されるまでに時間を要した。一方、「Service Down」が参照する`up`メトリクスは、Prometheus自身がスクレイプ試行の成否を即座に記録する、より外形的な指標である。

### 8-2. 解決時のタイムライン（実測）

```
21:04  Resolved: Service Down (Geth/Lighthouse)
21:04  Resolved: Beacon Node Not Synced（Service Downと同時）
21:13  Resolved: Attestation Readiness Low（9分遅れ）
```

発火時とは異なり、解決時は「Service Down」と「Beacon Node Not Synced」が同時に解決した。これは、lighthouse_vcの起動完了とBeacon Nodeとの接続確立が、`up`が1に戻るタイミングとほぼ重なったためと考えられる。

「Attestation Readiness Low」の解決だけが、発火時（4分遅れ）よりもさらに遅れて9分を要した。これは`rate(...)[5m]`という5分間の移動平均を使っているため、サービスが復帰してデータが流れ始めても、直近5分間の計算窓に「データがなかった期間」が含まれている間は、条件を満たしたままになるという、仕様上の遅延である。

> 💡 **即時指標と期間集計指標の非対称性。** `up`のような即時指標は状態変化に即座に反応するが、`rate()`のような移動平均型の指標は、発火・解決のいずれの局面でも、ウィンドウの長さに応じたラグを持つ。この特性は第4部第9章でも確認されていたが、発火時と解決時とで遅延の出方（どちらのルールがより遅れるか）が必ずしも同じパターンを辿るとは限らない、ということが今回新たに分かった。

### 8-3. タイムラグへの対応方針

発火まで数分を要する現状の設定（Evaluation interval 1分、Pending period 1分）について、より迅速な検知を可能にする余地（Pending periodの短縮等）はある。ただし、アラート受信後の対処運用（誰が、何を、どこまで確認するか）がまだ確立していない段階のため、今回は設定変更を見送った。第4部第9章の当時と同一の設定値を踏襲していたことも確認しており、変更の必要性は低いと判断している。

## 9. 通知テンプレートの改善

実機検証で届いた通知は、Grafanaのデフォルトテンプレートのまま、`Value`・`Labels`・`Source`・`Silence`等の内部情報をすべて含む、冗長な形式だった。第4部第9章6節で構築した、シンプルなカスタムテンプレートを再現した。

```go
{{ define "lido_csm_telegram" }}
{{ if eq .Status "firing" }}🔴 アラート発生{{ else }}✅ 復旧{{ end }}
{{ range .Alerts }}
{{ .Annotations.summary }}
{{ if .Annotations.description }}{{ .Annotations.description }}{{ end }}
{{ end }}
{{ end }}
```

> ⚠️ **「Content」欄と「Payload」欄を間違えないこと。** テンプレート編集画面には、テンプレートのコードを書く「Content」欄と、プレビュー用のサンプルJSONを書く「Payload」欄の2つが存在する。この2つの区別が直感的に分かりにくく、探すのに手間取った。

Contact Pointの「Message」欄に`{{ template "lido_csm_telegram" . }}`を設定し、テスト通知で確認したところ、以下のシンプルな形式に変わった。

```
🔴 アラート発生

Notification test
```

以前の内部情報（`datasource_uid`、`ref_id`、`Source URL`、`Silence URL`等）はすべて省略され、「何が起きたか」だけが一目で分かる形になった。

## 10. 翌朝の誤報事案：シミュレーション値の限界

本章の作業を終えた後、就寝前に「Attestation Readiness Low」のアラートが発火した。

```
🔴 アラート発生

Summary: ⚠️ Attestation準備状況（シミュレーション）が低下しています
Description: 直近5分間のAttestationシミュレーション成功率が低下しています。
```

`node_check`で確認したところ、全サービスが正常稼働、同期完了、Peer数も健全な範囲であり、サーバー自体には何の異常もなかった。Grafanaのグラフでも、Network Peers・Memory・Swap・Disk・CPU Temperatureのいずれも正常範囲で推移していた。

原因は、7節で述べた通り、このメトリクスが「実際の署名成功率」ではなく「シミュレーション値」である点にあった。当日実施した複数回の`node_stop`/`node_start`検証の影響が、5分間の移動平均の計算窓にまだ残っていたため、一時的に閾値（95%）を下回ったと考えられる。しばらく時間を置くと、値は100%に回復した。

> 💡 **このアラートが本来意味すること。** バリデータはまだPending activation中であり、実際の署名は一度も行われていない。「Attestation Readiness Low」が測っているのは、「もし今このバリデータがActiveだったら、正しく振る舞えていたはずか」という、Lighthouseの内部シミュレーション結果である。実害はなく、Activation前の検証作業（意図的なサービス停止）が引き金になった、いわば「リハーサル中にリハーサルを中断したので、リハーサルの点数が下がった」という状況だった。

### 10-1. Activation後に必要となる対応

このメトリクスは、あくまで「本物の署名メトリクスが見つからなかったための代替」である。Activation後、実際の署名活動が始まった時点で、以下の対応が必要になる。

```
[ ] 本物の署名メトリクス（vc_signed_attestations_totalの後継に相当する
    もの）を、Lighthouse VC/Beacon Nodeのメトリクス一覧から再探索する
[ ] 見つかったメトリクスで、Attestation Readiness Lowのクエリを
    差し替える（シミュレーション値 → 実際の署名成功率へ）
[ ] ルール名・パネル名も、実態に即して
    「Attestation Success Rate Low」「Attestation Success Rate」に戻す
```

## 1. なぜディスク使用量の調査から始めたのか

第2部で確立した`node_backup`スクリプトは、「稼働中のバリデータ」を前提に設計されたものでした。しかし今、SSVクラスターも本業10鍵もすべて引退済みです。今回のバックアップは「稼働継続のための保険」ではなく、**「テストネット運用の集大成を、メインネット移行前に総括する」**という、性質の異なる作業でした。

そのため、まず「今、ディスクの中に何がどれだけあるのか」を`du`コマンドで正確に把握するところから始めました。

## 2. ディスクの内訳を突き止める

`df -h /`では212GB使用となっていましたが、内訳はすぐには分かりませんでした。`du`コマンドで1階層ずつ掘り下げていくと、意外な事実が見えてきました。

```bash
sudo du -h -d 1 /var/lib 2>&1 | sort -rh | head -20
```

```
195G    /var/lib
189G    /var/lib/ethereum      ← ここが本体だった
2.1G    /var/lib/prometheus
1.9G    /var/lib/lido-csm
1.5G    /var/lib/containerd
300M    /var/lib/grafana
```

**Gethのブロックチェーンデータは`/var/lib/geth`ではなく、`/var/lib/ethereum`という独自パスに格納されていた**ことが、この調査で初めて分かりました。第2部の構築当初、`ethereum`ユーザーのシステムディレクトリとして設計していたことが、時間が経って忘れかけていたのを、改めて発見した形です。

> 💡 **教訓：構築時の設計は、時間が経つと本人でも忘れる。** `du -h -d 1`で1階層ずつ掘り下げていく地道な調査が、結局もっとも確実な方法でした。

## 3. バックアップ対象を3つに分類する

全体像が見えたところで、「メインネット移行で使わないものが多くある」という前提のもと、対象を3つのカテゴリに整理しました。

### カテゴリA：メインネットでも再利用する「型」

```
✅ node_check.sh、node_safe_stop.sh（ロジックはネットワーク非依存）
✅ /etc/systemd/system/*.service（geth/lighthouse/lighthouse-vc/mev-boost の起動オプションの型）
✅ /etc/chrony/chrony.conf（時刻同期設定）
```

第5部第1章の「残すもの（テンプレートとして再利用）」の分類と一致する内容です。

### カテゴリB：テストネット運用の記録として保存（アーカイブ）

```
📦 /var/lib/lido-csm/（10鍵分のkeystore、スラッシング保護DB、設定一式）
📦 /opt/ssv/（SSVクラスター構築〜引退の記録）
📦 既存のcronバックアップ（過去の複数世代）
📦 鍵生成で失敗した鍵（記録用として、念のため含める）
```

### カテゴリC：メインネットでは使わない・破棄してよいもの

```
🗑 /var/lib/ethereum（189GB、Gethのブロックチェーンデータ本体）
   → メインネットでは新規に同期するので不要
🗑 各種ログファイル
```

## 4. アーカイブ作成時に発覚した意外な内訳

カテゴリBのアーカイブを作成する過程で、`/var/lib/lido-csm`（1.9G）の中身を`tar -tzvf`で確認したところ、**実はその大部分（約1.86GB）がバリデータクライアントの運用ログだった**ことが分かりました。

```
var/lib/lido-csm/validators/logs/validator.log.1〜9（各約200MB）
```

鍵本体やスラッシング保護DB自体は、1鍵あたり数百バイト〜数十KB程度に過ぎず、「記録として重要なデータ」と「容量を食っているもの（ログという副産物）」は、まったく別物だったということです。

## 5. 「鍵の実体を含めるか」という判断

第2部の原則では「鍵本体はバックアップに含めない（漏洩即スラッシングリスクのため）」でしたが、今回は10鍵とも引退済みで、実運用リスクがない状況でした。

判断のポイントとして、以下の2択を検討しました。

- 鍵を含める：完全なアーカイブとして、当時の環境をそのまま再現できる
- 鍵を含めない：前日（第5部第4章）の検証で「ニーモニックさえあれば完全復元できる」ことが実証済みなので、鍵ファイル自体は冗長という考え方もできる

**「もう使わないと思うが、完全なアーカイブとして残したい」**という判断のもと、鍵本体・パスワードを含める方針としました。

## 6. アーカイブ作成とパーミッションの落とし穴

```bash
mkdir -p ~/testnet-archive
sudo tar -czpf ~/testnet-archive/hoodi_testnet_full_archive_$(date +%Y%m%d).tar.gz \
  /var/lib/lido-csm/ \
  /opt/ssv/ \
  <node_backupsのパス> \
  <failed_keys_backupのパス>

sudo chown <your_user>:<your_user> ~/testnet-archive/*.tar.gz
```

作成直後、`ls -l`で確認したところ、**アーカイブファイルのパーミッションが`-rw-r--r--`（所有者以外も読み取り可能）になっている**ことに気づきました。中身には10鍵分のkeystoreと、一部のパスワードまで含まれているため、これは見過ごせません。

```bash
chmod 600 ~/testnet-archive/hoodi_testnet_full_archive_*.tar.gz
```

`-rw-------`に変更し、所有者以外はアクセスできない状態にしました。

> ⚠️ **`tar`コマンドの`-p`（`--preserve-permissions`）オプションは、アーカイブ「内部」のファイルの権限を保持するものであり、アーカイブ「自体」のファイル権限とは別問題です。** 圧縮ファイル自体の権限は、作成後に別途確認・調整する必要があります。

最終的なアーカイブサイズは1.2GB（圧縮後）でした。

## 7. 外部への安全な転送

サーバー内に置いたままでは、ディスク故障時に一緒に失われるリスクがあります。第2部で確立した「3重の保護」（サーバー内・母艦PC・クラウド同期）の考え方に沿って、Windows母艦PCへ`scp`転送しました。

```bat
scp -p "<your_user>@<your_tailscale_ip>:~/testnet-archive/hoodi_testnet_full_archive_*.tar.gz" "<転送先パス>"
scp -p "<your_user>@<your_tailscale_ip>:~/mainnet-templates/*" "<転送先パス>"
```

転送後、Windows側のプロパティ画面で、**サーバー側の`ls -lh`で確認したバイト数と、Windowsのプロパティ画面のバイト数が完全に一致している**ことを確認しました。1バイトの狂いもなかったことが、転送中の破損・欠損がなかった何よりの証拠です。

## 8. 既存の自動化タスクの扱い

第2部で構築した、Windows タスクスケジューラによる週次バックアップ転送も、稼働中のバリデータがなくなった今、新しく守るべきデータが発生しなくなりました。

削除ではなく**無効化**を選択しました。設定自体は残しておき、メインネット移行後、同じ仕組みをそのまま再利用できるようにするためです。

## 9. まとめ

```
① 「ディスクの中身を1階層ずつ掘り下げる」地道な調査により、
   忘れていた設計（/var/lib/ethereumという独自パス）を再発見できた
② バックアップ対象を「型（再利用）」「アーカイブ（記録）」
   「破棄可」の3分類で整理すると、判断がぶれなかった
③ アーカイブの大部分は、実は鍵本体ではなく運用ログだった
④ 引退済みの鍵は、実運用リスクがないため、
   「完全なアーカイブとして残す」判断ができた
⑤ tar -pはアーカイブ内部の権限保持であり、
   アーカイブ自体のファイル権限は別途chmod 600で締める必要がある
⑥ 転送後はファイルサイズの完全一致を確認し、
   破損なく転送できたことを裏付けた
⑦ 不要になった自動化タスクは、削除ではなく無効化して
   「型」として温存した
```

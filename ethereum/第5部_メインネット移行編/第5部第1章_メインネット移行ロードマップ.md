## 1. なぜ今、メインネット移行なのか

2024年8月、「ステーキングとは何か」も分からないまま参加したイベントから、約2年。第1部〜第4部を通じて、VM検証・ベアメタル移行・SSV分散化・数々の障害対応・ICS取得までを、実地で積み重ねてきました（第14章参照）。

## 2. テストネットの「残すもの・残さないもの」

メインネット移行は、テストネットの設定を「書き換えて使う」のではなく、**「型は活かしつつ、中身は総入れ替えする」**という考え方で進めます。

### 残さないもの（新規作成が必要）

```
① バリデータの鍵（keystore、ニーモニック）
   → メインネット用に、新規生成する
② ネットワーク固有の設定
   （--network hoodi のような指定、ブートノード等）
   → メインネット用として、新規に設定する
③ OS自体
   → LVM構成で再インストールする（後述）
```

### 残すもの（テンプレートとして再利用）

```
① 各種スクリプト（node_check.sh、node_safe_stop.sh等）
   → ロジック自体はネットワーク非依存。
     変数部分（バリデータインデックス等）だけ
     メインネット用に書き換えれば、ほぼそのまま使える

② systemdサービスファイルの「型」
   → Geth/Lighthouse/SSVの起動オプションの構造は、
     ネットワーク指定以外はほぼ共通

③ Grafana/Prometheusの監視ダッシュボード設定
   → パネル構成・アラートルールのロジックは
     ネットワークに依存しない。エクスポート→
     インポートで、そのまま活用できる

④ 権限設計（chown/chmod等のセキュリティ設定）
   → 「バイナリはroot所有、実行ユーザーは別」という
     設計思想自体は、そのまま踏襲する
```

## 3. ハードウェア方針

### 3-1. 同じ物理サーバーを転用する

メインネット用に専用サーバーを新たに購入するのではなく、これまでHoodiテストネットで使ってきた**Minisforum AI X1（Ryzen 7 255、32GB RAM）を、そのまま転用**します。

```
理由：
  ・テストネットを正式に引退させてから再構築するため、
    「稼働中バリデータの停止」という制約がなく、
    ダウンタイムを気にせずじっくり作業できる
  ・追加のハードウェア投資を避けられる
  ・IDVTC練習等の実験用途が必要になれば、
    その時点で改めてテストネット環境を作り直せばよい
```

### 3-2. ディスク構成をLVMへ移行する

現在（Hoodi運用時点）のディスク構成は、LVMを使わない、単純なext4パーティション（1.8TB）でした。

```bash
# 現状確認（2026年8月時点）
lsblk
# nvme0n1p2 259:2  0  1.8T  0 part /
```

しかし実測（node_check）で確認したところ、使用量は209GB（13%）程度に留まっており、**1.5TB近い未使用領域が生じていました。** メインネットのGeth容量は将来的に2TBを超える可能性があり、この「片方だけが枯渇する」非効率を避けるため、**LVM構成へ移行**します。

```
方針：
  ① OS再インストール時に、最初からLVM構成で
     パーティションを組む
  ② 既存のSSD（Samsung 990 PRO 2TB）1枚から開始する
  ③ 将来、容量が逼迫してきたタイミングで、
     同一モデルの2枚目を追加し、LVMのオンライン拡張
     （pvcreate → vgextend → lvextend → resize2fs）で
     容量を増やす
     ※SSDの物理的な取り付け自体は、PCの蓋を開ける
       必要があるため、計画停止を伴う
```

> ⚠️ **RAID（特にミラーリング）は採用しません。** バリデータ運用においては、RAID構成のディスク障害・復旧の過程で、slashing protection dbが意図せず古い状態に巻き戻ってしまうリスクがあります。これは二重署名（第2章で検証したスラッシングの原因）を引き起こしかねません。LVM（単純結合、冗長性なし）と、第1章のバックアップ手順による鍵の保護を組み合わせる方針とします。

### 3-3. SSD購入のタイミング

2枚目のSSD（同一モデル：Samsung 990 PRO MZ-V9P2T0B-IT）の価格は、2025年8月から2026年8月の1年間で、約2万円台から一時12万円台まで、3倍以上高騰しました（2026年8月時点、8万円前後で高止まり）。

```
方針：
  今すぐ2枚目を購入せず、まず既存の1枚（2TB）で
  スタートする。価格が落ち着いた、または容量が
  実際に逼迫してきたタイミングで、2枚目を追加する。
```

## 4. 運用規模の判断：1鍵運用でスタート

予算の都合により、メインネットは**1鍵からスタート**します。

```
必要なBond（担保金）：
  ICSの場合、初回鍵 1.3〜1.5 ETH
  （2026年8月時点のレートで、約38〜44万円程度）

32 ETH本体は、Lidoプロトコルが供給するため、
運用者が用意する必要はない
```

### 収益についての現実的な認識

以前の試算では、月5万円の収益を得るには約20鍵・Bond総額約26 ETHが必要という結果でした。1鍵運用の場合、年間収益はごくわずか（数万円程度）に留まります。

```
そのため、本メインネット移行は「稼ぐこと」を
主目的とはしません。優先するのは：
  ・イーサリアムバリデータとしての本番参加
  ・技術コミュニティとの対等な関わり
  ・学ぶ姿勢・情報収集という、プライスレスな経験
```

## 5. 資金・ウォレット戦略

### 5-1. 取引所からの資金移動

```
複数の国内取引所を利用しており、それぞれ以下の方針とします。

```
取引所A（現在ETHを保有中）：保有ETH全額を移動する
取引所B（現在積立中）      ：積立を停止し、
              送付手数料が無料の別の取引所へ
              乗り換えを検討する
              （現在利用中の取引所は送付手数料が
                固定額＝2026年8月時点で
                1回あたり1,000円台と高め）
```

### 5-2. ウォレットの3層構造

```
① ICS紐づけアドレス（Node Operator用、変更不可）
   → Bond拠出・鍵登録等、CSM運用の実務専用
   → 大きな残高は置かない

② 資金保管用ハードウェアウォレット
   （Ledger・Hito Walletの2つを未開封で保有、
     これから開封・初期設定を行う）
   → 取引所からの入金先、常に残高0を目指す
     「橋渡し役」
```

### 5-3. 報酬は基本的にBondへ再投資する（デポジット思想）

得られた報酬（Rewards）は、都度どこかへ払い出すのではなく、**基本的にはBondへ再投資し、stETH建てのまま保有し続ける**方針とします（Claimingオプション③「Rewards → Excess Bond」、第15章6-4節参照）。

```
理由：
  ・報酬をBondに留めておけば、Lidoの通常の
    ステーキング機能（リベース）により、
    そのまま複利的に増え続ける
  ・第15章で確認した通り、バリデータとしての
    稼働報酬とは別に、Bond自体もstETH建てで
    保有している限りリベースする
  ・「稼ぐ」ことより「ETH資産の有効活用」を
    優先する、これまでの一貫した方針とも合致する
```

> 💡 **なお、CSM v3の新機能（Reward Splitting）を使えば、Rewards Address（報酬の払い出し先）を、Node Operatorのアドレスとは別に設定することも技術的には可能です。** ただし今回の運用方針（報酬は再投資し、都度払い出さない）では、この機能を積極的に使う予定はありません。将来、運用規模が拡大し、報酬の一部を都度現金化したくなった場合の選択肢として、記憶に留めておきます。

### 5-4. 手数料への意識

Ethereumネットワーク自体のガス代は、2026年8月時点で歴史的低水準（単純送金なら1円未満）です。高く感じられていた手数料の正体は、**取引所側が設定している固定の送金手数料**でした。そのため、送金はできるだけ回数をまとめて実行する方針とします。

## 6. テストネット手じまいの実施順序

```
① SSVクラスター（検証用バリデータ、32 ETH）の
   Voluntary Exitを先行実施
   - Owner（0x2D82...4D6F）は運用者自身のウォレットのため、
     単独の判断で実行可能
   - クラスター参加オペレーター（Operator 214・549・
     573）への事前連絡は、そもそも連絡先を持たず、
     組成自体もパーミッションレスな仕組みの中で
     一方的に選んだものであるため、不要と判断
   - SSVノード（Dockerコンテナ）を停止し、
     クラスターから実質的に離脱する

② 本業10鍵（Lido CSM）の正式なVoluntary Exit
   - 第4章の手順を踏襲、10鍵分を計画的に実施
   - ブロック提案チェック（第11章）で安全な
     タイミングを選ぶ

③ Bond Claim（完全フロー）の実施
   - 第7章・第15章で確立した手順に沿って、
     ETH/stETHいずれかを選んで請求する
   - 「操作した」で満足せず、必ず着金確認を行う

④ 設定一式のバックアップ（第1章の手順を踏襲）
   - スクリプト、systemdサービスファイル、
     SSVのdocker-compose.yaml、
     Grafana/Prometheusの設定等

⑤ OS再インストール・LVM構成での再構築

⑥ メインネット用の新規鍵生成・1鍵運用開始
```

## 1. きっかけ：消えていた監視項目への気づき

日々`node_check`を確認する中で、ふと気づいた。テストネット時代（第2部）のnode_check.shには、ネットワーク帯域の日次・月次使用量を表示する`[10] Network Usage`という項目があったはずだが、メインネットの`node_check_mainnet.sh`には、この項目が存在していなかった。

```bash
which vnstat
```

結果、`vnstat`自体が、メインネットサーバーにはインストールされていないことが確認できた。

## 2. 「意図的な省略」ではなく「移植漏れ」

これが意図的な設計判断だったのか、単なる移植漏れだったのかを確認するため、これまでの構築記録を振り返った。結果、該当する判断の記録は見当たらず、**第7章のchrony設定漏れ、第12章のGlobal C-state Control未実施と同じ、構築時の移植漏れ**であると判断した。

> 💡 **3件目の「移植漏れ」パターン。** これで、テストネット時代に確立していた仕組みが、メインネット構築時に部分的に引き継がれなかった事例は、chrony設定・BIOS電源管理設定・ネットワーク帯域監視の3件目となった。「.serviceファイル群は忠実に踏襲されていたが、周辺の運用ツール・監視設定は部分的にしか移植されていなかった」という、これまでの傾向が、改めて裏付けられた形になる。

## 3. vnstatの導入

現在の回線環境は、テストネット時代から変わっていないことを確認した上で、導入を進めた。

```bash
sudo apt update
sudo apt install -y vnstat
sudo systemctl enable --now vnstat
```

対象インターフェースを確認する。

```bash
ip addr
```

ベアメタル環境のため、テストネット時代のVM環境（`enp0s3`）とは異なり、`enp1s0`（1000 Mbit、物理有線LAN）が対象であることを確認した。

```bash
vnstat --iflist
# Available interfaces: enp1s0 (1000 Mbit) wlp2s0 tailscale0
```

`enp1s0`は既にvnstatに認識されており、正常にデータベースが作成されていた。導入直後のため、意味のある統計はまだ蓄積されていない状態だったが、リアルタイムモードで、現状の通信量を確認した。

```bash
vnstat -l -i enp1s0
# /      rx:   11.09 Mbit/s  7452 p/s       tx:   19.60 Mbit/s  9781 p/s
```

送信（tx）が受信（rx）を上回っている。これは、バリデータ運用において最も帯域を消費するのは、他ノードへのブロックデータ配信（アップロード）であるという、テストネット時代の知見と一致していた。

## 4. node_check_mainnet.shへの組み込み

`vi`での手動編集により、既存の`[9] Security & Remote Access`と`[10] OS Update & Restart Status`の間に、新しい`Network Usage`セクションを挿入した。これに伴い、以降のセクション番号を1つずつ繰り下げた。

「OS Update & Restart Status（再起動要否の判断）」を、あえて最後のセクションに残すよう配置を調整した。日々のチェックで最後に目に入る情報が、次に取るべき行動の判断材料になるようにするためである。

念のため、スクリプトによる自動置換ではなく、手動での慎重な編集を選んだ。バリデータの署名業務に影響が及ぶ操作を、意図しない挙動によって引き起こすリスクを避けるためである。

```bash
# 10. Network Usage
echo -e "\n${YELLOW}[10] Network Usage (rx:Down / tx:Up / total)${NC}"
if command -v vnstat >/dev/null 2>&1; then
    IFACE="enp1s0"
    vnstat -i $IFACE | grep "yesterday" | awk '{
        printf " - Yesterday : ↓ %-8s | ↑ %-8s | Total: %-8s\n", $2" "$3, $5" "$6, $8" "$9
    }'
    T_DATA=$(vnstat -i $IFACE | grep "today")
    T_RX=$(echo "$T_DATA" | awk '{print $2" "$3}')
    T_TX=$(echo "$T_DATA" | awk '{print $5" "$6}')
    T_TOT=$(echo "$T_DATA" | awk '{print $8" "$9}')
    T_EST=$(vnstat -i $IFACE -d | grep "estimated" | awk '{print $8" "$9}')
    printf " - Today     : ↓ %-8s | ↑ %-8s | Total: %-8s (Est: %-8s)\n" "$T_RX" "$T_TX" "$T_TOT" "$T_EST"
else
    echo -e "${RED} - vnstat is not installed.${NC}"
fi
```

`Yesterday`行は、`vnstat`が確定させた前日分の統計を、`Today`行はリアルタイムの当日分実測値と、1日分の傾向から算出された推定値（Est）を、それぞれ表示する。

## 5. 初回実測：一見、大幅に増加したように見えた

翌日、初めて「Yesterday（前日確定値）」のデータが得られた。

```
[10] Network Usage (rx:Down / tx:Up / total)
 - Yesterday : ↓ 58.48 GiB | ↑ 82.07 GiB | Total: 140.55 GiB
 - Today     : ↓ 18.12 GiB | ↑ 27.25 GiB | Total: 45.37 GiB (Est: 150.20 GiB)
```

以前、テストネット時代に記録していた「一般的な目安」——日次30〜80GB、月間1〜2.5TB——と比較すると、この実測値（日次約140GB、月換算約4.2TB）は、大きく上回っているように見えた。当初は「メインネットへの移行に伴い、通信量が大幅に増加した」と判断しかけた。

## 6. 過去ログとの照合：Peer数との強い相関を発見

この「一般的な目安」自体が、実際にどこまで正確なものだったのかを確認するため、テストネット運用時代（<Operator番号>、10鍵運用）の、日々のヘルスチェック記録を遡って確認した。

**テストネット運用終盤（8/13、通常運用の最終盤）の実測**

```
Peer数：Lighthouse 117 / Geth 50
通信量：Today Total 110.64 GiB（Est 112.99 GiB）
```

これだけでも、「一般的な目安（30〜80GB/日）」を超える水準で、既に安定運用されていたことが分かる。さらに、Peer数がより高い水準にあった時期の記録も確認した。

**テストネット運用中、Peer数200前後を維持していた時期（7月末〜8月上旬）の実測**

| 日付 | Lighthouse Peers | Yesterday Total | Today Est |
|---|---|---|---|
| 8/2 | 200 | — | 149.54 GiB |
| 8/3 | 205 | 167.42 GiB | 166.83 GiB |
| 8/4 | 200 | 174.89 GiB | 166.94 GiB |
| 8/5 | 200 | 165.12 GiB | 160.52 GiB |
| 8/6 | 201 | 166.22 GiB | 167.78 GiB |

Peer数200前後の時期は、通信量が概ね160〜175 GiB/日のレンジで推移していた。Peer数117の時期（110〜125 GiB/日）と比較すると、**Peer数が約1.7倍になると、通信量はおよそ1.4〜1.5倍に増加する**、という相関が明確に見て取れる。

## 7. 結論：通信量はチェーンの種別ではなく、Peer数に依存する

この過去データと、今回のメインネット実測を並べると、当初の懸念は覆る。

| | Peer数 | 通信量（Total/日） |
|---|---|---|
| テストネット（8/13、運用終盤） | 117 | 約111〜113 GiB |
| テストネット（8/2〜8/6、Peer数増加期） | 200前後 | 約150〜175 GiB |
| **メインネット（9/3、現在）** | **200〜210** | **約140〜150 GiB** |

**同水準のPeer数（200前後）で比較すると、メインネットの通信量は、テストネット時代とほぼ同じか、むしろやや少ない水準に収まっている。**

つまり、通信量を左右する主な要因は、チェーンがテストネットかメインネットかではなく、**Peer数そのもの**であることが、実測を通じて確認できた。

> 💡 **「大幅に増加した」という第一印象は誤りだった。** 単一の「一般的な目安」とだけ比較して結論を出すのではなく、実際に約6ヶ月間運用してきたテストネット時代の実測ログという、より確度の高い比較対象を掘り起こしたことで、正確な結論にたどり着けた。これは、第5〜6節にわたる作業を通じて得られた、最大の教訓である。

## 8. プロバイダへの影響についての判断

契約している個人向け光回線の公式規約を確認したところ、月間データ容量の上限は設けられておらず、「一般的な利用であれば制限はございません」と明記されている。ただし、具体的な閾値は公表されておらず、複数の第三者情報源が、目安として「1日あたり30GBのアップロード」という数字を挙げている。

今回のメインネットのアップロード実測（約82 GiB/日）は、この目安を大きく超えている。しかし、**テストネット時代に、ほぼ同水準（Peer数200前後で165〜175 GiB/日のTotal、アップロードはその過半を占める）の通信を、約6ヶ月間にわたり同じ回線で継続してきた実績があり、その間、速度低下や接続不安定といった実害は一度も観測されていない。**

この長期実績に基づき、今回のメインネットの通信量についても、プロバイダへの実害はないと判断した。

```
✅ sync_distance: 0（完全同期を維持）
✅ Lighthouse Peers: 200前後を維持（減少の兆候なし）
✅ MEV-Boost Builder API: Online
```

現時点で`--target-peers`を下げるなどの能動的な対策は行わず、日々の`node_check`でこの`[10] Network Usage`とPeer数・同期状態を合わせて観察し、実際に速度低下等の兆候が現れた場合にのみ対応する、という方針とした。

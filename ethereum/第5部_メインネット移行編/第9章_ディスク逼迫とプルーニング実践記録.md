## 1. 発覚：node_checkが示した94%

Activation待ちに入って間もなく、日課の`node_check`でディスク使用率が94%に達していることに気づいた。

```
/dev/mapper/ubuntu--vg-ubuntu--lv  1.8T  1.6T  115G  94% /
```

第5部第1章で「1.5TB近い未使用領域があった」と記していた同じディスクが、わずか1年で逼迫している。まず疑ったのは、当初想定していた対処——2枚目のSSD（Samsung 990 PRO 2TB、同一モデル）の増設だった。

## 2. SSD価格の急騰という現実

第1章の時点で「約2万円台から一時12万円台まで高騰」と記録していた同モデルの価格を、複数のショップで確認した。

```
2026年8月21日時点（価格.com・ドスパラ調べ）：
  最安値（楽天エクセラー）: 89,892円
  ドスパラ:                  96,980円
```

発売当初（2022年12月）は1〜2万円台だった製品が、9〜10万円という水準になっている。世界的なNANDフラッシュメモリの供給逼迫が背景にあり、短期的な一時要因かどうかは見通せない。9万円という金額を「仕方ない」と即断する前に、技術的な対策で延命できないかを検討することにした。

## 3. 原因調査：内訳を`du`で特定する

漠然と「Gethが重い」と捉えるのではなく、`du`コマンドで内訳を確認した。

```bash
sudo du -sh /var/lib/ethereum/geth/*
sudo du -sh /var/lib/ethereum/geth/geth/chaindata
sudo du -sh /var/lib/ethereum/geth/geth/chaindata/ancient
```

```
1.6T    /var/lib/ethereum/geth/geth/chaindata
1.2T    /var/lib/ethereum/geth/geth/chaindata/ancient
```

chaindata全体1.6TBのうち、実に1.2TBが`ancient`——マージ（2022年9月）以前の、Proof-of-Work時代の履歴データを含む領域だった。差し引いた約400GBが、現在のstate（残高・スマートコントラクトの状態）を含む部分にあたる。

## 4. 技術選定：prune-stateとprune-historyの違い

Gethには、目的の異なる2種類のプルーニングコマンドが存在する。

| コマンド | 対象 | 今回のケースでの削減余地 |
|---|---|---|
| `geth snapshot prune-state` | state（現在の残高・コントラクト状態） | 数十〜100GB程度 |
| `geth prune-history` | ancient（マージ以前の履歴） | 数百GB規模 |

今回のディスク圧迫の主犯がancient側と判明した以上、`prune-history`の方が効果が大きく、かつ純粋なAttestation/Proposal専用のバリデータ運用（RPCサービスやアーカイブ用途なし）という用途にも合致していた。

## 5. 公式情報での安全性確認

`prune-history`は比較的新しい機能のため、実行前に公式情報での裏付けを取った。

geth公式ドキュメント（`geth.ethereum.org/docs/fundamentals/historypruning`）には、以下の記載がある。

> This command will scan your database and delete historical block bodies and receipts up to the merge block. The state trie and all headers are preserved. Your node remains fully functional for consensus.

state trieとヘッダーは保持されるため、コンセンサス参加機能（署名業務）には影響しないという設計になっている。

機能追加時のGitHub PR（#31384）には「Geth is not fully ready to work in this mode, please do not run this command on your production node」という初期警告があったが、これは開発初期段階のものであり、現在の公式ドキュメントにはこの警告は存在しない。使用しているGeth 1.17.4は、この機能が導入されたv1.16.0より新しいバージョンであり、その後のv1.17.2では`--history.chain postprague`という追加オプションも実装されるなど、継続的に強化されている機能であることが確認できた。

> 💡 **後から気づいた設計の反省点：** Ethereum財団のドキュメントには、新規ノード構築時に`--history.chain postmerge`フラグを指定することで、マージ前データのダウンロード自体を最初からスキップできるとの記載がある。第7章でのサーバー構築時にこのフラグを指定していれば、今回のような後からの延命措置自体が不要だった可能性が高い。次にサーバーを再構築する機会があれば、最初から組み込む。

## 6. 実践記録：安全停止からプルーニング完了まで

### 6-1. サービスの安全停止

`node_safe_stop.sh`は、第6章のバックアップから復元し、メインネット向けに再設計中の`~/mainnet-templates/`配下に置かれていた。実行権限がまだ付与されておらず（`Permission denied`）、中身を確認すると10鍵分のテストネット時代のバリデータインデックスがハードコードされたままだった。現在のバリデータはPending activation中でブロック提案の義務自体が存在しないため実害はないと判断し、権限修正は後回しにして、スクリプトの中身と同じ内容を直接コマンドで実行した。

```bash
sudo systemctl stop lighthouse-vc
sudo systemctl stop lighthouse
sudo systemctl stop mev-boost
sudo systemctl stop geth
```

4サービスとも`inactive`を確認。

### 6-2. tmuxセッションでの実行

`prune-history`の所要時間は、事前に参照した情報（コミュニティの実践記録等）では「数十分」とされていたため、SSH切断時の処理中断リスクを避ける目的でtmuxセッション内での実行を選んだ。

```bash
tmux new -s prune
```

結果的には後述の通り1秒未満で完了しており、tmuxがなくても問題は起きなかったと考えられる。ただし、実行前の時点で所要時間が正確に読めなかった以上、この判断自体は妥当だったと考えている。tmux自体の操作（デタッチ・再アタッチ）に不慣れで戸惑う場面もあり、今回が初めての使用経験だった。

### 6-3. フラグ不足による2度の失敗

```bash
sudo -u ethereum geth --datadir /var/lib/ethereum/geth prune-history
```

```
--history.chain flag is required
```

同じコマンドを気づかずもう一度実行し、同じエラーで即終了した。いずれもフラグ検証の段階で処理が始まる前に終了しており、データベースへの実害はなかった。`--help`で選択肢を確認し、純粋なバリデータ運用に適した`postmerge`を採用した。

```bash
sudo -u ethereum geth --datadir /var/lib/ethereum/geth prune-history --history.chain postmerge
```

### 6-4. 実行結果

```
Starting history pruning  head=25,800,675 target=15,537,393
History pruning completed tail=15,537,393 elapsed=716.923ms
Persisting dirty state    head=25,800,675 root=0e0a90..0321a8 layers=404
Persisted dirty state to file  path=.../triedb/merkle.journal size=515.96MiB elapsed=4.324s
Blockchain stopped
```

所要時間は**1秒未満**（716ミリ秒）だった。事前に想定していた「数十分」を大幅に下回った。`prune-state`が「trieを1件ずつ判定して書き換える」重い処理であるのに対し、`prune-history`は「削除対象範囲を確定して切り捨てる」だけの軽い処理であるため、と考えられる。

## 7. 効果測定

| | プルーニング前 | プルーニング後 |
|---|---|---|
| Used | 1.6T | 1.3T |
| Avail | 115G | 475G |
| Use% | 94% | 73% |

約300GBの削減となった。当初検討していたSSD増設（9万円）の緊急性は、この時点で大きく後退した。

## 8. サービス再起動と正常性確認

停止時と逆順（geth → lighthouse/mev-boost → lighthouse-vc）で起動した。

```bash
sudo systemctl start geth
sudo systemctl start lighthouse
sudo systemctl start mev-boost
sudo systemctl start lighthouse-vc
```

4サービスとも`active (running)`を確認した。

## 9. 「1.2TBあったはずなのに、300GBしか減っていない」への検証

効果測定の数字を見て、疑問が残った。ancientディレクトリは1.2TBあったのに、削減できたのは300GBのみ。残り約900GBはどこへ行ったのか。

この疑問に答えるため、`geth db inspect`でデータベースの内訳を検証した。このコマンドはデータベースを排他的に開くため、再度サービスを停止する必要があった。

```bash
sudo systemctl stop lighthouse-vc
sudo systemctl stop lighthouse
sudo systemctl stop mev-boost
sudo systemctl stop geth

sudo -u ethereum geth --datadir /var/lib/ethereum/geth db inspect
```

全データベース（1.33TiB、58億件のキー）を走査するため、完了までに約8分を要した。結果、疑問への答えが明確になった。

```
+-----------------------+-----------------------------+-------------+------------+
|       Database        |          Category           |    Size     |   Items    |
+-----------------------+-----------------------------+-------------+------------+
| Ancient store (Chain) |           Headers           |  12.79 GiB  |  25800881  |
| Ancient store (Chain) |           Bodies            | 599.99 GiB  |  10263488  |
| Ancient store (Chain) |          Receipts           | 246.69 GiB  |  10263488  |
+-----------------------+-----------------------------+-------------+------------+
|                       |            Total            |  1.33 TiB   | 5809441167 |
+-----------------------+-----------------------------+-------------+------------+
```

（全カテゴリの内訳は本章末尾に記載）

Ancient store (Chain)のBodies（599.99 GiB）とReceipts（246.69 GiB）だけで、合計約847GBを占めている。`prune-history --history.chain postmerge`が削除するのは**マージ以前**（2022年9月15日以前、PoW時代）のBodies・Receiptsのみであり、マージ**以降**——つまり現在運用中のPoSチェーンのBodies・Receiptsは、フルノードとして保持し続ける設計になっている。これは削除し忘れではなく、現行のGethの仕様上、削除する手段が存在しない領域だった。

847GBは、マージ（2022年9月）から現在（2026年8月）までの約4年分の蓄積にあたる。この部分は`prune-history`でも`prune-state`でも削減できず、Ethereum財団が構想しているPartial History Expiry（直近N日だけ残すローリング方式の履歴削減）が実装されるまでは、対処手段が存在しない。

> 💡 **今回の検証で判明した限界：** 今回の300GB削減は、あくまで「マージ以前の過去データ」という一度きりの塊を清算したものであり、マージ以降のBodies・Receiptsは今後も新しいブロックが生成されるたびに増え続ける。今回の対処で「解決した」わけではなく、「一度だけ延命した」というのが正確な認識である。

## 10. まとめ

```
① ディスク逼迫94%の主犯は、state（約400GB）ではなく
   ancient（マージ以前の履歴、1.2TB）だった
② SSD価格が当初想定の3〜5倍（9〜10万円）に高騰していたため、
   技術的対策を優先する判断をした
③ prune-stateとprune-historyは対象が異なり、
   今回のケースではprune-historyの方が効果が大きかった
④ prune-historyはgeth 1.16.0以降の正式機能であり、
   継続的に強化されている（1.17.2でpostprague対応）
⑤ node_safe_stop.shは第6章のバックアップから復元し
   再設計中だったため、実行権限や古いインデックスが
   残っていたが、Pending activation中のため実害はなかった
⑥ --history.chainフラグを忘れて2回失敗したが、
   フラグ検証の段階で終了するため実害はなかった
⑦ 実行時間は事前想定（数十分）に反し、1秒未満で完了した
⑧ 結果、94%→73%（約300GB削減）となり、
   SSD増設の緊急性を大きく後退させることができた
⑨ db inspectによる検証で、マージ以降のBodies・Receipts
   （約847GB）は現行Gethでは削減不可能と判明した。
   今回の対処は「解決」ではなく「一度きりの延命」である
⑩ 「最初から--history.chain postmergeで同期していれば
   ancient側の問題自体が起きなかった」という気づきは、
   次回のサーバー構築時の教訓として残す
```

## 1. きっかけ：Activation後を見据えた素朴な疑問

Activationが近づく中、「本格的に署名業務が始まったら、定期バックアップの設定も必要になるのでは」という、ごく自然な確認から始まった。記憶では「週1回、iCloudのフォルダに自動転送していたはず」というものだった。

## 2. 発見：5件目の移植漏れ

実機を確認したところ、記憶とは裏腹に、サーバー側に何も存在していなかった。

```bash
which node_backup
crontab -l | grep node_backup
ls -la ~/node_backups/ 2>/dev/null
```

```
✅ node_backup コマンド：存在しない
✅ crontabへの登録：no crontab（何も登録されていない）
✅ ~/node_backups/ ディレクトリ：存在しない
```

これは、第15章（swappiness）に続く、**5件目の「移植漏れ」**だった。テストネット期（第4部第1章）に確立・検証済みだった仕組みが、メインネット構築時にまるごと引き継がれていなかった。

## 3. 設計の再確認：第2部と第4部第1章の食い違い

過去の記録を確認すると、設計自体は2つの経路で残っていた。

```
第2部 Step 30〜32：node_backup.sh、一般ユーザーのcrontab想定、
                   週1回のWindowsタスクスケジューラー転送
第4部第1章（テストネット実運用）：node_backup、rootのcrontab、
                   scpでの手元PCへの引き揚げ
```

**実際にテストネット期に機能していたのは、後者（rootのcrontab）方式**だった。理由は、バックアップスクリプトが`/var/lib/lido-csm/`（`ethereum`ユーザー所有）を読み込む必要があり、一般ユーザー権限では実行できないため。この実績のある方式を、メインネットでも採用することにした。

## 4. 実機のファイル構造を先に確認する

スクリプトを作る前に、思い込みで進めず、実際のパスを一つずつ確認した。

```bash
sudo ls -la /var/lib/lido-csm/
sudo ls -la /var/lib/lido-csm/validators/
```

```
/var/lib/lido-csm/
├── keystore_password.txt          ← 除外対象
├── secrets/                       ← 除外対象
└── validators/
    ├── 0x81819a69.../             ← 鍵本体ディレクトリ（除外対象）
    │   ├── keystore-....json      ← 鍵本体（暗号化済み）
    │   └── keystore-....json.lock ← ロックファイル（実害なし）
    ├── api-token.txt              ← 含める
    ├── logs/                      ← 除外（署名記録そのものではない）
    ├── slashing_protection.sqlite ← 【最重要】含める
    ├── validator_definitions.yml  ← 含める
    └── validator_key_cache.json   ← 含める
```

この確認により、第2部の除外パターン（`*/*.json`）が実際のファイル名と正しくマッチすることも検証できた。

> 💡 **寄り道：`keystore_password.txt`が平文であることへの懸念。** 確認の過程で、このファイルが暗号化されていない平文であることに気づいた。しかし、パスワード単体では意味を持たず、暗号化されたkeystore本体（`.json`）とセットで初めて鍵が開く。今回のバックアップ設計は、この2つを**どちらもバックアップから除外する**ことで対策しており、暗号化という追加対策は不要と判断した。ファイル権限（`-rw-------`）による保護も既に適切だった。

## 5. node_backup.shの作成とテスト

実機のパスに合わせて、第2部の設計を修正した。

```bash
#!/bin/bash

BACKUP_DIR="/home/<your_user>/backups"
mkdir -p "$BACKUP_DIR"

BACKUP_FILE="$BACKUP_DIR/node_backup_$(date +%Y%m%d_%H%M%S).tar.gz"

tar -czpf "$BACKUP_FILE" \
    --exclude='/var/lib/lido-csm/validators/*/*.json' \
    --exclude='/var/lib/lido-csm/secrets' \
    --exclude='/var/lib/lido-csm/keystore_password.txt' \
    --exclude='/var/lib/lido-csm/validators/logs' \
    /var/lib/lido-csm/ \
    /etc/systemd/system/geth.service \
    /etc/systemd/system/lighthouse.service \
    /etc/systemd/system/lighthouse-vc.service \
    /etc/systemd/system/mev-boost.service \
    /home/<your_user>/node_check_mainnet.sh \
    /home/<your_user>/node_safe_stop_mainnet.sh \
    /home/<your_user>/node_safe_start_mainnet.sh \
    /etc/chrony/chrony.conf 2>/dev/null

find "$BACKUP_DIR" -name "node_backup_*.tar.gz" -mtime +30 -delete

echo "Backup completed: $BACKUP_FILE"
echo "Backup size: $(du -sh $BACKUP_FILE | cut -f1)"
```

テスト実行の結果、バックアップサイズは**8.9KB**（鍵1本分の軽量な構成）。中身を検証したところ、除外・包含ともに設計通りだった。

## 6. cron自動化

```bash
sudo crontab -e
```

```
# 毎日午前3時にバックアップを自動実行
0 3 * * * /home/<your_user>/node_backup.sh >> /home/<your_user>/backups/backup.log 2>&1
```

> 💡 **UTC/JSTの注意（第17章からの継続的な学び）。** サーバーはUTC運用のため、この「午前3時」は実際にはJST正午（12:00）を意味する。第17章で得た教訓がここでも活きた。

## 7. Windows側：反映されていなかったSSH鍵の指定

テストネット期のバッチファイル（`auto_backup.bat`）を、IPアドレスとパスをメインネット用に書き換えて実行したところ、エラーに遭遇した。

```
<your_user>@<Tailscale IP>: Permission denied (publickey).
scp: Connection closed
```

普段のSSH接続（PowerShellでのエイリアス）は問題なく通っていたため、原因の切り分けに時間を要したが、実際には**第7章6節で既に明記されていた内容**だった。メインネット用に`id_ed25519_mainnet`という非標準の鍵名を発行しており、`-i`オプションでの明示指定、または`~/.ssh/config`でのエイリアス設定が必要——という点は、構築時点で既に分かっていたことであり、単に`auto_backup.bat`側への反映が漏れていただけだった。

```bat
scp -p -i "C:\Users\<your_user>\.ssh\id_ed25519_mainnet" "<your_user>@<Tailscale IP>:~/backups/node_backup_*.tar.gz" "<転送先パス>"
```

`-i`オプションを追加したところ、正常に転送できることを確認した。

## 8. タスクスケジューラーの再有効化

テストネット期のタスク「Ethereum Node Auto Backup」は、無効化された状態で残っていた。これは見落としではなく、第5部第6章8節で記録されている通り、**テストネット撤収時に「削除ではなく無効化」を意図的に選択し、メインネット移行後に同じ仕組みをそのまま再利用できるよう、計画的に温存されていたもの**だった。

その計画通り、今回トリガー時刻を「毎週月曜13:00」に更新し、以下2点を確認した上で有効化した。

```
✅ ネットワーク条件：Tailscale接続時のみ実行（サーバー到達不能時の失敗を防ぐ）
✅ 「スケジュールされた時刻に開始できなかった場合、すぐに実行する」
   → PCの電源が入っていない場合でも、次回起動時に取りこぼしを自動実行
```

## 9. バックアップの整合性検証（安全な範囲での確認）

Activation直前というタイミングを踏まえ、本番の`/var/lib/lido-csm/`には一切触れない、安全な範囲での検証に留めることとした。

```bash
mkdir ~/restore_test
tar -xzpf ~/backups/node_backup_20260915_030001.tar.gz -C ~/restore_test
find ~/restore_test -type f
```

展開結果は、除外・包含とも設計通り。さらに、`slashing_protection.sqlite`が破損なく展開できているかを確認した。

```bash
file ~/restore_test/var/lib/lido-csm/validators/slashing_protection.sqlite
```

```
SQLite 3.x database, last written using SQLite version 3051001,
file counter 4, database pages 7, cookie 0x4, schema 4, UTF-8, ...
```

正常なSQLiteファイルとして認識され、破損の兆候は一切なかった。確認後、テスト用ディレクトリは削除し、本番環境には何の影響も残さなかった。

> 💡 **今回検証しなかったこと。** 今回の検証は「バックアップファイルが壊れていないか」という一次的な健全性チェックに留めた。Lighthouseの公式コマンド（`lighthouse account validator slashing-protection import`）を使った、実際のVCへのインポートまで含むフルの復元テストは、Activation後、落ち着いたタイミングで別途行うこととした。

## 10. 寄り道：バックアップファイルの所有権について

検証中、`~/backups/`ディレクトリが`root:root`所有になっていることに気づいた。これは`sudo`でスクリプトを実行し続けた結果であり、意図した通りの挙動である。

一点確認しておきたかったのは、「rootユーザーへの直接ログイン・なりすましを禁止する」という、第2部で実施済みのセキュリティ設計（`passwd -l root`）との整合性だった。整理すると、両者は矛盾しない。

```
✅ 禁止している：rootとして直接ログインする経路
✅ 許容している：sudoによる、一般ユーザーからの一時的な権限昇格
```

`sudo`実行の結果としてファイルがroot所有になるのは、Linuxの正常な挙動であり、今回のケースで問題は生じていない。

## 11. まとめ

```
① バックアップの仕組みが、メインネット構築時に一切移植されていなかった
   ことを発見した（chrony・BIOS・vnstat・swappinessに続く5件目の移植漏れ）
② 第2部（一般ユーザーcrontab想定）と第4部第1章（rootのcrontab、実績あり）
   の2つの設計が存在し、実績のある後者を採用した
③ 実機のファイル構造を事前に確認することで、除外パターンの妥当性を
   検証してから、node_backup.shを確定させた
④ サーバー側（cron自動化）・Windows側（SSH鍵指定漏れの発見と修正、
   タスクスケジューラー再有効化）の両方を整備し、
   「3重の保護」（サーバー→Windows→iCloud）を再構築した
⑤ Activation直前というタイミングを踏まえ、本番環境に影響を与えない
   範囲（tar展開とファイル整合性確認）でバックアップの健全性を検証した
⑥ 副次的に、静的設定のテンプレート（~/mainnet-templates/）の存在や、
   バックアップファイルの所有権とセキュリティ設計の整合性についても
   確認できた
```

「本当に壊れた時、実際に復元できるか」というフルの検証はまだ残っているが、**バックアップという安全網そのものが存在しなかった状態から、日々自動で積み上がる状態へ**、Activationを前に間に合わせることができた。

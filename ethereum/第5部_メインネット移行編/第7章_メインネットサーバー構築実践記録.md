## 1. OSインストール

Ubuntu Server 24.04.4 LTSを、GPT/UEFI構成でクリーンインストールした。ホスト名は`lide-csm-bare`から**`mainnet-csm-bare`**に変更し、テストネットとの区別を明確にした。

## 2. ストレージ：LVM構成の判断（第2部からの変更点）

パーティション構成自体は第2部と同様だが、**ルート（`/`）のサイズを、インストーラーのデフォルト100GBから500GBに変更**した。

判断の根拠は、LVMの特性にある。**足りなくなってからの拡張は容易**（`lvextend`＋`resize2fs`でオンライン拡張可能）だが、逆に一度大きく確保しすぎたものを縮小するのはリスクが高い。縮小コマンド自体は存在するが、ファイルシステムがマウントされたまま実行すると破損リスクがあるため、原則オフライン作業が必要になる。拡張はオンラインで完結する一方、縮小はそうはいかない、という非対称性が、今回「少なめに確保し、必要になったら足す」という判断の根拠になった。

### 構成確認コマンド

```bash
# Physical Volume（物理ボリューム）の確認
sudo pvs

# Volume Group（ボリュームグループ）の確認
sudo vgs

# Logical Volume（論理ボリューム）の確認
sudo lvs
```

### 実測結果

```
$ sudo pvs
  PV             VG        Fmt  Attr PSize  PFree
  /dev/nvme0n1p3 ubuntu-vg lvm2 a--  <1.82t <1.33t

$ sudo lvs
  LV        VG        Attr       LSize
  ubuntu-lv ubuntu-vg -wi-ao---- 500.00g
```

物理ボリューム全体1.82TBのうち、ルート用に割り当てた500GBを差し引いた**約1.33TBが、未割当のまま将来の拡張用に残っている**ことが確認できた。

### 拡張時のコマンド（次回以降の参考）

```bash
# 例：ルートを+200GB拡張する場合
sudo lvextend -L +200G /dev/ubuntu-vg/ubuntu-lv
sudo resize2fs /dev/ubuntu-vg/ubuntu-lv
```

## 3. バックアップの復元で気づいたこと（新しい学び）

第5部第6章で作成した`testnet-archive`と`mainnet-templates`は、Windows母艦PC（iCloud経由）に保管していた。今回、これを**新サーバーへ「逆方向」に転送する**必要があった。

作業中、`mainnet-templates`のテンプレートファイルを参照しようとして「存在しない」というエラーに遭遇し、そこで初めて「まだ新サーバーには転送していない」ことに気づいた。Windows母艦PCが、旧サーバーと新サーバーの間の**中継地点（ハブ）**として機能する構造を、実務の中で再確認する形になった。

```bash
# 新サーバー側で受け皿を作成
mkdir -p ~/mainnet-templates

# Windows側から転送（旧サーバーからではなく、iCloud経由の母艦PCから）
scp -i ~/.ssh/id_ed25519_mainnet <転送元パス>\* <your_user>@<Tailscale IP>:~/mainnet-templates/
```

> 💡 **教訓：「バックアップを取った」ことと「復元先で使える状態にする」ことは別の作業。** 転送先の作業ディレクトリを、事前に用意しておく癖をつけると良い。

## 5. 今回初めて遭遇した問題：cloud-initによるSSH設定の上書き

パスワード認証を`sshd_config`本体で無効化したにもかかわらず、実際にはパスワードでログインできてしまう現象が発生した。

原因は、`/etc/ssh/sshd_config.d/50-cloud-init.conf`という、**Ubuntu Serverインストーラーが自動生成したファイル**が、`sshd_config`本体の設定を後から上書きしていたためだった。

```bash
sudo cat /etc/ssh/sshd_config.d/50-cloud-init.conf
# → PasswordAuthentication yes
```

このファイルを削除し、`sshd`を再起動することで解決した。

```bash
sudo rm /etc/ssh/sshd_config.d/50-cloud-init.conf
sudo systemctl restart ssh
```

> ⚠️ **第2部の時点では、この問題は記録されていなかった。** Ubuntu Serverのバージョンやインストーラーの挙動の違いによるものと考えられる。今後、同じ構築をする際は、パスワード認証無効化の直後に`sshd_config.d/`配下も必ず確認すべき、という新しい教訓が得られた。

## 6. SSH鍵の使い分け

テストネット時代の鍵（`id_ed25519`）とは別に、**`id_ed25519_mainnet`という新しい鍵ペア**をメインネット用に発行した。同じPC内に複数のed25519鍵が並存する場合、SSHクライアントは標準的な名前（`id_ed25519`等）を自動的に優先するため、非標準の名前を使う場合は`-i`オプションでの明示指定、または`~/.ssh/config`でのエイリアス設定が必要になる。

```
Host mainnet-csm-bare
    HostName <Tailscale IP>
    User <your_user>
    IdentityFile ~/.ssh/id_ed25519_mainnet
```

## 9. Checkpoint Syncの実測結果

3つのサービス（Geth、MEV-Boost、Lighthouse）を起動した結果、Lighthouseは起動からわずか数分で`sync_distance: 0`（Headへの完全追随）に到達した。

```json
{
  "is_syncing": false,
  "is_optimistic": true,
  "sync_distance": "0"
}
```

`is_optimistic: true`は、Execution Layer（Geth）側の検証がまだ完了していないことを示す、正常な中間状態である。Geth自体は、この時点でまだビーコンヘッダーの同期中だった。

## 10. 同期中のディスク逼迫と、LVM拡張の実例

サービス起動後、Gethの同期ログを継続的に確認したところ、**当初確保していた500GBでは、同期完了時に容量不足に陥る可能性がある**ことが判明した。

### 見積もりの根拠

```
State download: synced=12.74%, state=52.40GiB
  → 完了時推定サイズ ≈ 52.40 ÷ 0.1274 ≈ 約411GiB

Chain download: synced=18.77%, chain=21.37GiB
  → 完了時推定サイズ ≈ 21.37 ÷ 0.1877 ≈ 約114GiB

合計推定 ≈ 500GiB前後（当初確保量とほぼ同じか、それを超える水準）
```

### 対応：オンラインでのLVM拡張

Gethを停止することなく、稼働させたまま拡張を実施した。

```bash
sudo lvextend -L +500G /dev/ubuntu-vg/ubuntu-lv
sudo resize2fs /dev/ubuntu-vg/ubuntu-lv
```

```
$ df -h /
Filesystem                         Size  Used Avail Use% Mounted on
/dev/mapper/ubuntu--vg-ubuntu--lv  984G   94G  845G  10%
```

500GB → 1TBへ、サービスを一切止めることなく拡張できた。これは、まさに第2節で述べた「LVMの拡張はオンラインで容易」という特性が、机上の理屈ではなく実際に活きた場面だった。

> ⚠️ **今回、ディスク逼迫は監視アラートによってではなく、手動でのログ確認によって発見した。** この時点で、Grafana/Prometheusによる監視体制がまだ新環境に構築されていなかったため、「事前に自動で警告される仕組み」が存在しなかった。仮に監視なしのまま放置していた場合、Geth・Lighthouseが書き込み失敗によりクラッシュし、データ破損や再同期が必要になっていた可能性がある。監視体制の再構築を後回しにすることのリスクを、実地で認識する結果となった。

### 拡張後の同期進捗（参考推移）

| 経過時間 | State同期 | Chain同期 | ディスク使用 |
|---|---|---|---|
| 起動直後 | 12.74% | 18.77% | 23G |
| +8分 | 16.81% | 21.21% | 110G |
| +16分 | 23.56% | 25.59% | 154G |

拡張後の845GB（後に785GBまで消費が進行）の空き容量に対し、上記推移から算出される追加消費見込みは十分に収まる範囲であり、拡張の判断は結果的に適切だったと考えられる。

### さらに2回の追加拡張（合計4回）

その後も同期は進み、State downloadは開始から2時間13分31秒で完了（確定サイズ439.09GiB）した一方、Chain downloadの総量見積もりは進行とともに何度も上振れした。

| 時点 | Chain進捗 | Chain完了時推定サイズ |
|---|---|---|
| 開始直後 | 12.74% | 約500GiB |
| 中盤 | 68.83% | 約761GiB |
| 終盤 | 74.88% | 約939GiB |

見積もりが同期の進行とともに一貫して上振れし続けたため、都度LVM拡張で対応した。

```bash
# 2回目：1TB → 1.46TB
sudo lvextend -L +500G /dev/ubuntu-vg/ubuntu-lv
sudo resize2fs /dev/ubuntu-vg/ubuntu-lv

# 3回目：1.46TB → 1.8TB
sudo lvextend -L +300G /dev/ubuntu-vg/ubuntu-lv
sudo resize2fs /dev/ubuntu-vg/ubuntu-lv

# 4回目：1.8TB → 1.81TB（Volume Group残余量のほぼ全て）
sudo lvextend -L +50G /dev/ubuntu-vg/ubuntu-lv
sudo resize2fs /dev/ubuntu-vg/ubuntu-lv
```

最終的に、Volume Groupの未割当領域（`VFree`）は約10GBまで減少し、この1枚のSSDでの拡張余地は実質的に使い切った。

```
$ sudo vgs
  VG        #PV #LV #SN Attr   VSize  VFree
  ubuntu-vg   1   1   0 wz--n- <1.82t 9.96g
```

> 💡 **教訓：ディスク見積もりは、同期の初期段階ほど不正確になりやすい。** State downloadのように完了間際まで精度が上がりにくい種別のデータと、Chain downloadのように後半にサイズが急増する種別のデータが混在するため、単純な進捗率からの外挿は当てにしすぎず、余裕を持った拡張判断を都度下す方が安全である。

### Gethの完全同期達成

開始から約24時間後、Execution Layer側の検証を含めた完全同期に到達した。

```json
{
  "is_syncing": false,
  "is_optimistic": false,
  "sync_distance": "0"
}
```

`is_optimistic`が`false`に切り替わったことが、Consensus Layer・Execution Layer双方の同期が完全に完了したことを示す、確実な指標である。ログの表現も、「Syncing」から「Chain head was updated」「Imported new potential chain segment」という、通常運用時のものへと切り替わった。

### 所要時間の総括：テストネットとの比較

| 項目 | テストネット（Hoodi、第2部の目安） | メインネット（今回の実測） |
|---|---|---|
| chain download | 約30〜60分 | 約24時間（Chain単体で939GiB規模） |
| state download | 約1〜2時間 | 2時間13分（確定439.09GiB） |
| Gethディスク使用量 | 189GB | 約1.6TB規模 |

メインネットの規模は、テストネットの5〜6倍に達した。第2部で確立した所要時間の目安は、あくまでテストネット規模のものであり、メインネットにはそのまま適用できないことが、実測を通じて明らかになった。

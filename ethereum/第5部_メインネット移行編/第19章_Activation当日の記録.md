## はじめに：Activationとは何か、ここまでの経緯

**Activation（活性化）とは。** バリデータが、正式に「仕事を始める」状態になることである。Activationを迎えると、バリデータに署名（Attestation）やブロック提案の役割が割り当てられ、報酬が入り始める。逆に、役割を果たせない時間が続くと、小さなペナルティを受ける。

**ここまでの経緯。** Lido CSM（Community Staking Module）では、オペレーターが32 ETHを自分で用意するのではなく、Bond（担保）を預けて鍵を登録する。そのうえで、Lidoのステーキングプールから、32 ETHがその鍵に割り当てられる。

```
2026年8月20日ごろ  鍵の生成とNode Operator登録（第8章）
                    32 ETHの入金が、ビーコンチェーンに記録される
                    （beaconcha.inのDepositsに「38日22時間前」と表示。
                     9月28日夜の時点からの逆算）
8月下旬〜9月      入金の反映を待つ列（Deposit queue）に並ぶ
9月28日 7:40頃   Deposit credited（入金がバリデータの登録簿に反映）
9月28日 8:25頃   Activation
```

デポジットからActivationまで、約38日（5週間強）かかった。待ち時間の大半は、最初の列（Deposit queue）だった。beaconcha.inに表示された順位は、次のように減っていった。

```
9/12 #10,384  →  9/15 #8,696  →  9/21 #4,966  →  9/24 #1,922
9/26 #746     →  9/27 #198    →  9/28 #2
```

列の進みは、ネットワーク全体で処理できる量に上限があるため、自分では早められない。待つ間にできるのは、ノードを安定させ、監視と記録を整えることだった。第5部の第9章〜第18章は、主に、この待ち時間に行った作業である。

**段階ごとの見え方。** 同じ状態が、beaconcha.inと`node_check`で、違う名前で表示される。

| 段階 | beaconcha.in | `node_check`（ビーコンノードのAPI） | 意味 |
|---|---|---|---|
| 入金の反映待ち | Pending（Deposit queue） | 該当なし（`unknown validator`、第16章） | 入金は認識されたが、バリデータとしては未登録 |
| Deposit credited後 | Pending（Activation queue）、バリデータ番号が付く | `pending_initialized` → `pending_queued` | 登録簿に載り、番号が付いた。まだ署名はしない |
| Activation | Active | `active_ongoing` | 署名の役割が始まる |

Deposit creditedからActivationまでは、今回は約45分（7エポック）だった。本章は、この日に起きたことの記録である。

### 4-2. どのプロセスの通信か

`vnstat`は、サーバー全体の通信量しか見せない。「誰が」通信しているかを見るには、別の道具が要る。ここで使ったのが`nethogs`である。

```bash
sudo apt install -y nethogs
sudo nethogs -t -c 6 enp1s0
```

`nethogs`は、ネットワークカード（ここでは`enp1s0`）を通る通信を、プロセスごとに分けて、リアルタイムで表示する。`-t`はテキスト形式での出力、`-c 6`は6回、区切って表示したら自動で終了する指定である。1回ごとに測り直しているのではなく、起動してからの積算（足し算されていく量）を、6回、スナップショットとして見せる。`ss`や`vnstat`と違い、**今、その瞬間、動いている間しか見えない**。終了すれば、その時見ていた内容は、どこにも残らない。

導入し、6回の計測を行った。

`nethogs`の出力には時刻が付かないため、計測した時刻は、前後の`node_check`やログ確認の時刻から推定した。

```
1回目：JST 11時台後半〜12時ごろ（バックフィル中。11:46の node_check の後）
2回目：JST 15時前後　　　　　　（バックフィル完了後。14:44の node_check の後）
```

受信（KB/s）の推移を、値が出た5回ぶん、計測の順に並べる。

| プロセス | 1回目（バックフィル中、JST 12時ごろ） | 2回目（完了後、JST 15時前後） |
|---|---|---|
| lighthouse | 305 → 889 → 1,934 → 2,586 → 2,660 | 1.9 → 6.9 → 10.9 → 40.9 → 65.5 |
| geth | 7 → 57 → 81 → 101 → 116 | 14 → 30 → 73 → 192 → 293 |

どちらの計測でも、計測が進むほど値が大きくなる傾向があった（原因は確認していない）。そのため、最初の値と最後の値を混ぜて比べず、**最後の値どうし**で見る。lighthouseの受信は、バックフィル中の約2,660 KB/sから、完了後の約65 KB/sへ、約40分の1に下がっていた。

一方、gethの受信は、完了後のほうがバックフィル中より大きい値が出ている（116 → 293）。6回だけの短い計測で、この差の意味は判断していない。送信は、lighthouseがバックフィル中で約34〜90・完了後で約0.3〜94、gethがバックフィル中で約20〜140・完了後で約18〜381 KB/sだった。

**受信の増加は、lighthouseが原因だった。** バックフィル中は約2.6MB/sを受信していたが、完了後には大きく下がっていた。

### 4-3. ログの手がかり

lighthouse（ビーコンノード）のログに、これまで出ていなかった行があった。

```
22:59:41 UTC  Downloading historical data columns
              distance: "131008 slots (2 weeks 4 days)", est_time: "4 hrs 32 mins"
```

過去約2週間4日分のデータカラム（PeerDASで分散保管されるデータの単位）を、さかのぼって取得するバックフィルだった。開始時の見積もりは約4.5時間で、実際にも約5時間で終わった（第4-5節）。

**「バックフィル」は、構築時に何度も待った「同期」とは、別のものである。** 第2部・第7章で待った同期は、ブロックチェーン本体（ブロックの中身）を、順に取り込む作業で、geth・lighthouseが動き出す前に、必ず終える必要があった。今回のバックフィルは、それとは別に、「データカラム」という、別の種類のデータを、ノードが正常に動き出した後から、追加で埋め直す作業である。

**データカラムとは何か。** Ethereumは、Fusakaアップグレード（PeerDAS）以降、L2（レイヤー2）が使う大きなデータ（ブロブ）を、そのままの形では配らず、誤り訂正符号をかけて、128個の断片（データカラム）に分割し、ネットワーク全体で分担して保管する設計になっている。1台のノードが全部を持たなくても、十分な数のノードから断片を集めれば、元のデータを復元できる。どのノードが、どの断片を、どれだけ保管するかを決める単位が「カスタディグループ（custody group）」である。

### 4-4. なぜ始まったのか（仕様との照合）

Ethereum公式のconsensus-specs（Fulu）には、バリデータが接続されたノードは、接続バリデータの実効残高に応じた数のカスタディグループを保管し、その要件が増えた場合にはバックフィルしてよい、という趣旨の記述がある。Lighthouse公式ドキュメントにも、バリデータが接続されたノードは、保管すべきカラム数が増える、と書かれている。

バリデータ接続前後で、保管する量が、実際に増えたかどうかは、lighthouseのAPIに、直接、問い合わせて確かめられる。

```bash
curl -s http://localhost:5052/lighthouse/custody/info | jq
```

`5052`は、lighthouse（ビーコンノード）が、自分の状態を、外部から確認できるように、開いている窓口（API）のポート番号である。`jq`は、返ってきた結果（JSON形式）を、見やすく整形する道具である。当日、この方法で確認した結果は、次のとおりだった（バックフィル完了前、JST 12時台に取得）。

```
custody_group_count: 8
earliest_custodied_data_column_slot: 15202080
```

「バリデータ接続でカラム保管が増え、その分をさかのぼって取得した」という説明は、仕様と、バックフィルの開始時刻（バリデータの認識の約16分後）の両方と整合する。ただし、**接続前の`custody_group_count`を測っていない**ため、「増えた」ことの直接の証拠はない。

**翌9/29、あらためて`custody/info`を確認すると、次のとおりだった。**

```
custody_group_count: 8
earliest_custodied_data_column_slot: 15187616
```

`custody_group_count`（保管する量、8個）は、変わっていない。一方、`earliest_custodied_data_column_slot`（保管している中で、一番古いスロット）は、9/28時点の15202080より、約14,000スロット（約2日分）、さらに過去にさかのぼっていた。

はじめ、「バックフィルは、もう終わったはずなのに、なぜ、また動いているのか」と思ったが、これは、Ethereum公式の仕様（consensus-specs、Fulu）に、明記されている、正常な動きだった。保持すべき期間（約18日、`MIN_EPOCHS_FOR_DATA_COLUMN_SIDECARS_REQUESTS`）は、「その時、その時の、現在時刻」から、逆算して決まる、動く基準として定義されている。時間が進めば、保持すべき範囲そのものが、まるごと、前へずれる。`custody_group_count`は変わっていないので、「量が、また増えた」のではなく、「窓（期間）が、日々、前へ動いている」だけである。

参考：LighthouseのGitHubには、同じ`Downloading historical data columns`の最中に、受信が大きく膨らんだという報告（約550バリデータの大規模環境、別バージョンの報告）がある。症状は似ているが、規模が全く違うため、同一の原因かどうかは分からない。

**引き金は、Activation本体ではない。** 第1節の時系列を見直すと、バックフィルの開始（22:59:41）は、Activation（23:25:17）より26分早く、バリデータの存在が確認された時刻（22:43:59）から、約16分後だった。「バリデータが、ノードに接続された（Validator Clientが、その鍵を認識した）」ことが、直接の引き金だったと見るほうが、時刻の並びに合う。MEV-Boostの登録が、Activation本体を待たずに動き出していた（第3節）のと、同じ構造である。

**今のメインネット環境にとっては、初めて起きたことである。** ただし、「今まで、起きていなかった」とは、言い切れない。テストネット期にも、バリデータを稼働させ、署名していた時期があり、同じ仕組みで、バックフィルは、起きていたはずである。`vnstat`自体は、テストネット期にも導入していたが、当時は、プロバイダとの通信量契約を把握する目的で使っており、日々の通信量を、比べる使い方は、していなかった（第14章）。そのため、気づかずに過ぎていた、と考えるほうが、自然である。

## 5. 初日の報酬と、最初のスイープ出金

Activationから約11時間後、beaconcha.inで次の数字を確認した。

```
Attestations   : 104件（100%）
Total missed   : 0
Total Income   : +0.00082 ETH（1エポックあたり約8,200 Gwei）
Balance        : 32.00012 ETH
```

報酬の累計が0.00082 ETHなら、Balanceは32.00082になるはずだった。実際は32.00012で、**約0.0007 ETHが減っていた。** `node_check`でも、14:44の32.0005 ETHから、19:30には32.0001 ETHへ下がっていた。

### 5-1. 仮説と裏取り

まず、署名が外れて報酬が減った可能性を確かめた。署名は100%成功しており、欠測の報酬もゼロだった。次に、出金資格情報が`0x01`であることから、**32 ETHを超えた分の自動出金（スイープ）**の可能性を確かめた。

公式ドキュメントには、`0x01`の資格情報では、32 ETHを超えた分が自動的に出金アドレスへ送られること、その頻度は平均週1回程度であることが書かれていた。

```
beaconcha.inのWithdrawals（Consensus Layer）：
  epoch 478,543 / slot 15,313,391（JST 17:38頃）
  宛先：0xB9D7934878B5FB9610B3fE8A5e441e8fad7E293f
  金額：0.000699 ETH

0.000699（出金）+ 0.00012（現在の超過分）= 0.000819
Total Income 0.00082 ETH と一致
```

Balanceの減少は、**部分出金（スイープ）**で説明がついた。

### 5-2. 宛先の確認（設計どおりの再確認）

出金アドレスは、鍵の生成時に指定した宛先で、第1部・第2部の手順書にも、Mainnet用のLido公式Withdrawal Vaultアドレスとして載せている。今回新しく分かったことではない。ただ、実際の出金が、その宛先へ向かったかを、初めて記録で確認できたため、出金資格情報を全文で突き合わせ直した。

```
確認した出金資格情報：
0x010000000000000000000000b9d7934878b5fb9610b3fe8a5e441e8fad7e293f

Lido公式ドキュメント（WITHDRAWAL_CREDENTIALS）：同一
```

`0x01`は資格情報の種類、続く`0`の並びは詰め物で、末尾の40桁がアドレスである。このアドレスは、Lidoの`WithdrawalVault`（ビーコンチェーンからの部分出金・完全出金を集める、DAO管理のコントラクト）である。**超過分は、設計どおり、個人のウォレットではなく、Lidoの公式コントラクトへ向かった。**

### 5-3. 出金時刻の見積もり

出金の時刻を、報酬ペースを一定と仮定して「epoch 478,548前後」と見積もったが、実際は478,543で、約5エポックのずれがあった。報酬ペースからの逆算では、時刻を正確には出せなかった。

次回の出金は、beaconcha.inが約7日14時間後、0.000115 ETHと見込んでいる。これは同サイトの見積もりで、確認はしていない。


このアラートは、Activation前に作った仮の指標が鳴ったものである。beaconcha.inの署名成績は、同日19時台の時点で、Activation後の欠測がゼロだった。

### 6-1. 翌日、あらためて行ったネットワーク面の確認

本番環境に移行したことを受け、翌9/29、あらためてセキュリティ面（不正な通信がないか）を確認した。特に、通信量と、許可していないポート・プロセスによる通信を、対象とした。

**① 通信量・発信先の確認**

UFWは、外部からの着信を制御しており、SSHポートへの接続は、VPN（Tailscale）経由のみを許可している。ただし、中から外への発信は、これまで制限していない。

```bash
sudo ss -tnp
```

`ss`は、サーバーが、今、この瞬間、張っている通信の接続を、一覧で見せるコマンドである。`-t`はTCP、`-n`はホスト名に変換せず数字のまま、`-p`は、どのプロセスが、その接続を持っているかを、あわせて表示する指定である。`nethogs`と同じく、**今の状態しか見せず、過去にさかのぼって確認する機能はない。**

`ss -tnp`で、現在の接続をすべて確認したところ、lighthouse・geth・mev-boost・tailscaled・grafana・prometheus・sshd以外の、説明のつかない発信は、見当たらなかった。

発信の中身を絞る設計は、宛先が不特定多数（P2Pの性質上）のため、簡単ではない。ここは、今後も、注力していく必要がある。

**② プライベートネットワーク・VPN内の確認**

外部からの着信は、ファイアウォールで遮断しているが、自宅LAN内や、Tailscale（VPN）内であれば、その制御の外になる。そのため、あらためて、この範囲も確認した。自宅LAN内、Tailscale内とも、想定外の相手との通信は、見当たらなかった。Tailscale経由の通信は、すべて、自分の端末からのもの（SSH、Grafana）だった。

**③ 前日の、正体不明の通信について**

9/28、通信量の調査中に、nethogsの記録の中に、上記の通信が残っていた。6回の計測のうち、5回、まったく同じ数値で、最後の1回で、接続が切れていた。プロセス名は、表示されなかった。

9/29、あらためて`ss -tnp`と`nethogs`で確認したところ、同じ通信は見当たらなかった。`nethogs`には、プロセス名の分からない行が、他にもいくつか出ていた。これが何によるものかは、`lsof`で確かめた。

```bash
sudo lsof -i -P -n | grep geth
```

`lsof`は、あるプロセスが、今、開いているファイルや、通信の接続を、一覧で見せるコマンドである。`-i`で通信（ネットワークソケット）に絞り、`-P`・`-n`は、ポート番号やIPアドレスを、名前に変換せず、数字のまま表示する指定である。`grep geth`で、gethが開いている接続だけを、抜き出した。結果、ポート番号と、接続の相手先が、`nethogs`側でプロセス名不明だった行と、一致した。いずれも、gethの、通常の接続と判断できた（gethは、この時点で30件以上の接続を持っており、`nethogs`側で、一部の取りこぼしが起きやすい状態だった）。

## 1. バリデータ収益の概論

本題に入る前に、Ethereumバリデータの収益がどう構成されているかを整理しておきます。これを知らないと、今回の出来事の意味が正しく伝わりません。

### 1-1. 二階建ての収益構造

```
① Attestation報酬（基本給）
   毎エポック（約6.4分）ごとに発生。全バリデータが
   ほぼ平等に得られる、安定した報酬。1回あたりの金額は
   小さいが、頻度が非常に高い。第11章までのnode_checkで
   日常的に確認してきた「Successfully published
   attestations」のログが、まさにこれ。

② Block Proposal報酬（ボーナス）
   バリデータがそのスロットの「提案者」に選ばれた時だけ
   発生する報酬。頻度は低いが、1回あたりの金額は大きい。
```

Attestation報酬が絶え間なく安定しているのに対し、Block Proposal報酬は、提案者選出の仕組み（RANDAO）による不規則性のため、ずっと散発的に発生します。

### 1-2. 提案者はどうやって選ばれるか（RANDAO）

Ethereumには「本物の乱数」は存在しません。もし各ノードが本当にランダムな数字を生成してしまうと、ノード同士で合意ができなくなるためです。代わりに、RANDAOという仕組みで「予測しづらい」選出を実現しています。

```
重要な性質：
  ・提案者はバリデータの残高に応じて重み付けされる
  ・つまり32 ETHの鍵を1本持つ人も10本持つ人も、
    「1本あたりの当選確率」は変わらない
  ・鍵を多く持てば、その分「試行回数」が増えるだけ
```

10鍵運用しているからといって、1本あたりの当選確率が上がるわけではありません。あくまで「くじを10本引いている」だけです。

> 💡 **既存の章との繋がり：** RANDAOの値は2エポック前に確定するため、「次のエポックに自分の提案が入っているか」は事前に予測できます。これは新しい話ではなく、第11章・第12章の`node_safe_stop.sh`・アップデート作業で実施していたブロック提案チェック（`/eth/v1/validator/duties/proposer/{epoch}`）が、まさにこの性質を利用したものでした。停止作業の前に「今、提案の権利を握っていないか」を確認していたのは、RANDAOが持つ「予測可能性」のおかげだったことになります。

### 1-3. どのくらいの頻度で当たるのか

参考になる試算として、ネットワーク全体でアクティブバリデータ数が約47万の場合、1バリデータが提案者に選ばれる確率はおよそ2ヶ月に1回程度、という数字があります。

```
単純計算：
  1鍵あたり: 約2ヶ月に1回
  10鍵運用: 平均して1週間に1〜2回程度、
           いずれかの鍵に提案が回ってくる計算
```

つまり10鍵運用では、Proposalの成功自体はそれなりの頻度で起きます。ただし**2鍵が同時期に成功するのは、統計的にさらに稀な重なり**になります。

### 1-4. MEVによる上乗せ

Block Proposal報酬が大きくなる最大の理由は、MEV（Maximal Extractable Value）です。

```
仕組み：
  ブロックビルダーが、手数料を最大化したブロックを作成
    ↓
  リレーが複数のビルダーからブロックを集約
    ↓
  MEV-Boost（第2部で構築済み）が、接続している全リレーから
  最も報酬の高い入札を取得
    ↓
  バリデータは、その最良の入札を選んで署名・提案する
```

2026年時点の一般的な水準として、MEV-Boost収益は基本APRに対して10〜30%程度の上乗せになる、という報告があります。

### 1-5. （参考）SSVオペレーター報酬との違い

第3部・第13章で構築したSSVオペレーター活動の報酬は、ここまでの説明とは全く別の経済圏です。

```
本業（Lido CSM・10鍵）: Attestation + Proposal報酬、ETH建てで完結
SSVオペレーター活動  : ステーカーから、SSVトークン建てで
                       手数料を受け取る仕組み
                       （2026年、ETH建てへの移行が進行中）
```

同じ「バリデータ運用」でも、受け取る通貨単位そのものが異なります。この違いは、本ガイドの経済的な話をする上で、常に意識しておく必要があります。

## 2. 発端 — 2鍵同時のブロック提案成功

2026年8月1日のnode_checkで、直近24時間以内に2つの鍵が同時にブロック提案を成功させていたことに気づきました。

```
該当鍵: validator index 1280904, 1334506

残高の変化：
  0xb4f66315...: 32.0488 ETH（他の鍵は32.0018 ETH前後）
  0x95b018ed...: 32.0494 ETH

beaconcha.in上の確認値：
  Proposal Participation: 2/0
  Proposal Efficiency   : 97.12%
  この日のRewards        : 0.111733 ETH
  APR（表示上の瞬間値）  : 12.75%
```

これまでの運用で、2鍵同時のProposal成功は初めての記録です。先述の通り、1鍵あたり約2ヶ月に1回という頻度を踏まえると、これはかなり稀な巡り合わせでした。

## 3. 「運」と「実力」の切り分け

### 3-1. 運の要素：選ばれるかどうか

```
2鍵が同時に提案者に選ばれたこと自体は、完全にRANDAOによる
偶然の重なりです。10鍵運用しているからといって、
狙って引き当てられるものではありません。
```

### 3-2. 実力の要素：選ばれた後、確実に成功させられるか

一方で、「提案者に選ばれる」ことと「実際に提案を成功させる」ことは別問題です。宝くじに例えるなら、**「当選番号を引き当てること」は運ですが、「当選金を実際に受け取りに行けるかどうか」は準備次第**です。

```
成功のために必要だった土台：
  ・MEV-Boostが正常に稼働し、リレーから入札を取得できる状態
    にあったこと（第2部で構築）
  ・ノードが正しく同期し、提案のタイミングを逃さなかったこと
    （第8〜9章の監視体制）
  ・swap管理・定期メンテナンス（第11章）で、
    OSレベルの不調を予防できていたこと
```

**Proposal Efficiency 97.12%という数値は、これまで積み重ねてきた運用品質の裏付けです。** 提案の権利を得ても、ノードが不安定であれば、これは簡単に取りこぼされます。

## 4. 実際のMEV-Boost構成

今回の報酬の背景にある、実際のリレー設定を確認しました。

```bash
systemctl cat mev-boost.service | grep -i relay
```
```
-relays https://<pubkey>@boost-relay-hoodi.flashbots.net,
        https://<pubkey>@bloxroute.hoodi.blxrbdn.com
```

```
接続リレー: Flashbots + bloXroute（計2つ）
```

単一リレーへの依存は避けられていますが、主要なリレー（Ultra Sound、Aestus等）にはまだ接続していません。より多くのリレーに接続すれば、入札の競争が増え、報酬の最大化が期待できる一方、「質の低いリレーを含めるリスク」や「MEV-Boostの応答遅延によって、かえって提案を逃すリスク」とのトレードオフになります。これは第10章で扱った「単一障害点の解消」と同じ考え方が応用できるテーマです。

## 5. 経済的な位置づけの整理

```
当日（8/1）のAPR: 12.75%
平常時のAPR    : 1.9%前後で推移
```

**当日の数字だけを見て「年利12.75%が実現できている」と誤解してはいけません。** これは統計的な特異日であり、平常時のAPR（1.9%前後）こそが、実質的な基準値です。

これまで本ガイドで扱ってきた「資本効率の主張は、実際の運用コストと比較して評価すべき」という懐疑的な姿勢（第10章等）と同じく、**臨時ボーナスも「狙って得られるものではなく、たまたま基礎的な運用品質の上に乗った結果」として捉える**のが誠実な向き合い方だと考えています。

| 知見 | 内容 |

| バリデータ収益は二階建て | Attestation（基本給・安定）とProposal（ボーナス・散発的）の組み合わせ |

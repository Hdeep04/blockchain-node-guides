## 1. バリデータ収益の概論

本題に入る前に、Ethereumバリデータの収益がどう構成されているかを整理しておきます。これを知らないと、今回の出来事の意味が正しく伝わりません。

### 1-1. 二階建ての収益構造

```
① Attestation報酬（基本給）
   毎エポック（約6.4分）ごとに発生。全バリデータが
   ほぼ平等に得られる、安定した報酬。1回あたりの金額は
   小さいが、頻度が非常に高い。第11章までのnode_checkで
   日常的に確認してきた「Successfully published
   attestations」のログが、まさにこれ。

② Block Proposal報酬（ボーナス）
   バリデータがそのスロットの「提案者」に選ばれた時だけ
   発生する報酬。頻度は低いが、1回あたりの金額は大きい。
```

Attestation報酬が絶え間なく安定しているのに対し、Block Proposal報酬は、提案者選出の仕組み（RANDAO）による不規則性のため、ずっと散発的に発生します。

### 1-2. 提案者はどうやって選ばれるか（RANDAO）

Ethereumには「本物の乱数」は存在しません。もし各ノードが本当にランダムな数字を生成してしまうと、ノード同士で合意ができなくなるためです。代わりに、RANDAOという仕組みで「予測しづらい」選出を実現しています。

```
重要な性質：
  ・提案者はバリデータの残高に応じて重み付けされる
  ・つまり32 ETHの鍵を1本持つ人も10本持つ人も、
    「1本あたりの当選確率」は変わらない
  ・鍵を多く持てば、その分「試行回数」が増えるだけ
```

10鍵運用しているからといって、1本あたりの当選確率が上がるわけではありません。あくまで「くじを10本引いている」だけです。

> 💡 **既存の章との繋がり：** RANDAOの値は2エポック前に確定するため、「次のエポックに自分の提案が入っているか」は事前に予測できます。これは新しい話ではなく、第11章・第12章の`node_safe_stop.sh`・アップデート作業で実施していたブロック提案チェック（`/eth/v1/validator/duties/proposer/{epoch}`）が、まさにこの性質を利用したものでした。停止作業の前に「今、提案の権利を握っていないか」を確認していたのは、RANDAOが持つ「予測可能性」のおかげだったことになります。

### 1-3. どのくらいの頻度で当たるのか

参考になる試算として、ネットワーク全体でアクティブバリデータ数が約47万の場合、1バリデータが提案者に選ばれる確率はおよそ2ヶ月に1回程度、という数字があります。

```
単純計算：
  1鍵あたり: 約2ヶ月に1回
  10鍵運用: 平均して1週間に1〜2回程度、
           いずれかの鍵に提案が回ってくる計算
```

つまり10鍵運用では、Proposalの成功自体はそれなりの頻度で起きます。ただし**2鍵が同時期に成功するのは、統計的にさらに稀な重なり**になります。

### 1-4. MEVによる上乗せ

Block Proposal報酬が大きくなる最大の理由は、MEV（Maximal Extractable Value）です。

```
仕組み：
  ブロックビルダーが、手数料を最大化したブロックを作成
    ↓
  リレーが複数のビルダーからブロックを集約
    ↓
  MEV-Boost（第2部で構築済み）が、接続している全リレーから
  最も報酬の高い入札を取得
    ↓
  バリデータは、その最良の入札を選んで署名・提案する
```

2026年時点の一般的な水準として、MEV-Boost収益は基本APRに対して10〜30%程度の上乗せになる、という報告があります。

### 1-5. （参考）SSVオペレーター報酬との違い

第3部・第13章で構築したSSVオペレーター活動の報酬は、ここまでの説明とは全く別の経済圏です。

```
本業（Lido CSM・10鍵）: Attestation + Proposal報酬、ETH建てで完結
SSVオペレーター活動  : ステーカーから、SSVトークン建てで
                       手数料を受け取る仕組み
                       （2026年、ETH建てへの移行が進行中）
```

同じ「バリデータ運用」でも、受け取る通貨単位そのものが異なります。この違いは、本ガイドの経済的な話をする上で、常に意識しておく必要があります。

## 3. 「運」と「実力」の切り分け

### 3-1. 運の要素：選ばれるかどうか

```
2鍵が同時に提案者に選ばれたこと自体は、完全にRANDAOによる
偶然の重なりです。10鍵運用しているからといって、
狙って引き当てられるものではありません。
```

### 3-2. 実力の要素：選ばれた後、確実に成功させられるか

一方で、「提案者に選ばれる」ことと「実際に提案を成功させる」ことは別問題です。宝くじに例えるなら、**「当選番号を引き当てること」は運ですが、「当選金を実際に受け取りに行けるかどうか」は準備次第**です。

```
成功のために必要だった土台：
  ・MEV-Boostが正常に稼働し、リレーから入札を取得できる状態
    にあったこと（第2部で構築）
  ・ノードが正しく同期し、提案のタイミングを逃さなかったこと
    （第8〜9章の監視体制）
  ・swap管理・定期メンテナンス（第11章）で、
    OSレベルの不調を予防できていたこと
```

**Proposal Efficiency 97.12%という数値は、これまで積み重ねてきた運用品質の裏付けです。** 提案の権利を得ても、ノードが不安定であれば、これは簡単に取りこぼされます。

## 5. 経済的な位置づけの整理

```
当日（8/1）のAPR: 12.75%
平常時のAPR    : 1.9%前後で推移
```

**当日の数字だけを見て「年利12.75%が実現できている」と誤解してはいけません。** これは統計的な特異日であり、平常時のAPR（1.9%前後）こそが、実質的な基準値です。

これまで本ガイドで扱ってきた「資本効率の主張は、実際の運用コストと比較して評価すべき」という懐疑的な姿勢（第10章等）と同じく、**臨時ボーナスも「狙って得られるものではなく、たまたま基礎的な運用品質の上に乗った結果」として捉える**のが誠実な向き合い方だと考えています。

## 6. 報酬の出口 — ETH・stETH・wstETHをどう受け取るか

ここまでは「稼ぐ」側の話でした。最後に、稼いだ報酬・返却された担保金を実際にどう受け取るか、という「出口」の話を整理します。実際にBond Claimを行った際、ETH・stETH・wstETHという3つの選択肢に直面したことがきっかけです（第7章8-5節で整理した、Bondと32 ETH元本の区別も参照してください）。

### 6-1. なぜ「受け取り方」を知っておく必要があるか

CSMのボンド（担保金）は、ETH・stETH・wstETHのいずれでも拠出・返却が可能です。これは公式ドキュメントに明記されている仕様で、単なる表示形式の違いではなく、**受け取った後の資産の性質そのものが変わります。**

### 6-2. 3つの資産の違い

```
① ETH
   Ethereumのネイティブ通貨そのもの。何にも紐づかない、
   完全に自由な状態。

② stETH（Staked ETH）
   LidoにETHを預けると1:1で発行される、"リベース"トークン。
   毎日、ステーキング報酬に応じて残高そのものが自動的に
   増えていく（例：100 stETHが翌日100.01 stETHになる）。

③ wstETH（Wrapped stETH）
   stETHを"ラップ（包装）"した、非リベース版。
   残高（数量）は変わらず、代わりに「1 wstETHあたりの
   価値」がstETHに対して上昇していく。UniswapやMakerDAOなど、
   残高が毎日変動するリベース方式のトークンに対応できない
   DeFiプロトコルのために用意されている。
```

**たとえるなら、自分でバリデータを運用すること（本業）は「自分でラーメン屋を経営する」ことで、stETHを保有することは「ラーメン屋チェーンの株を買って配当を受け取るだけ」の立場です。** 同じ「業界に関わっている」点は共通していますが、経営者（運用者）と株主（stETH保有者）は全く違う役割です。今回のBond Claimでは、担保金という「経営者としての持ち分」の一部を、いったんstETHという「株主的な持ち分」に切り替えて受け取ったことになります。

### 6-3. 実際の選び方（ユースケース別）

```
すぐ使いたい・現金化したい      → ETH
そのまま何もせず増やしたい      → stETH
DeFiで運用したい（貸付・LP等）  → wstETH
```

実際にCSM UIのClaim画面で確認したところ、選択によって**待ち時間も大きく異なります。**

```
ETH   : 約2日（withdrawal NFT経由、Ethereum側の
        出金プロセスを待つ必要があるため）
stETH : 約1分
wstETH: 約1分
```

### 6-4. もう一つの軸：3つのClaimingオプション

「どのトークンで受け取るか」に加えて、CSM UIの`Bond & Rewards`画面には、**「何を、どこへ請求するか」**というもう一つの選択軸があります。

```
① Excess Bond → Rewards Address
   Excess Bond（担保金の余剰分）のみを請求する。
   報酬（Rewards）は請求せず、そのまま残しておく。

② All → Rewards Address
   Excess BondとRewards（報酬）の両方を、
   まとめて自分のウォレットへ請求する。

③ Rewards → Excess Bond
   Rewards（報酬）を出金せず、あえてBondへ繰り入れる。
   株式投資でいう「配当再投資」に近い動き。
```

> ⚠️ **用語の整理：「デポジット」との混同に注意。** ここでいうBondは、32 ETH本体（バリデータのデポジット）とは別物です。32 ETH本体はプロトコル・Lidoの管理下にあり、運用者が直接動かすことはできません（第7章8-5節参照）。Bondはあくまで運用者自身が拠出した「担保金」であり、Claim画面で扱えるのはこちらだけです。

③を選んで報酬をBondへ繰り入れると、Bond残高が厚くなります。CSMの仕組み上、Excess bond amountが十分にあれば、新しい鍵を追加する際にウォレットから改めてETHを支払う必要がなくなり、預けていた余剰分から自動的に充当されます。**これは「配当再投資」というより「鍵を増やすための積み立て」という意味合いが強い操作**です。

**2つの軸を掛け合わせると、実務上は次のような組み合わせになります。**

```
例：「報酬は再投資しつつ、余ったBondだけ今すぐ現金化したい」
  → ①Excess Bond → Rewards Address を選び、
    受け取りトークンはETH（またはstETH/wstETH）を選択

例：「増やした鍵の分の報酬もまとめて全部受け取りたい」
  → ②All → Rewards Address を選び、
    受け取りトークンを選択
```

どちらの軸も独立して選べるため、「今すぐ使いたい分だけ現金化しつつ、残りは複利的に増やし続ける」といった、柔軟な資金管理が可能になっています。

> ⚠️ **「All」を選んでも、32 ETH本体は戻ってきません。** Claim画面で動かせるのは、あくまでExcess Bond（担保金の余剰分）とRewards（報酬）の2つだけです。32 ETH本体は、バリデータが実際にExit（引退）するまで、プロトコル上のバリデータとして拘束され続けます（第7章参照）。

### 6-5. バリデータ運用者は、実は二重にLidoと関わっている

ここまでの内容を踏まえると、CSMオペレーターとしての立場を整理すると、実は**2つの異なる関わり方**を同時に持っていることが分かります。

```
① CSMオペレーターとして（本業）
   自分でハードウェアを用意し、Geth・Lighthouseを動かし、
   実際にAttestation・Proposalの署名を行う。
   32 ETHの元本そのものを、直接"経営"している立場。

② Excess Bond・Rewardsの保有者として
   Claimせずに放置している間、その残高（stETH建て）は
   Lidoの一般的なステーキングプールに間接的に委任され、
   自動的にリベースし続けている。
```

**たとえるなら、「ラーメン屋を自分で経営しながら（①）、その利益の一部を、同じグループの別のラーメン屋チェーンの株として保有し続けている（②）」ような状態です。** どちらも「Lidoのステーキングに関わっている」という点は共通していますが、役割としては全くの別物です。

### 6-6. Lidoエコシステム全体を俯瞰する

ここまで登場した要素を、一枚の図として整理します。

```
                    ┌─────────────────────┐
                    │   Lidoプロトコル全体   │
                    │  （ステーカーの32 ETHを │
                    │   多数のバリデータで運用）│
                    └──────────┬──────────┘
                               │
              ┌────────────────┼────────────────┐
              │                                  │
    ┌─────────▼─────────┐          ┌─────────▼─────────┐
    │  CSMオペレーター     │          │  一般のLidoステーカー  │
    │ （本業として運用）    │          │ （stETHを保有するだけの│
    │                    │          │   一般ユーザー）       │
    │ ・自分でバリデータを  │          │ ・自分では何もしない   │
    │   直接運用          │          │ ・ETHを預けてstETHを   │
    │ ・Attestation/       │          │   受け取るだけ         │
    │   Proposal報酬       │          │ ・プールされた資金の    │
    │   （ETH建て）        │          │   取り分を得るだけ      │
    │ ・Bond（担保金）を    │          └──────────────────┘
    │   拠出する義務あり    │
    └─────────┬─────────┘
              │
   Excess Bond・Rewardsを
   Claimせず放置すると…
              │
              ▼
   ①の中に、②的な性質を持つ
   資産（stETH建て）が生まれる
   （間接的な委任状態）
```

**本業（①）は「自分で手を動かして運用する」能動的な立場、Excess Bond・Rewardsの保有（②）は「預けて増えるのを待つ」受動的な立場です。** 本ガイドが一貫して扱ってきたのは①の話ですが、Claim操作を境に、資産の一部が②の性質に切り替わる、という視点を持っておくと、Lidoエコシステム全体の見通しが良くなります。

### 6-7. 実例：Bond Claimを振り返る

実際にBond Claimを行った際、Excess Bond 1.9929 stETHを、より待ち時間の短いstETHとして受け取りました。

```
Before: CSMオペレーターとしての担保金（拘束された状態）
  ↓ Claim実行
After : 一般のLidoステーカーとしてのstETH保有
       （Lidoの通常のステーキングプールに、自動的に
         委任され続けている状態）
```

つまり「Claimして終わり」ではなく、Claim後もその資産は形を変えて、Lidoエコシステムの中で運用され続けています。何もしなければ、そのままLidoの通常のステーキング報酬を継続的に受け取れる状態です。ETHとして完全に現金化したい場合は、改めてLidoの出金機能（Withdrawals Request → Claim）を使い、1:1のレートでETHに交換する必要があります。

## 1. 発端

第12章でLighthouseをv8.1.3からv8.2.1へアップデートした際、ふと「このアップデートで、SSVノードのCLをローカルLighthouseに接続できるようになっていないだろうか」という考えが浮かびました。

第3部・第10章の結論をおさらいすると、以下の通りでした。

```
CL（Beacon Node）: 外部RPC（Alchemy + Chainstack）継続
EL（Geth）        : ローカル

理由：SSVノード（v2.4.2）をローカルLighthouseに接続すると
      "nil pointer dereference" でクラッシュするため
      （ネットワーク名 "hoodi" を受け付けない、という当時の結論）

今後の見通し：SSVバージョンアップ（v2.5.x）でhoodi名の許容を期待
```

半年近く経ち、状況が変わっている可能性を検証してみることにしました。

---

## 2. まず疑ったこと：SSVは本当に変わっていないのか

現在稼働中のSSVノードは`ssvlabs/ssv-node:latest`タグで運用しています。バージョンが勝手に上がっていないか確認しました。

```bash
docker exec ssv-node /go/bin/ssvnode version
```
```
v2.4.2-9117de68763017de6711515fb6e9dcad44bcc0e1
```

第3部で確認したバージョンと同じv2.4.2でした。念のため、GitHubの公式リリース一覧でも確認しましたが、v2.4.2が現時点の最新版であり、見込んでいた「v2.5.x」というバージョン自体がまだ存在しないことも分かりました。

**つまりSSVノード自体は、半年前から一切変わっていません。**

---

## 3. それでも試してみる

バージョンが変わっていないなら結果も同じだろうと思いつつ、まずは実際に試してみることにしました。失敗しても`docker-compose.yaml`を元に戻すだけで復旧できるため、リスクは小さいと判断しました。

```bash
# 現在の設定をバックアップ
cp /opt/ssv/docker-compose.yaml /opt/ssv/docker-compose.yaml.backup_before_local_test

# BEACON_NODE_ADDR をローカルLighthouseに書き換え
sudo sed -i 's|BEACON_NODE_ADDR=.*|BEACON_NODE_ADDR=http://127.0.0.1:5052|' /opt/ssv/docker-compose.yaml

# 再起動
cd /opt/ssv
docker compose down
docker compose up -d
docker compose logs -f --tail 30
```

**結果：クラッシュしませんでした。**

```
INFO    Operator        operator node has been started  {"operator_id": <SSV_ID>}
INFO    DutyScheduler   received head event. Processing...      {"slot": 3534949, ...}
INFO    P2PNetwork      Verified handshake nodeinfo     {...}
INFO    Controller      recording validator status      {"status": "attesting", ...}
```

`nil pointer dereference`は一度も発生せず、P2Pピアとの接続も確立し、担当バリデータのステータスも`attesting`（署名中）と正常でした。

## 4. 本当の原因を突き止める

「なぜ動くようになったのか」を確認せずに終わらせたくなかったため、当時の記録を掘り起こしました。

第3部の公式な結論は「ネットワーク名の不一致（`"hoodi"` vs `"holesky"`）」でしたが、実は日本のLido CSMコミュニティのTelegramに、当時もう少し詳しい調査結果を投稿していたことを思い出しました。

> 以前相談していた「Lido CSM (Hoodi) 同居環境での SSV ノードのパニック」について、原因が分かりましたので共有します。
>
> ローカルの Lighthouse (Hoodi) と Alchemy の Beacon API で、取得できるスペック情報（`/eth/v1/config/spec`）を比較してみたのですが、中身のデータは同じでも、JSON の梱包のされ方（階層構造）が違っていました。
>
> 具体的には、Alchemy は `{"data": { ... }}` という箱の中にスペック情報が入っていますが、ローカルの Lighthouse はその「箱」がなく、いきなりデータが来る形式でした。SSV ノードはこの「箱の有無」に非常に厳格で、期待した梱包で届かないとパニックを起こしてクラッシュしてしまうようです。

つまり実際の原因は、**ネットワーク名の不一致ではなく、Lighthouseの`/eth/v1/config/spec`レスポンスがBeacon API仕様の梱包形式（`{"data": {...}}`）に準拠していなかったこと**だった可能性があります。

### 4-1. 現在のレスポンスを検証する

```bash
curl -s http://127.0.0.1:5052/eth/v1/config/spec | head -c 300
```
```
{"data":{"CONFIG_NAME":"hoodi","PRESET_BASE":"mainnet", ...
```

**現在は正しく`{"data": {...}}`の形式で返っています。** 以前投稿した「箱がない」状態は、少なくとも今は解消されていました。

### 4-2. どのバージョンで直ったのかは特定できず

Lighthouseの変更履歴を調べたところ、`/eth/v1/beacon/rewards/*`のレスポンスを「Beacon API仕様の梱包形式に合わせた」という、同種の修正が行われた記録が見つかりました。Lighthouseチームがこうした「レスポンス形式をAPI仕様に準拠させる」修正を継続的に行っている傾向があることは確認できましたが、**`/eth/v1/config/spec`自体が正確にどのバージョンで修正されたかは、今回の調査では特定できませんでした。**

「v8.2.1のこの修正が原因」と断定はできず、v8.1.3以前のどこかのバージョンで直っていた可能性も含め、正確な原因バージョンは不明という結論にとどめます。

### 4-3. イメージの同一性も確認済み

「SSVノードの`latest`タグがいつの間にか再ビルドされて変わっていたのでは」という仮説も検証しました。

```bash
docker inspect ssv-node --format '{{.Image}}'
docker image inspect ssvlabs/ssv-node:latest --format '{{.RepoDigests}}'
```
```
sha256:ecf766a29acd7e4d4d21054fc7579bb5e23597ba95e8030969f1185ada5d5690
[ssvlabs/ssv-node@sha256:ecf766a29acd7e4d4d21054fc7579bb5e23597ba95e8030969f1185ada5d5690]
```

コンテナが実際に使用しているイメージと、現在の`latest`タグが指すイメージのダイジェストは完全に一致していました。バージョン番号（v2.4.2）も変わっていないことから、SSVノード側は不変であり、**変化があったのはLighthouse側**と考えるのが最も筋が通っています。

> 💡 **学び：Dockerの`latest`タグは自動更新されない。** `restart: always`は「落ちたら再起動する」設定であり、「毎回最新イメージを取得し直す」設定ではありません。イメージが変わるのは`docker compose pull`を明示的に実行した時だけです。

## 5. node_check.sh・Grafanaへの影響確認

構成変更後、監視まわりに修正が必要か確認しました。結論として、**どちらも修正不要でした。**

### node_check.sh

第10章で実装したCL Source・CL Status表示ロジックは、エンドポイント数に応じて動的に分母・分子を計算する設計だったため、1本構成に戻っても自動的に正しく表示されました。

```
CL Source : Primary: Local (http://127.0.0.1:5052)
CL Status : 1/1 synced
```

`Local`接続の場合は「単一障害点」警告（`Single point of dependency`）を出さない設計になっており、これも意図通りに動作しています（外部RPC1本の場合にのみ警告する設計だったため）。

### Grafana

```
Attestation Success Rate : 100%
SSV CL Status (Beacon)   : Synced
SSV Validator Attesting  : Attesting
SSV EL Status            : Ready
SSV Duty Failures        : データなし（失敗ゼロ）
```

切り替え直後にSSV Round Changesのグラフで軽微なスパイクが見られましたが、これは再接続・再同期に伴う一時的な動きであり、Duty Failuresには影響していませんでした。

---

## 6. 現在の構成

```
変更前（第3部・第10章確立時点）：
  EL（Geth）        : ローカル
  CL（Beacon Node） : 外部RPC（Alchemy Primary + Chainstack Secondary）

変更後（本章時点）：
  EL（Geth）        : ローカル
  CL（Beacon Node） : ローカルLighthouse
```

外部RPCへの依存がなくなったことで、Alchemy・Chainstackの無料枠消費の心配が軽減されました。また、第10章で確立した複数エンドポイント構成の仕組みは今回使っていませんが、コード自体は将来また外部RPCを併用したくなった場合にそのまま使える状態で残っています。

## 7. まとめ

| 知見 | 内容 |
|---|---|
| 「解決策の見込み」は外れることがある | 第3部では「SSVのバージョンアップ（v2.5.x）」を解決の条件として見込んでいたが、実際にはそのバージョンは存在せず、Lighthouse側の変化が真因だった |
| 過去の結論を鵜呑みにせず再検証する価値がある | 半年前に「無理」と判断した構成が、今回改めて試すとあっさり動いた。定期的な再検証には意味がある |
| 公式ドキュメントと自分の過去の投稿で説明が食い違うことがある | 第3部本文の「ネットワーク名不一致」説と、Telegramに投稿していた「JSON梱包形式」説は別の説明だった。両方の記録を突き合わせたことで、より正確な原因に近づけた |
| 断定できないことは断定しない | 正確にどのLighthouseバージョンで修正されたかは特定できなかった。分からないことは分からないと記録する方が、後々の自分や読者のためになる |
| `latest`タグは自動更新されない | Dockerイメージが変わるのは明示的に`pull`した時だけ。「知らないうちに変わっていた」という直感は誤りだった |
| 堅牢な設計は構成変更に強い | node_check.sh・Grafanaともに、事前に「エンドポイント数が変わっても対応できる」設計にしておいたことで、今回の変更に対して一切の修正が不要だった |

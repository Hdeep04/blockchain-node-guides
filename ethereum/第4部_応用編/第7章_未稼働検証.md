## 1. 検証の目的

第3章・第5章では、クライアントの移行や構成変更を扱いました。本章では
視点を変え、「バリデータを意図的に停止し、放置するとどうなるか」を
実際に確かめます。単純なペナルティ額の確認だけでなく、運用者として
以下の点を明らかにすることが目的です。

```
① ペナルティの大きさ・蓄積ペースはどの程度か
② 放置すると監視・アラート（CSM Sentinel）は気づいてくれるのか
③ 放置し続けると強制退場（Exit/Ejection）になるのか
④ Lido CSM独自の「Strikesシステム」は、実際何回・いつ付与されるか
⑤ Strikesが閾値に達した場合、実際にForce Ejectionされるか
⑥ Force Ejectionが発生した場合、CSM Sentinelは通知してくれるか
```

①〜⑥のすべてについて、最終的に本章内で確定した結論を得ています
（詳細はセクション5・セクション8参照）。

## 5. 確定している結論

### ② CSM Sentinel（Telegram通知）は気づいてくれるか

**結論：気づかない（今回の規模・期間では無反応）。**

未稼働検証の開始から本章執筆時点まで、Sentinelからの通知は一切来ていない。
BeaconScoreが90%台から10%台後半まで落ちる規模の劣化が起きても、Sentinelは
沈黙していた。

> **実用的な学び：** CSM Sentinelの監視対象は、スラッシングやExitのような
> 「イベント系」であり、Inactivity Leakのような地味な「状態系の劣化」は
> 検知してくれない可能性が高い。「Sentinelが鳴らないから大丈夫」と判断
> するのは早計。別の監視レイヤーが必要（詳細はセクション7）。

### ③ 放置し続けると強制退場（Exit/Ejection）になるか

**結論：レイヤーによって答えが異なる。Ethereumプロトコル本体は「ならない」、
Lido CSM独自レイヤーは「なる」（実測済み。詳細はセクション8）。**

```
Ethereumプロトコル本体：
  - Inactivity Leakは報酬が削られるだけのペナルティで、強制退場の
    仕組みではない
  - 唯一の強制退場ルートはバランスが16 ETH閾値を割り込んだ場合のみ
  - 今回のペナルティペース（数日で0.001〜0.005 ETH程度）では、
    16 ETH減るまでに天文学的な時間がかかる

Lido CSM独自レイヤー（Strikesシステム）：
  - Ethereumプロトコル本体とは無関係に、独自の強制退場が発生する
  - 今回、開始から約5週間でStrikeが3/3に到達し、実際にEjectionが
    発生した（セクション8参照）
  - ペナルティ額は「32 ETH - 実際の引き出し残高」の計算式で、
    実測値は1バリデータあたり0.258 ETH
```

## 6. サーバーが物理的に消失した場合はどうなるか

検証中に浮かんだ追加の問い：「VMを止める」のではなく「サーバー自体が
物理的になくなった」場合、プロトコルから見て挙動は変わるのか。

**結論：プロトコルレベルでは完全に同一視される。**

Ethereumのコンセンサス層が観測できる状態は`Pending → Active → Exited → Withdrawn`
の4つのみ。「サーバーが壊れた」「ソフトウェアを止めた」という"理由"は
プロトコルには伝わらず、「Attestationが来ない」という事実だけが観測される。

```
サーバー消失後の挙動（プロトコル単体）：
① Activeのまま残り続ける（永久に）
② Inactivity Leakで報酬が削られ続ける
③ CSM Sentinelはこの状態に気づかない（上記②の通り）
④ 16 ETH閾値に達するまで強制Exitされない（数年〜数十年オーダー）
⑤ ただし、Lido CSM独自のStrikesシステムが別途働く可能性がある（セクション8）
```

> **実用的な学び：** もしサーバーが物理的に失われ、誰も気づかなければ、
> Ethereumプロトコル単体では「生きているように見える」状態が続く。
> 実際にいつ・どう退場処理されるかは、CSM独自のStrikesシステムに
> 依存する。死活監視（セクション7）の必要性を裏付ける根拠になる。

## 7. 死活監視・アラート体制の課題

今回の検証で「CSM Sentinelだけでは不十分」という実用上の発見があった。
イベント系（スラッシング・Exit）は拾えるが、地味な性能劣化（Inactivity
Leak等）には無反応なため、別の監視レイヤーが必要になる。

### 候補①：Grafana Alerting（既存資産の延長・優先度高）

```
- 第2部で構築済みのGrafanaダッシュボードの延長で導入できる
- BeaconScore（30d）が一定閾値（例：95%）を下回ったらアラート
- Telegram/Discord/メールへのWebhook通知も無料で設定可能
```

### 候補②：Uptime Kuma（外部監視・無料・自己ホスト）

```
- オープンソースの死活監視ツール
- HTTPエンドポイントやAPIレスポンスを定期チェックして外部から死活監視
```

### 候補③：自作Cron + beaconcha.in API + Telegram Bot

```
- node_check.sh の延長線上で作りやすい
- beaconcha.in APIでBeaconScore・バランスの変化を定期取得
- 閾値を下回ったらTelegram Botで通知
```

> 今後の宿題として記録。着手は別セッションで予定。

## 8. 【発見】Lido CSM独自の「Strikesシステム」

### 8-1. 発見の経緯

別の検証（Google Cloud無料枠で構築したバリデータ）で、以下のような
CSM Sentinel通知ログが残っていた。

```
🚨 Strikes penalty processed
  Penalty amount: 0.258 ether
  Penalty will be charged when the validator withdraws

🚨 Exit fee recorded
  Fee paid now: 2 wei / Fee to be charged on exit: 2 wei

👀 Information about validator withdrawal has been submitted
  Exit balance: 31.96988154 ether

📈 Rewards distributed!
  ⚠️ Strikes detected for your validators
```

ペナルティ確定（最初の通知）から退場提出（3番目の通知）まで、わずか
9分で完了していた。これは本章で観察しているInactivity Leak（じわじわ
削れるだけで何も起きない）とは全く異なる、即時的な強制退場の実例。

### 8-2. 公式ドキュメントによる裏付け

Lido公式ドキュメント（Penalties・Join CSM）によると、CSM v2で導入された
Strikesシステムは、Ethereumプロトコル本体とは別の、独自の強制退場
メカニズムです。

```
- ストライクとは、評価フレーム単位でバリデータのパフォーマンスが
  しきい値を下回ったことを示す記録
- ストライク数が閾値（公式ドキュメントの例：6か月で3回）に達すると、
  permissionless（誰でも実行可能）な方法でそのバリデータの退場を
  トリガーできる
- 退場時、badPerformancePenalty（DAOが設定する固定額）がNode
  Operatorのボンドから没収される
- ストライクは一定期間（ライフタイム）を超えると古いものから失効する
```

### 8-3. EthereumプロトコルとCSM独自レイヤーの違い

| レイヤー | 強制退場の有無 | トリガー条件 |
|---|---|---|
| Ethereumプロトコル本体 | なし | バランスが16 ETH閾値を割り込んだ場合のみ（現実的には到達しない） |
| **Lido CSM（独自レイヤー）** | **あり** | **Strikesが一定数累積した場合** |

> これは本章セクション5・③の結論を補足する重要な点。「強制退場には
> ならない」という結論は、Ethereumプロトコル本体のみを見た場合の話で、
> **CSM独自のStrikesシステムを踏まえると話が変わる。**

### 8-4. Force Ejection 実測記録

観察開始から約5週間後、実際にStrikesが蓄積し、Force Ejectionが発生しました。
発見時点（セクション8-3執筆時）は「With strikes: 0」でしたが、その後の
経過を時系列で記録します。

**前提：2種類の異なる「数字」を区別してください**

本節のタイムラインには、似ているが意味の異なる2種類の数字が登場します。
混同すると「3回警告が来たら退場」のように誤解しやすいため、先に整理します。

```
① CSM UI画面の「Strike X/3」表示（鍵ごとの累積カウント）
   → その"1つの鍵"に何回Strikeが蓄積したかを示す
   → 0 → 1 → 2 → 3 と積み上がり、3に達した瞬間に退場処理が
     トリガーされる。退場を直接決めるのはこの数字。

② Telegramアラートの「Validators with strikes: N」（該当する鍵の数）
   → 今Strikeが1つ以上付いている"鍵の総数"を示す集計値
   → 個々の鍵が①でいう何回目のStrikeなのかは、この数字だけでは
     分からない。今回はたまたま観察対象が2鍵だったため「2」で
     安定していたが、これは「2回目のStrike」という意味ではない。
```

**タイムライン：**（①＝鍵ごとの累積カウント、②＝該当鍵数、と付記）

```
6月29日 19:14  Telegramアラート：Strikes detected
               ②Validators with strikes: 3
               同時刻のCSM UI確認：testnetcsm・testnetcsm2ともに
               ①Strike 1/3
               （②の「3」は、当時Strikeが付いていた鍵が3つ
                 （後にStrikeとは無関係の理由で退出済みとなった
                 鍵を含む）あったためと考えられる。①は両鍵とも
                 1回目のStrikeだった）

7月13日 19:13  Telegramアラート：Strikes detected
               ②Validators with strikes: 2

7月19日        CSM UI確認：testnetcsm・testnetcsm2ともに
               ①Strike 2/3（6フレーム中2個のStrikeを示す
                 赤丸表示）まで進行。まだEject未発生

7月27日 19:13  Telegramアラート：Strikes detected
               Node Operator ID: <OPERATOR_ID>
               ②Validators with strikes: 2

7月27日 19:28  Telegramアラート（連続4件）：
               ・Triggerable Withdrawal fee recorded（testnetcsm2）
                 Fee to be charged on exit: 1 wei
               ・Strikes penalty processed（testnetcsm2）
                 Penalty amount: 0.258 ether
               ・Triggerable Withdrawal fee recorded（testnetcsm）
               ・Strikes penalty processed（testnetcsm）
                 Penalty amount: 0.258 ether

7月27日 19:59  CSM UI確認：両バリデータとも
               Status: Exited (withdrawal pending)
               ①Strike 3/3（上限到達 → Force Ejection確定）
```

**まとめ：** 退場を引き起こしたのは、①（鍵ごとの累積カウント）が
6/29→7/19→7/27で「1→2→3」と積み上がったことです。②（該当鍵数）は
終始「2〜3」で推移していましたが、これは退場の直接の引き金ではなく、
「今どの鍵に注意が必要か」を知らせるための集計値でした。

### 8-5. ペナルティの実額と、引き出しまでの流れ

**確定したペナルティ額：1バリデータあたり 0.258 ETH**

Lido公式ドキュメント（Penalties）によると、このペナルティは以下の
計算式で決まります。

```
Penalty amount = 32 - validator's withdrawal balance
```

つまり「32 ETHの元本から、実際に引き出せた残高を差し引いた額」が、
そのままペナルティとしてボンド（担保金）から徴収される仕組みです。
このペナルティは、バリデータの引き出しがオンチェーンで報告される
トランザクションの中で即座に確定します（"applied immediately within
the reporting transaction"）。

**引き出し完了までの実測タイムライン：**

```
7/27 19:59  Exited（退出確定）
7/28 23:18  beaconcha.inが提示した当初のWithdrawable予定時刻
7/29（時点）まだ Status: Withdrawing のまま。
            beaconcha.inの推定表示は「あと1日3時間」に更新されており、
            当初予定より遅延している
```

beaconcha.in上には以下の注記があり、今回はまさにこの通りの状態でした。

```
Note: Due to uncertainty in execution-triggered withdrawals,
your withdrawal may take significantly longer to process.
```

> **実用的な学び：** 「Withdrawable（引き出し可能）になった時刻」と
> 「実際に引き出しが実行される時刻」は別物です。プロトコル側の自動処理
> （regular sweep）を待つ必要があり、当初の推定時刻を過ぎても実行され
> ないことがあります。

**資金が手元に届くまでの、もう一段階：Bond Claimは手動操作が必要**

ここが見落としやすいポイントですが、32 ETHの元本自体はLidoプロトコルへ
返却されるものであり、運用者自身のウォレットとは無関係です（実際、
Etherscanでウォレット履歴を確認しても、退出処理に対応する新規取引は
一切記録されていませんでした）。

運用者が実質的に負担・回収するのは、**ボンド（担保金）** の部分です。

```
本業資産の流れ：
  32 ETH元本        → Lidoプロトコルへ返却（運用者のウォレットとは無関係）
  Strikeペナルティ   → 運用者のボンド（担保金）から徴収
  残った余剰ボンド    → CSM UI「Bond & Rewards」画面から
                       運用者本人が**能動的にClaim（請求）操作**する
                       必要がある（自動送金ではない）
```

Claim画面では、ETH（Withdrawal NFTの形）・stETH・wstETHの3種類から
受け取りトークンを選べ、それぞれ待ち時間の目安も表示されます
（例：ETH ≈1日、stETH/wstETH ≈1分）。「バリデータが退出すれば自動的に
資金が戻ってくる」ものではなく、**最後は自分でClaimボタンを押す必要が
ある**という点は、初めて経験すると見落としやすい部分です。

## 9. 学んだこと・教訓

- **死活監視には「イベント系」と「状態系」の2種類があり、片方しか
  カバーしていないと盲点が生まれる：** CSM Sentinelはスラッシング・
  Exitのようなイベントには気づくが、Inactivity Leakのような地味な
  状態劣化には無反応だった。一方、Strikes関連のイベント（発生・
  ペナルティ確定）には確実に反応し、通知が届いた。
- **「強制退場の有無」はレイヤーによって答えが異なる：** Ethereum
  プロトコル本体の話とLido CSM独自レイヤーの話を混同すると、誤った
  結論に至る。今回、Ethereumプロトコル本体のみでは強制退場されない
  規模の放置でも、CSM独自のStrikesシステムにより実際に強制退場に
  至った。
- **検証対象の全バリデータについて、開始前の基準値を必ず記録する：**
  比較対象（今回はtestnetcsm2）のBefore値を記録し忘れたことで、
  構成差の原因分析が「推測の域」に留まってしまった。
- **公式UIには、見落としがちな便利な確認手段が用意されている場合
  がある：** CSM Dashboardの「With strikes」カウンターは、地道な
  個別確認より効率的な定点観測ポイントだった。
- **「Validators with strikes」の数字はStrike累積数ではなく、
  Strikeが付いている鍵の"数"：** Telegram通知とCSM UI表示の数値が
  一致しないように見えた謎は、両者が異なる指標（累積カウント vs
  該当鍵の数）を表示していたために生じた見かけ上の不一致だった。
- **「引き出し可能」と「実際に引き出し完了」は別物：** beaconcha.in
  が提示する推定時刻を過ぎても、プロトコル側の自動処理（sweep）を
  待つ必要があり、当初の見込みより時間がかかることがある。
- **32 ETH元本の返却先と、運用者本人が受け取る金額は別の話：**
  元本はLidoプロトコルへ返却され、運用者のウォレットには一切動きが
  出ない。運用者が実際に回収するのはボンド（担保金）部分のみで、
  かつ受け取りには「Bond & Rewards」画面での能動的なClaim操作が
  必要（自動送金ではない）。

## 1. 発端 — セキュリティリリースの通知

Lido CSMコミュニティのDiscordを通じて、Lighthouse v8.2.1が公開された連絡を受けました。GitHubのリリースノートを確認すると、以下の内容でした。

```
バージョン：v8.2.1（High Priority／高優先度）
内容：複数のセキュリティ脆弱性の修正、バグ修正、最適化
      （脆弱性の詳細はユーザーへの対応猶予のため非公開）
対象：全メインネットBeaconノードユーザー
     （Staking Users: Beacon Node = High、Validator Client = Low）
破壊的変更・DBスキーマ移行：なし
Hoodi/Sepolia関連：Partial Data Columns（EIP-8136）の
                   キャッシュ・ゴシップ処理に関する複数バグ修正を含む
```

> 💡 **なぜここまで急いで対応するのか：** 「High Priority」はLighthouse開発チーム（Sigma Prime）が定める更新優先度の中で最も高いランクです。セキュリティ内容自体は「ユーザーへの対応猶予のため」意図的に非公開にされています。これは、脆弱性の詳細を公開すると悪用されるリスクが高まるため、まず世界中の運用者にアップデートする時間を与えてから詳細を明かす、業界標準のプラクティスです。

## 2. 過去のLighthouseアップデート対応との違い

Lighthouseのセキュリティアップデート対応自体は今回が初めてではなく、過去にもv8.1.2・v8.1.3への対応を行っていました。その際はsha256ハッシュ値の照合で検証していましたが、今回はいくつか異なる点がありました。

| 項目 | v8.1.3対応（過去） | v8.2.1対応（今回） |
|---|---|---|
| 検証方法 | sha256ハッシュの数値照合 | PGP署名検証 |
| 対応後の処置 | `sudo reboot`（OS再起動） | サービス再起動のみ（OS再起動なし） |
| 使ったスクリプト | なし（手動コマンドのみ） | `node_safe_stop.sh` は不使用（Geth等も含め全停止してしまうため） |

### なぜ今回はsha256ではなくPGP署名なのか

過去の対応ではリリースページに記載されたsha256ハッシュ値を目視で照合していましたが、v8.2.1のリリースページにはsha256の記載がなく、代わりに各バイナリに対応する`.asc`（PGP署名）ファイルが提供されていました。GitHubのリリース方式は都度変わりうるため、**「今回はどちらの検証方法が提供されているか」を確認する癖をつけておく**ことが大切です。

## 3. PGP署名検証とは何か

### 3-1. sha256との違い

| 検証方法 | 何を証明できるか |
|---|---|
| sha256ハッシュ照合 | ファイルが「ダウンロード中に破損・改ざんされていないか」 |
| PGP署名検証 | ファイルが「本当にSigma Prime（Lighthouse開発元）が作成したものか」＋「改ざんされていないか」 |

sha256は「このファイルの中身」に対してのみ意味を持つ数値で、**誰でも計算できてしまいます**。極端な話、悪意のある第三者が偽のバイナリを用意し、その偽バイナリのsha256値を公開ページに一緒に載せてしまえば、照合結果は「一致」になってしまいます（もちろん、正規のリリースページ自体が改ざんされない限りこれは起きませんが、理屈としての弱点です）。

PGP署名は違います。**Sigma Primeだけが持っている「秘密鍵」で署名しないと作れない**という数学的な性質を利用しています。誰でも真似できるsha256とは根本的に異なる仕組みです。

### 3-2. 公開鍵暗号の考え方

```
Sigma Prime が持つもの：
  秘密鍵（絶対に公開しない、署名を作るための鍵）

世界中の誰でも入手できるもの：
  公開鍵（Fingerprint: 15E66D941F697E28F49381F426416DC3F30674B0）
```

Sigma Primeは秘密鍵でバイナリに対して署名（`.asc`ファイル）を作ります。この署名は、対応する公開鍵を使うことで「本当にこの秘密鍵の持ち主が署名したものか」を誰でも検証できます。秘密鍵を知らない第三者が偽の署名を作ることは（現在の暗号技術では）事実上不可能です。

### 3-3. 実際に行ったコマンドと、その意味

```bash
# ① バイナリ本体と、対応するPGP署名ファイルの両方をダウンロード
cd ~
wget https://github.com/sigp/lighthouse/releases/download/v8.2.1/lighthouse-v8.2.1-x86_64-unknown-linux-gnu.tar.gz
wget https://github.com/sigp/lighthouse/releases/download/v8.2.1/lighthouse-v8.2.1-x86_64-unknown-linux-gnu.tar.gz.asc
```

> 💡 **なぜ2つのファイルが要るのか：** `.tar.gz`が本体、`.asc`が「このファイルはSigma Primeが作りました」という署名データです。片方だけでは検証できません。

```bash
# ② Sigma Primeの公開鍵をインポートする（初回のみ）
gpg --keyserver keyserver.ubuntu.com --recv-keys 15E66D941F697E28F49381F426416DC3F30674B0
```

> 💡 **なぜFingerprintを指定するのか：** 鍵サーバーには同姓同名や偽物の鍵も存在しえます。公式サイトに掲載されている正確なFingerprint（40桁の16進数）を指定してインポートすることで、「本当にSigma Prime本人の鍵」であることを保証します。

```bash
# ③ 署名を検証する
gpg --verify lighthouse-v8.2.1-x86_64-unknown-linux-gnu.tar.gz.asc \
             lighthouse-v8.2.1-x86_64-unknown-linux-gnu.tar.gz
```

**実行結果：**
```
gpg: Signature made Tue 21 Jul 2026 03:56:37 AM UTC
gpg:                using RSA key 15E66D941F697E28F49381F426416DC3F30674B0
gpg: Good signature from "Sigma Prime <security@sigmaprime.io>" [unknown]
gpg: WARNING: This key is not certified with a trusted signature!
gpg:          There is no indication that the signature belongs to the owner.
```

### 3-4. `Good signature` は出たのに `WARNING` も出る理由

初めて見ると不安になる表示ですが、これは2つの異なる質問に対する、2つの異なる答えです。

```
Q1. この署名は本物か？（改ざんされていないか）
A1. Good signature ← 検証成功。本物と確認できた

Q2. あなたはこの鍵の持ち主を個人的に知っていて、信頼していますか？
A2. WARNING（未知） ← GPGの「信頼の輪」機能上の警告。
    今回鍵を初めてインポートしたので、GPG自身は
    「Hiroshiさんがこの鍵の持ち主を信頼すると明示的に
    宣言していない」ことを教えてくれているだけ
```

Q1（技術的な真正性）さえ確認できていれば、今回の目的（改ざんされていない公式バイナリだと確認する）としては十分です。Q2は「あなたはこの人を友達と認定しますか？」に近い、GPGコミュニティ独自の信頼スコアの話であり、セキュリティ上の実害を示す警告ではありません。

## 4. 適用手順と実測記録

### 4-1. 実行前のバージョン確認

```bash
/usr/local/bin/lighthouse --version
```
```
Lighthouse v8.1.3-176cce5
```

### 4-2. 展開・停止・入替・再開

```bash
# 展開する
tar -xvf lighthouse-v8.2.1-x86_64-unknown-linux-gnu.tar.gz
```

> ⚠️ **`node_safe_stop.sh`は今回使いませんでした。** このスクリプトはGeth・MEV-Boost・SSVノードまで含めて全サービスを止める設計になっています。今回はLighthouseの入替だけが目的なので、不要な停止・再起動を避けるため、対象サービスだけを個別に手動で停止しました。

停止前に、ブロック提案が今のエポックに割り当たっていないかを手動で確認しました（第11章のロジックを流用）。

```bash
CURRENT_EPOCH=$(curl -s http://localhost:5052/eth/v1/beacon/headers/head \
  | python3 -c "import sys,json; d=json.load(sys.stdin); print(int(d['data']['header']['message']['slot'])//32)")

curl -s http://localhost:5052/eth/v1/validator/duties/proposer/${CURRENT_EPOCH} \
  | python3 -c "
import sys, json
data = json.load(sys.stdin)
my_indices = set('<自分のindex_1> <自分のindex_2> ...'.split())
found = [d for d in data.get('data', []) if d['validator_index'] in my_indices]
print('⚠ 提案予定あり' if found else '✓ 提案予定なし。安全に停止できます。')
"
```
```
✓ 提案予定なし。安全に停止できます。
```

```bash
# 停止（署名担当を先に）
sudo systemctl stop lighthouse-vc
sudo systemctl stop lighthouse

# 旧バイナリのバックアップ（万が一の切り戻し用）
sudo cp /usr/local/bin/lighthouse /usr/local/bin/lighthouse.v8.1.3.bak

# 新バイナリの配置
sudo cp ~/lighthouse /usr/local/bin/lighthouse
sudo chown root:root /usr/local/bin/lighthouse
sudo chmod 755 /usr/local/bin/lighthouse
```

> 💡 **なぜ `chown root:root` と `chmod 755` を実行するのか：** Lighthouseサービスは`systemd`上で`User=ethereum`という一般ユーザー権限で動いています。一方、バイナリファイル自体の所有者は`root`にしています。これにより、`ethereum`ユーザーは「実行」はできても「書き換え」はできません。万が一Lighthouseプロセス自体に脆弱性があり、`ethereum`ユーザーの権限を奪われるようなことがあっても、攻撃者はバイナリ本体を勝手に改ざんできない、という仕組みです。この設計は第2部でGeth・MEV-Boost・`node_check.sh`にも一貫して適用しています。

```bash
# バージョン確認
/usr/local/bin/lighthouse --version
```
```
Lighthouse v8.2.1-b263df5
```

```bash
# 再開（停止と逆順）
sudo systemctl start lighthouse
sleep 15
sudo systemctl start lighthouse-vc
```

> 💡 **なぜバックアップを取っておくのか：** `chown root:root` により、稼働ユーザー（`ethereum`）自身にはバイナリの書き換え権限がありません。新バージョンに問題があった場合でも、`sudo`権限さえあれば`lighthouse.v8.1.3.bak`を即座に元の場所へ戻すだけで切り戻せます。

### 4-3. 二重の裏取り確認

バージョン表示だけでなく、実際に稼働しているプロセスの実体まで確認しました。

```bash
MAIN_PID=$(systemctl show -p MainPID --value lighthouse)
sudo ls -l /proc/$MAIN_PID/exe
```
```
lrwxrwxrwx 1 ethereum ethereum 0 Jul 21 10:11 /proc/23627/exe -> /usr/local/bin/lighthouse
```

矢印の先が更新後のバイナリを指しており、メモリ上で実際に動作しているプロセスの実体まで確認が取れました。

再起動後、SSVノードの`Sync Slot`が一時的に`Waiting for chain events...`に戻る場面がありました。

```
CL Status : 2/2 synced（正常）
EL Status : ready（正常）
```

## 7. まとめ

| 知見 | 内容 |
|---|---|
| リリースごとに検証方法が違いうる | sha256とPGP署名のどちらが提供されているか、その都度リリースページを確認する必要がある |
| PGP署名は「本物か」を証明する | sha256は破損チェックのみ。PGP署名は「本当に開発元が作ったものか」まで証明できる |
| `Good signature` と `WARNING` は別の話 | 前者が技術的な真正性、後者はGPGの信頼の輪機能に基づく別軸の警告。今回の目的では前者だけで十分 |
| root所有・755権限のバックアップ運用が効いた | 稼働ユーザーはバイナリを書き換えられない設計のため、`sudo`で安全に旧バージョンへ切り戻せる保険を用意できた |
| node_safe_stop.shは万能ではない | 部分的なアップデート（今回はLighthouseのみ）には、対象範囲が広すぎるスクリプトをそのまま使わず、手動コマンドで対象を絞る判断も必要 |
| OS再起動不要でもダウンタイムは発生する | DBスキーマ移行がなくても、サービスの停止〜再開の間は必ず数分の断絶が生じる。監視システムがそれを正しく検知・復旧報告することも合わせて確認できた |

# 第6部・メインネット運用編 第3章 初めてのアップデートと再起動 — 「中身を見てから、止める」

> **更新は、押す前に「中身」を見る。止める前に、「戻り方」を確かめる**

---

| 項目 | 内容 |
|---|---|
| 位置づけ | Activation後、初めての「停止・更新・再起動」の記録。テストネットで設計した安全な再起動の手順（第4部 第11章）を、メインネットで初めて使う |
| 実施日 | 2026年10月2日（Activationから4日目）、翌朝の確認は10月3日 |
| 対象 | `apt list --upgradable`、`node_stop`、`apt upgrade`、`systemctl reboot`、`journalctl`、beaconcha.in |
| 前提 | 第5部 第17章（needrestart）、第5部 第19章（Doppelganger Protection）、第6部 第1章・第2章 |

> ⚠️ 本章は機密情報を一切含みません。Operator番号・バリデータ番号は載せていません。残高と収益額は載せず、損失額（Missed rewards）と、割合のみを示します。

> 💡 **時刻の読み方。** サーバーのログと`last`の時刻はUTC、画面と`node_check`のヘッダーはJSTである（JST = UTC + 9時間）。本章では、両方を併記する。

> 💡 **用語：Doppelganger Protection。** 同じ鍵が、別の場所で、同時に署名してしまうと、重大な罰則（スラッシング）を受ける。これを避けるため、署名役（バリデータクライアント）は、起動した直後に、**数エポックのあいだ、署名せずに様子を見て**、同じ鍵で署名している相手がいないかを確かめる。確認できてから、署名を始める。

## はじめに：6件が24件に増えていた

10/1の朝まで、`node_check`の「保留中のアップデート」は、6件だった。10/2の朝、これが**24件**に増えていた。

今までは、この表示を見ても、中身を確かめずに、更新をかけていた。ところが、バリデータが稼働している今は、**更新は、署名を止める作業**である。何が、どう変わるのかを知らずに、押したくなかった。

本章は、「中身を見る」「リリースノートを読む」「止める」「更新する」「再起動する」「確かめる」の流れを、実測の数字とともに記録する。

## 1. 更新の中身を見る

```bash
apt list --upgradable
```

**なぜ打つか。** 更新できるパッケージの、名前と、新旧のバージョンが出る。`node_check`の件数だけでは、何が入っているか分からない。

出てきたのは、18のパッケージだった。名前から、種類に分けた。

| 種類 | パッケージ | 影響 |
|---|---|---|
| **geth系** | geth、ethereum、abigen、evm、rlpdump（すべて 1.17.4 → **1.17.7**） | **gethが更新される。署名に関わる** |
| **カーネル** | linux-image-generic、linux-headers-generic、linux-generic、linux-libc-dev、linux-tools-common（6.8.0-142 → **146**） | 適用後に**再起動が必要** |
| Grafana | grafana（13.2.2 → 13.2.3） | 軽微。Grafanaだけが再起動する。署名への影響なし |
| そのほか | apparmor、libapparmor1、libaudit-common、libaudit1、dmidecode、thermald、linux-firmware-amd-graphics | 通常の更新 |

前回（10/1）の6件は、「そのほか」の種類だけだった。今回は、**gethとカーネル**が入っていた。この2つが入っているかどうかで、作業の重さが変わる。

`ethereum`、`abigen`、`evm`、`rlpdump`は、gethと同じ配布元（PPA）のツール類で、一緒に更新される。

### 1-1. 「24件」と「18件」のずれ

`node_check`の表示は24件、`apt list --upgradable`に出たのは18件だった。実際に`apt upgrade`を実行したときの表示は、「18件を更新、7件を新規インストール」である。**数え方が、表示によって違う。** 理由は、本章では調べていない。**中身を見る`apt list --upgradable`の結果を、判断の基準にした。**

## 2. リリースノートを読む

gethの更新が入っていたので、GitHubのgo-ethereumのリリースページで、説明を確認する。

| 版 | リリースページ |
|---|---|
| 1.17.6 | https://github.com/ethereum/go-ethereum/releases/tag/v1.17.6 |
| 1.17.7 | https://github.com/ethereum/go-ethereum/releases/tag/v1.17.7 |
| 版の一覧（1.17.5以前を含む） | https://github.com/ethereum/go-ethereum/releases |

見るのは、次の3点である。

| 見る点 | 確認できたこと |
|---|---|
| セキュリティ修正（CVEの記載）はあるか | 1.17.6は、ブロック処理と初期同期の性能改善を中心とした**保守リリース**で、全ユーザーに推奨、と書かれていた。1.17.7の変更点にも、セキュリティ修正の記載は、見当たらなかった |
| 近いハードフォークに必須の更新か | どちらの版も、テストネット（Sepolia）のAmsterdamフォーク（10/6 13:53:36 UTC、JSTでは22:53:36）に対応済みで、**Sepoliaの運用者は、その時刻より前の更新が必要**と書かれていた。**メインネットの日程は、確認できた範囲では、書かれていなかった** |
| 設定やDBに関わる変更はあるか | 1.17.7で、履歴の削除位置を指定する新オプション（`--history.chain`、任意）が加わった。1.17.5で、ガベージコレクションの既定値が変わり、メモリのピークが高くなる代わりに、処理の負荷が下がる。Pebble v2は、新規作成のDBに使われ、既存のDBは、自動では変わらない |

1.17.7は、1.17.6を、Ubuntu向けの配布（PPA）に載せるのに失敗したため、急いで出された版である。aptに1.17.7が来たのは、この経緯のためである。ほかに、チェーン停止時のメモリリークの修正、キャッシュの解放、同期中の取引プールの不具合の修正が入っていた。

### 2-1. 判断

**セキュリティ修正の記載はなく、メインネットで急ぐ理由も、見当たらなかった。** ただし、次の点は、判断に影響する。

- **メモリ**：1.17.5の既定値の変更で、メモリの使われ方が変わる可能性がある。更新後の数日は、メモリとswapの傾きを見る。
- **メインネットのフォーク**：日程が公表されたら、geth・lighthouseの対応版を、あらためて確認する（今後の課題）。

「急ぐ理由がない」ので、時間のあるときを選んで、落ち着いて行う。

## 4. 止める：`node_stop`

```bash
node_stop
```

**なぜ打つか。** 手元のスクリプト（`node_safe_stop.sh`）で、4つのサービスを、**署名役から順に**止める。署名役を最初に止めることで、二重署名のリスクをなくす。

このスクリプトは、止める前に、**ブロック提案の予定**を確かめる。

```
[Step 0-b] Checking Block Proposal Schedule...
 現在のスロット: <slot>（エポック: 479487）
 ✓ 現在のエポックにブロック提案の予定はありません。安全に停止できます。
```

ブロックを提案する番が回ってきている最中に止めると、その報酬を取りこぼす。今回は、予定がないことを確かめたうえで、停止した。

停止後の表示は、次のとおりだった。

```
 - lighthouse-vc: inactive (Safe)
 - lighthouse: inactive (Safe)
 - mev-boost: inactive (Safe)
 - geth: inactive (Safe)
```

停止したことは、Telegramのアラートにも届いた（22:21）。**止めたのは自分なので、想定どおりの通知**である。

## 5. 更新する：`apt update && apt upgrade`

```bash
sudo apt update && sudo apt upgrade
```

**なぜ打つか。** `apt update`で、最新の更新の一覧を取り、`&&`でつないだ`apt upgrade`で、更新する。`apt update`が失敗したときは、`upgrade`に進まない。

**`-y`（確認を省略するオプション）は、付けなかった。** 付けないと、「何が更新・削除されるか」の一覧が出て、確認を求められる。今回は、gethとカーネルが入っているので、一度、画面で確認してから進めたかった。

### 5-1. 確認の画面の読み方

```
The following packages were automatically installed and are no longer required:
  libfwupd2 libgusb2
Use 'sudo apt autoremove' to remove them.
The following NEW packages will be installed:
  linux-headers-6.8.0-146 linux-image-6.8.0-146-generic ... （7件）
The following upgrades have been deferred due to phasing:
  sosreport
The following packages will be upgraded:
  abigen apparmor dmidecode ethereum evm geth grafana ... （18件）
18 upgraded, 7 newly installed, 0 to remove and 1 not upgraded.
Need to get 647 MB of archives.
```

| 表示 | 意味 |
|---|---|
| **`0 to remove`** | **アンインストール（削除）されるパッケージは、ない。** 更新（upgraded）は、同じ名前のパッケージを、新しい版に**置き換える**ことで、削除には数えない。geth、tailscale、sshなどの重要なソフトが、削除の対象に入っていないことを、ここで確認した |
| `7 newly installed` | **新しいカーネルの本体**が、新規に入る。カーネルは、置き換えではなく、**並べて追加**される。古いカーネル（142）は消えず、整理するまで残る。新しい版で問題が出たら、起動メニュー（GRUB）から、古い版を選んで戻れる |
| `deferred due to phasing`（sosreport） | Ubuntuが、更新を少しずつ段階的に配っていて、この環境には、まだ順番が来ていない。異常ではなく、数日後に自然に来る |
| 647MB、334MB | ダウンロードの量と、増えるディスクの量。空き383Gに対して、問題ない |
| `libfwupd2 libgusb2`（no longer required） | 「もう不要」の案内。変更を小さく保つため、今回は触らない |

> 💡 **用語：更新（upgrade）と削除（remove）。** 更新は、入っているパッケージを、新しい版に**置き換える**ことである。削除は、パッケージを**取り除く**ことである。更新に伴って、別のパッケージが不要になったり、競合したりすると、削除が出ることがある。**重要なソフトが消える場合は、確認の画面の`REMOVED`の欄で、気づける。** だから、`-y`を付けず、画面で確かめる。

確認して、`Y`で進めた。

### 5-2. 更新中に出た表示

- **`apparmor.postinst: 148: [: Illegal number: yes`**：パッケージの設定スクリプトが出す、軽い警告に見えた。直後に`Reloading AppArmor profiles`と続いており、処理は進んでいた。
- **GRUBの設定の再生成**で、新しいカーネル（146）、直前のカーネル（142）、さらに前のカーネル（139）の3つが、起動メニューに載った。
- **Grafanaは、更新の中で、自動的に再起動された**（`Restarting grafana-server service... OK`）。ほかのサービスは、すでに止まっているので、この再起動は、署名に関係ない。
- **needrestart**が、再起動すべきサービスの一覧（ssh、fail2ban、systemd系など）を表示した（第5部 第17章）。これから再起動するので、1つずつ手で再起動する必要はない。

## 6. 再起動する

```bash
cat /var/run/reboot-required
```

**なぜ打つか。** `*** System restart required ***`と出れば、新しいカーネルの更新が、正しく入っていることを確認できる。

```bash
sudo systemctl reboot
```

**なぜ打つか。** 新しいカーネルは、再起動して初めて使われる。4つのサービスは`enabled`なので、サービスは手で起動せず、再起動に任せた。

再起動の時刻は、次のコマンドで確認できる。

```bash
last -x reboot shutdown | head -4
```

| 行 | UTC | JST |
|---|---|---|
| shutdown（旧カーネル 142） | 13:22 | 22:22 |
| reboot（新カーネル 146） | 13:23 | 22:23 |

**再起動そのものは、約1分で済んだ。** 前回の再起動（9/24 8:53 JST）から、8日と13時間28分、動き続けていた。

## 8. 署名が止まっていた時間：実測

署名役のログで、様子見の経過を見た。

```bash
sudo journalctl -u lighthouse-vc --since "20 min ago" | grep -i -E "doppelganger|starting validator|error|warn" | tail -20
```

**なぜ打つか。** 署名役のログから、様子見に関わる行だけを抜き出す。

```
13:32:53 UTC  Listening for doppelgangers        doppelganger_detecting_validators: 1
        ... （12秒おきに同じ行が続く）
13:36:17 UTC  Listening for doppelgangers        doppelganger_detecting_validators: 1
13:36:20 UTC  Found no doppelganger              further_checks_remaining: 0, epoch: 479488
13:36:20 UTC  Doppelganger detection complete    msg: "starting validator"
```

- `Listening for doppelgangers`は、12秒（1スロット）ごとに出る「様子見の最中」の表示である。
- `Found no doppelganger`は、「同じ鍵で署名している相手は、見つからなかった」という、いちばん安心できる表示である。

**起動から、様子見の完了まで、約13分**かかった。

### 8-1. 署名の再開

様子見が終わっても、すぐには署名しない。**署名は、1エポック（約6.4分）に1回、決まったスロットで行う**ので、次の自分の番まで待つ。

```bash
sudo journalctl -u lighthouse-vc --since "10 min ago" | grep "Successfully published"
```

**なぜ打つか。** 署名の成功ログだけを抜き出す。1行でも出れば、再開している。

最初の署名は、**13:42:37 UTC（JST 22:42:37）**だった。直後の13:42:47には、MEV-Boostへの登録の再開も、ログに出た（`Published validator registrations to the builder network`）。

### 8-2. 更新前の最後の署名

```bash
sudo journalctl -b -1 -u lighthouse-vc | grep "Successfully published" | tail -1
```

**なぜ打つか。** `-b -1`は、「ひとつ前の起動期間」のログを指す。再起動の直前の、最後の署名の時刻が分かる。

最後の署名は、**13:12:00 UTC（JST 22:12:00）、エポック479486**だった。

### 8-3. 時系列のまとめ（JST）

| 時刻 | 出来事 | 出典 |
|---|---|---|
| 22:12:00 | 更新前の最後の署名（エポック479486） | `journalctl -b -1` |
| 22:19頃 | `node_stop`（エポック479487、提案予定なし） | `node_stop`の表示 |
| 22:22 | 旧カーネルを終了 | `last -x` |
| 22:23 | 新カーネルで起動 | `last -x` |
| 22:36:20 | Doppelganger検知が完了（起動から約13分） | 署名役のログ |
| 22:42:37 | **最初の署名**（エポック479490） | 署名役のログ |

**署名の途切れは、約30分37秒**だった。ただし、署名は1エポックに1回なので、**実際に欠けたのは、エポック479487、479488、479489の、3エポック分**である。「止まっていた時間」と「欠測の数」は、一致しない。

### 8-4. 見積もりとの違い

更新の前は、「数分で済む」と見積もっていた。実際は、次のとおりだった。

| 場面 | 様子見の長さ |
|---|---|
| Activation前（Pending）に起動したとき（第5部 第19章） | 約3分 |
| **稼働中のバリデータを再起動したとき（今回）** | **約13分** |

第5部 第19章では、「待機は、Activation前に吸収された」と書いた。**稼働後の再起動では、この様子見が、そのまま署名の欠測になる。** 停止の見積もりは、停止そのものの数分ではなく、**「止めている時間 ＋ 様子見の約13分 ＋ 次の自分の番までの待ち」** で立てる必要があった。

テストネットでは、Doppelganger Protectionを入れておらず、再起動のあと、すぐに署名を始めていた（実測はしていない）。メインネットでは、この機能を有効にしているため、署名の開始が、遅くなった。

> 💡 **この待ちは、「保険料」と考える。** 様子見は、署名役を起動するたびに、数エポック（約13〜19分）かかる。その間は、署名できない。今回の欠測は、この待ちを含めて3エポックで、1日の報酬の約1.5%だった。一方、同じ鍵が、別の場所でも署名してしまうと、重大な罰則（スラッシング）と、強制的な退出を受ける。**起きる確率は低くても、起きたときの損失が、はるかに大きい。** 待ちが発生するのは、署名役を起動するとき（再起動を含む）だけで、日常の運用では、ほとんど発生しない。導入の経緯は、第5部 第15章で扱っている。

## 9. 翌朝の確認：欠測の確定値

10/3の朝、beaconcha.inのSummary（直近24h）を見た。

| 項目 | 10/2朝（更新前） | 10/3朝（更新後） |
|---|---|---|
| Source | 225 / 0 | 222 / **3** |
| Target | 225 / 0 | 222 / **3** |
| Head | 223 / 2 | 221 / **4** |
| Att. Efficiency | 99.78% | 98.56% |
| Missed rewards | 0.000004 ETH | 0.000027 ETH |

**Source・Targetの3票は、8-3で数えた3エポックと、一致した。** Headの4票は、この3票に、普段の揺れの1票が加わった数である。

Missed rewardsは、**1日の報酬の約1.5%**にあたる。数字の見た目の下がり方（99.78% → 98.56%）に比べて、実害は小さい。

> 💡 beaconcha.inのバリデータページには、成績の相対的な順位を示すラベルが出る。今朝は、「Bottom 25%」と表示されていた（前日までは「Average」）。昨夜の欠測が、影響していると見ているが、計算の期間までは確認していない。**欠測の分が、24hの窓から外れるにつれて、戻るかを、数日見る。**

### 9-1. 更新前後の数字の比較

| 項目 | 更新前（22:17） | 再起動直後（22:25） | 翌朝（8:32） |
|---|---|---|---|
| メモリ使用 | 18Gi | 8.7Gi | 18Gi |
| Swap | 5.1Gi | 0 | 7.8Mi |
| ピア数（Lighthouse / Geth） | 157 / 47 | 23 / 39 | 126 / 49 |
| ディスク空き | 383G | 388G | 383G |
| 時刻同期のオフセット | -0.000122秒 | 0.000027秒 | 0.000312秒 |
| 保留中のアップデート | 24件 | 0件 | 0件 |

- **メモリ使用は、約10時間で、更新前と同じ18Giに戻った。** 1.17.5の既定値の変更で、メモリが増える可能性を考えていたが、いまのところ、目立った増加は見えない。ただし、約10時間の観測なので、数日の傾きを見る必要がある。
- **Swap**は、再起動で5.1Giから0に戻り、翌朝は7.8Miだった。増え方は、緩やかである。
- **ピア数**は、23、78（22:46）、126と、時間とともに戻っている。
- **ディスク空き**は、再起動直後に388Gと出たが、翌朝は383Gに戻った。再起動直後の増加は、一時的だった。原因は、調べていない。
- **時刻同期のオフセット**は、0.000312秒で、更新前より大きいが、目安の0.01秒より、はるかに小さい。参照先は、再起動で、NICTのサーバーの別の1台（ntp-a2 → ntp-a3）に変わっていた。設定では、`ntp.nict.jp`という**名前**で指定しており、NICTは、1つの名前の裏で、複数のサーバーを運用している。起動のたびに、名前から、そのときの1台に当たるためと考えられる。chronyは、NICT、Google、Cloudflareの3つを参照先に持ち、3つのずれは、数ミリ秒以内で一致していた（`chronyc sources`）。

## 10. まとめ

```
① 更新は、押す前に、apt list --upgradable で「中身」を見る。geth、カーネル、
   openssh、tailscale が入っているかどうかで、作業の重さが変わる。
   node_check の件数と、中身の件数が違うことがあるので、中身を基準にする
② gethが入っていたら、リリースノートを読む。見る点は、セキュリティ修正、
   必須のフォーク対応、設定・DBの変更の3つ
③ 更新前に、「再起動後に自動で立ち上がるか」(is-enabled) を確かめ、
   比較用の基準値を控える
④ 止めるときは、署名役から順に。ブロック提案の予定がないことを確かめてから止める
⑤ apt upgrade は、初回は -y を付けず、「削除されるもの（0 to remove）」を
   画面で確かめてから進める
⑥ 稼働中のバリデータの再起動では、Doppelganger の様子見が約13分かかる。
   Activation前の約3分とは違う
⑦ 「止めていた時間」と「欠測の数」は一致しない。署名は1エポックに1回。
   今回は、約30分の途切れで、3エポックの欠測だった
⑧ 翌朝、beaconcha.in で、欠測の確定値を見る。メモリ・swap・ピア数の
   傾きを、数日見る
```

テストネットでは、何度でも繰り返せた。メインネットでは、署名が止まることが、そのまま成績に出る。同じ手順でも、**重みが違う**。その重みが、「中身を見てから、止める」という習慣を、作った。

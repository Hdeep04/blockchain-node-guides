> **100%が99.89%に見えた朝は、焦りよりも先に、「何が外れたのか」を見る**

## はじめに：毎朝、何を見ているか

Activationの後は、毎朝、次の3つを見る。

| 見るもの | 何が分かるか |
|---|---|
| `node_check`（サーバー内で実行） | サービスの稼働、同期、ピア数、メモリ、時刻同期、通信量 |
| beaconcha.in（Monitoringの画面、直近24h） | 実際の署名成績（投票が当たったか、損失はいくらか） |
| Grafana | 数日〜1週間の傾き（ディスク、swap、ピア数、メモリ） |

この3つは、見ている対象が違う。`node_check`は「ノードが健康か」、beaconcha.inは「仕事の結果」、Grafanaは「時間をかけた変化」である。**どれか1つだけでは、判断を誤りやすい。** 本章は、この違いに気づいた記録である。

## 1. 9/30の朝：100%が99.89%になった

9/30の朝、`node_check`はすべて正常だった。ところが、beaconcha.inを開くと、これまで100%だった成績が崩れていた。

```
Attestations    : 225 / 0
  Source        : 225 / 0
  Target        : 225 / 0
  Head          : 224 / 1      ← ここが1票、外れた
Att. Efficiency : 99.89%
Missed rewards  : 0.000002 ETH
```

最初は、「崩れた」と感じた。しかし、数字の中身を読むと、外れていたのは**Headの1票だけ**だった。

### 1-1. 投票の中身：3つの票

Attestation（投票）は、1エポック（32スロット、約6.4分）に1回で、1日に約225回ある。1回の投票には、3つの票が入っている。

| 票 | 意味（初心者向けの言い方） |
|---|---|
| Source | チェーンの大きな区切り（チェックポイント）の、どこから来たか |
| Target | 今のエポックの区切りは、どれか |
| Head | **投票した時点での、チェーンの先頭のブロックは、どれか** |

SourceとTargetは、全部で225票ずつ当たっていた。Headだけが、224票当たり、1票外れた。**投票そのものは届いて、記録されている。** 3つの票のうち、1つが「結果として採用された先頭ブロックと違った」だけである。

### 1-2. Headだけが外れる理由

Headは、「投票したときに、自分が見ていた先頭のブロック」への投票である。次のような場面で、外れることがある。

- ブロックの到着が遅れて、投票の時点では、1つ前のブロックしか見えていなかった
- チェーンの先頭が一瞬だけ付け替えられた（reorg）

どちらも、自分のノードだけの問題とは限らない。ネットワークの出来事で、他のバリデータも同じ場面で外していることがある。

> 💡 **切り分けの方法。** beaconcha.inのバリデータページの「Atts.」タブで、Headが外れたエポックを開く。同じエポックで、他のバリデータも外していれば、ネットワーク側の出来事である。単発なら、様子を見る。本章の観察では、この確認までは行っていない（今後の課題）。

### 1-3. 損失額の目安

Missed rewardsは、0.000002 ETHだった。1日の報酬の約0.1%にあたる。**Headの1票は、成績の数字の見た目ほど、実害は大きくなかった。**

## 2. 3日間の記録

毎朝のbeaconcha.in（直近24h）の値を、並べた。

| 日（JST朝） | Head | Att. Efficiency | Missed rewards |
|---|---|---|---|
| 9/30 | 224 / 1 | 99.89% | 0.000002 ETH |
| 10/1 | 222 / 3 | 99.66% | 0.000006 ETH |
| 10/2 | 223 / 2 | 99.78% | 0.000004 ETH |

SourceとTargetは、3日とも、全部当たっていた。Headのミスは、1票、3票、2票と、上下している。

**判断の目安（暫定）。** サンプルが少ないので、ここでは暫定の目安として、次のように置く。

| 見え方 | 判断 |
|---|---|
| 毎日、1〜3票程度で上下する | 通常の揺れ。様子を見る |
| 毎日10票以上など、増え続ける | ピア数、時刻同期、ネットワーク遅延を調べる合図 |

3日分では、「増えているのか、もともと1〜3票の範囲で揺れているのか」は判断できない。**1週間ほど日次で記録してから、傾向を見る。**

> 💡 10/2の夕方に行った更新作業（再起動を含む）の欠測は、上の表（朝の値）には入っていない。この作業は、第3章で扱う。

## 3. `node_check`の読み方

9/30の出力から、読み方に迷いやすい項目を、取り上げる。

```
[3] Sync Status
 - is_syncing:    false
 - sync_distance: 1

[4] Peer Count
 - Lighthouse Peers: 174
 - Geth Peers:       48

[5] Recent Attestations (Last 3)
Sep 29 23:16:48 ... Successfully published attestations
  count: 1, validator_indices: [<validator_index>], slot: 15324982, ...
```

### 3-1. `sync_distance`：0〜1は正常

ブロックは約12秒ごとに進む。自分のノードが、最新から何ブロック遅れているかが `sync_distance` である。**0か1なら、追いついている。** 瞬間的に1と見えるのは、ちょうどブロックが届く直前だからである。

### 3-2. ピア数：上下するのが普通

Lighthouseのピア数は、9/30が174、10/1が149、10/2が164だった。毎日違うが、いずれも十分な数である。ピア数は、常に入れ替わっている。**減っても、100を大きく下回らなければ、慌てない。**

### 3-3. [5]の時刻：UTCとJSTのずれ

`[5]`のログは、`Sep 29 23:16:48`と出ている。ヘッダーは、`2026-09-30 08:19:48 (JST)`である。一見、9時間前の署名に見える。

実際は、ログがUTCで、ヘッダーがJSTだからである。`23:16:48 UTC`は、JSTでは`08:16:48`、つまり**約3分前**の署名だった。**この見かけのずれは、初心者が混乱しやすい。** 時刻を見るときは、まず、どのタイムゾーンかを確かめる。

### 3-4. メモリ：freeではなくavailableを見る

9/30のメモリは、次のとおりだった。

```
               total        used        free      shared  buff/cache   available
Mem:            29Gi        18Gi       1.1Gi       308Ki       9.8Gi        10Gi
```

`free`は1.1Giしかなく、少なく見える。しかし、`buff/cache`が9.8Giある。Linuxは、空いているメモリを、ディスクのキャッシュに使う。**キャッシュは、必要になれば自動で解放される。** 実質の余裕は、`available`の10Giである。

### 3-5. 通信量：日次集計はUTC基準

`[10]`の日次集計は、UTCの日付で区切られている（JSTの9:00に切り替わる）。第5部 第14章で入れた表示である。UTCの日ごとの、受信と合計は、次のとおりだった。

| UTC日 | 受信 | 合計 | 備考 |
|---|---|---|---|
| 9/28 | 90.86 GiB | 224.63 GiB | Activation当日（カラムバックフィルを含む。第5部 第19章） |
| 9/29 | 53.72 GiB | 128.73 GiB | |
| 9/30 | 53.98 GiB | 123.44 GiB | |
| 10/1 | 53.56 GiB | 127.94 GiB | |

受信は、9/29〜10/1の3日間、約53〜54 GiBで安定していた。第5部 第19章の「受信量が通常の水準で、1週間安定しているか」という課題は、3日分まで確認できた。残りは、観察を続ける。

## 4. Swap：使用量と、動作は別物

Grafanaの「Swap Usage」は、9/24の再起動で一度0に戻ったあと、右肩上がりで増えていた。`node_check`でも、`Swap: 4.1Gi / 8.0Gi`と出ている。

最初は、「メモリが足りなくなっているのでは」と感じた。メモリの`available`は10Giあるが、増え続けるなら、原因は把握したい。そこで、いま実際にswapが動いているかを、確かめた。

```bash
vmstat 5 3
```

**なぜ打つか。** 5秒おきに3回、メモリとswapの動きを表示する。`si`（swapから読み戻した量）と、`so`（swapへ書き出した量）の2列を見る。ほぼ0なら、使われなくなった古い領域が置いてあるだけで、害はない。数字が大きい状態が続くなら、メモリ不足で苦しんでいる。

結果は、次のとおりだった（抜粋）。

```
procs -----------memory---------- ---swap-- -----io---- -system-- -------cpu-------
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st gu
 0  0 4331100 751164  76996 10540520   14   21  1591  2832 15799   15  4  1 95  0  0  0
 1  0 4330332 673940  77024 10564640  146    0  3013  1295 20363 36524  5  1 94  0  0  0
 0  0 4330332 731976  77040 10580336   18    0  1570   420 16401 25228  4  1 95  0  0  0
```

### 4-1. 読み方

- **1行目は、起動してからの平均値**である。`vmstat`は、最初の1行だけ、そうなる。判断には使わない。
- **2行目と3行目が、5秒ごとの実測値**である。`so`は0と0、`si`は146と18だった。
- **`so`が0**なら、いま新たに、swapへ追い出していない。
- **`si`が146と18**（KB/秒）は、ごく少量である。
- `wa`（ディスク待ち）は0、`id`（CPUの空き）は94〜95%だった。

**結論：swapに約4.3GB置かれているが、動いてはいない。** 「swapを使っている」と、「swapで困っている」は、別の話である。

### 4-2. 危険な状態は、どう見えるか

`si`と`so`の両方が、数千KB/秒以上で、何十秒も続く状態である。このとき、GethやLighthouseの処理が遅れ、署名ミスにつながる。今回は、その逆の見え方だった。

### 4-3. 残した課題

この観察は、10秒分である。「今日は動いていない」ことしか言えない。swapの使用量が、緩やかに増えている理由（どのプロセスが持っているか）は、まだ調べていない。数日後に、Grafanaで傾きを見て、増え続け、かつ`available`も減っていくなら、対策を考える。

## 5. 稼働直後のAPRは、薄まって見える

beaconcha.inのバリデータページには、APRが3つ並ぶ。

```
APR  7d | 31d | 365d
9/30 : 0.46% | 0.10% | 0.01%
10/1 : 0.76% | 0.17% | 0.01%
```

この数字は、バリデータの実力を表していない。7日、31日、365日の平均には、**Activation前の、報酬が0の日**が含まれている。稼働して数日なので、平均が薄まって、小さく出る。

一方、Monitoringの画面（直近24h）のAPRは、2.1%前後だった。直近1日の報酬を、年率に直した値で、こちらが現在の水準に近い。

## 6. テストネットとの比較：票数ではなく、ミス率で

「テストネットよりも、メインネットのほうが、成績が良い」と感じた。数字で比べた。

| 項目 | テストネット（Hoodi、10鍵、直近24h） | メインネット（1鍵、10/1） |
|---|---|---|
| Head | 2,057 / 193 | 222 / 3 |
| Headのミス率 | 約8.6% | 約1.3% |
| Att. Efficiency | 98.02% | 99.66% |
| Source / Target | すべて当たり | すべて当たり |

Headのミス率は、メインネットのほうが、約6分の1だった。

**比べるときの注意が、3つある。**

1. **鍵の数が違う。** 票数ではなく、ミス率で比べる。
2. **メインネットは、まだ数日分である。** 1票の差で、数字が大きく動く。1週間ほど記録してから、判断する。
3. **原因までは、言えない。** テストネットは、ネットワーク側の要因が大きかった可能性があるが、当時、原因は調べていない。構成や設定の違いも、あるかもしれない。

「メインネットのほうが、成績は良さそう。1週間の記録で確かめる」が、いまの位置づけである。

## 7. ダッシュボードの100%と、実成績は別物

9/30の朝、Grafanaの「Attestation Readiness」は、100%のままだった。beaconcha.inでは、Headが1票外れていたのに、である。

この指標は、名前のとおり「投票できる状態か」を見ている。**結果（Headが当たったか）は、見ていない。** 指標の計算式は、本章では確認していない。

## 8. まとめ

```
① beaconcha.inで、100%が99.89%に見えても、まず「どの票が外れたか」を
   見る。Headの1票だけなら、投票は届いており、損失は1日の報酬の約0.1%
② Headのミスは、9/30〜10/2で、1票・3票・2票だった。通常の揺れの範囲に
   見えるが、3日分では傾向は言えない。1週間の記録で判断する
③ node_checkの[5]は、ログがUTC、ヘッダーがJST。約9時間前に見えても、
   実際は数分前のことがある
④ swapの使用量が多いことと、swapで困っていることは別。vmstatの
   si・so（2行目以降）で、動きを見る
⑤ 稼働直後のAPR（7d・31d・365d）は、Activation前の日を含むため、
   薄まって見える。現在の水準は、直近24hのAPR（約2.1%）が近い
⑥ テストネットとの比較は、票数ではなく、ミス率で行う。ただし、
   メインネットの数字が、まだ少ない
⑦ Grafanaの「Attestation Readiness」は、実際の署名成績とは別物
```

「100%が崩れた」と感じた朝は、数字の中身を読んで、落ち着いた。**見る場所が3つあり、それぞれ、見ている対象が違う。** その気づきが、この章の、いちばんの収穫である。

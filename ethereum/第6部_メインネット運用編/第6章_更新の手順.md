## はじめに：ニュースを見て、最初に浮かんだ問い

2026年10月、ソフトウェアのセキュリティ事故が、立て続けにニュースになった。GitLabの緊急パッチ、eMudhra認証局の鍵の問題、PHPの緊急セキュリティリリース、AI関連のソフトLiteLLMの汚染された版などである。日本でも、大きな話題になった。

最初に浮かんだ問いは、「**このバリデータのサーバーに影響はあるのか。何か対策はあるのか**」だった。

調べていくと、サーバーのソフトの更新には、**aptの一覧に出るものと、出ないもの**の2種類があると分かった。第3章と第5章で扱ったのは、前者である。本章では、後者（手で入れたソフト）の更新を、実際にやった手順で記録する。ニュースを見たときの確認の仕方は、次の第7章で扱う。

## 1. 更新には2種類ある

| 種類 | 例 | 新しい版が出たとき |
|---|---|---|
| **apt** | geth、grafana、tailscale、OSの部品 | `node_check`と`apt list`に**出る** |
| **手動** | lighthouse、mev-boost、prometheus、node_exporter | どこにも**出ない** |

初心者がつまずきやすい点は、**「保留中の更新は0件」と表示されても、手動のソフトに新しい版がないとは限らない**ことである。aptは、自分が管理しているソフトしか数えない。手で置いたバイナリ（実行ファイル）は、aptから見えない。

たとえるなら、aptは「宅配で届く荷物」、手動は「自分で店に買いに行く荷物」である。宅配の一覧に載っていなくても、店には新商品が並んでいる。

`apt list --upgradable`の読み方は、第3章の1節と、第5章の1節で説明した。本章では、繰り返さない。

### 1-1. どのソフトが、どちらか

```bash
for c in geth lighthouse mev-boost prometheus node_exporter grafana-server tailscale; do p=$(which $c 2>/dev/null); echo "== $c : ${p:-見つからない}"; [ -n "$p" ] && dpkg -S "$p" 2>/dev/null | head -1; done
```

**なぜ打つか。** 7つのソフトについて、「どこに置かれているか」（`which`）と、「aptが自分の管理物として知っているか」（`dpkg -S`）を、続けて調べる。読むだけで、何も変更しない。

```
== geth : /usr/bin/geth
geth: /usr/bin/geth
== lighthouse : /usr/local/bin/lighthouse
== mev-boost : /usr/local/bin/mev-boost
== prometheus : /usr/local/bin/prometheus
== node_exporter : /usr/local/bin/node_exporter
== grafana-server : /usr/sbin/grafana-server
grafana: /usr/sbin/grafana-server
== tailscale : /usr/bin/tailscale
tailscale: /usr/bin/tailscale
```

**表示の読み方**

| 表示 | 意味 |
|---|---|
| `== geth : /usr/bin/geth` | `which`の結果。gethの実行ファイルの置き場所 |
| その次の行（`geth: /usr/bin/geth`） | `dpkg -S`の結果。「aptのgethパッケージが、このファイルを入れた」という意味。**管理下** |
| 次の行が出ない（lighthouseなど） | aptが、そのファイルを知らない。**管理外**（自分で置いたもの） |

| ソフト | 置き場所 | aptの管理 |
|---|---|---|
| geth、grafana、tailscale | `/usr/bin`、`/usr/sbin` | 管理下。`apt upgrade`で更新される |
| lighthouse、mev-boost、prometheus、node_exporter | `/usr/local/bin` | **管理外**。自分で、新しい版に入れ替える |

> 💡 **`/usr/local/bin/`は、「自分で置いたプログラム」の置き場所である。** aptが入れるものは、`/usr/bin`などに置かれる。置き場所を見るだけでも、手動かどうかの見当が付く。

### 1-2. 手動のソフトの版を、自分で確かめる

```bash
lighthouse --version | head -1; mev-boost -version 2>&1 | head -1; prometheus --version 2>&1 | head -1; node_exporter --version 2>&1 | head -1
```

**なぜ打つか。** 手動のソフトは、aptの一覧に版が出ない。そこで、ソフト自身に「何版か」を聞く。4つを1行にまとめると、見比べやすい。

```
Lighthouse v8.2.2-e423a66
mev-boost 1.12
prometheus, version 3.14.0 (branch: HEAD, revision: d7598b71…)
node_exporter, version 1.12.1 (branch: HEAD, revision: 6044da78…)
```

（これは、更新前の版である。）

- `v8.2.2`が版番号である。ハイフンのあとの`e423a66`は、ビルド元の目印（コミット番号）で、版の比較には使わない。
- `| head -1`は、出力の1行目だけを見せる指定である。続きの行（BLSライブラリの情報など）は、版の確認には要らない。
- `2>&1`は、エラーの表示も同じ画面にまとめる指定である。ソフトによっては、版を、エラー側の出力に書くものがある。

この版番号を、**公式のリリースページの最新版と見比べる**のが、手動ソフトの更新確認である。

### 1-3. aptで入るものにも、「自動」と「自分の仕事」がある

aptの管理下でも、すべてが同じ扱いではない。

- **自分の仕事のもの：geth。** `apt list`の一覧に「待っている」状態で出てくる。第3章では、1.17.4から1.17.7への更新が、入らないまま一覧に載っていた。入れる日は、自分で決める。
- **自動で入るもの：OSの部品、カーネル。** 第5章の1-2で、手を入れていないのにカーネルが入っていた。自分では更新していないので、Ubuntuの自動のセキュリティ更新が入れたと見ている。ただし、自動更新の設定は、確認していない（第5章の「今後の課題」）。

> 💡 **「自動」と「自分」の境目が分からなくなったら、`apt list --upgradable`を見る。** 一覧に出ているものが、「まだ入っていないもの」である。

## 2. 手動ソフトの見張り：GitHubのReleases通知

### 2-1. なぜ通知が要るのか

手動のソフトは、aptの一覧に出ない。新しい版が出ても、自分から見に行かない限り、気づけない。**気づけないと、セキュリティの修正が出ても、古い版のまま動き続ける。** 署名役とビーコンノードの本体であるLighthouseが、その1つである。

そこで、「新しい版が出たら、メールが届く」仕組みを作る。GitHubには、リポジトリ（ソフトの置き場）ごとに、**Releases（新しい版の公開）だけ**を通知する設定がある。

### 2-2. 見張る5つ

| ソフト | リポジトリ | 見張る理由 |
|---|---|---|
| Lighthouse | `sigp/lighthouse` | 手動。署名役と、ビーコンノードの本体 |
| MEV-Boost | `flashbots/mev-boost` | 手動 |
| Prometheus | `prometheus/prometheus` | 手動（監視） |
| node_exporter | `prometheus/node_exporter` | 手動（監視） |
| Geth | `ethereum/go-ethereum` | aptで入るが、更新の前に、リリースノートを読むため |

Gethは、aptの一覧にも出る。それでも通知を設定するのは、一覧には「新しい版がある」としか出ず、**中身（セキュリティ修正か、設定の変更か）は読めない**ためである。第3章では、リリースノートを読んで、1.17.7が急ぎの版ではないと判断した。

### 2-3. 設定のしかた（リポジトリごとに1回ずつ）

1. GitHubにログインして、リポジトリのページを開く。
2. 右上の**Watch**を押す。
3. **Custom**を選び、**Releases**にだけチェックを入れて、保存する。

**なぜ「Releases」だけか。** Watchの既定は、議論や修正依頼など、あらゆる通知が届く。バリデータの運用に必要なのは、新しい版の知らせだけである。他の通知まで受けると、大事なメールが埋もれる。

> 💡 通知の送り先は、普段使いのメールとは**分けた、専用のアドレス**にした。見張り用のメールだけを探せば済み、迷惑メールの中にも、紛れ込みにくい。

### 2-4. 通知が届いたら

届いたメールには、新しい版の番号と、リリースノートが載っている。**メールを見たら、公式のリリースページも、直接開いて確認する**（3節）。

## 3. 公式の案内の読み方

### 3-1. 検索の要約ではなく、公式のページを見る

新しい版が出たら、**GitHubのリリースページを、直接開く**。検索の要約は、古い版や、一部だけを拾うことがあるためである。実際に、AIアシスタント（Claude）に調べてもらったとき、検索の要約だけで、最新版（v8.3.0〜v8.3.2）を見落としかけた（10節）。

リリースページは、上から次の順に読む。

| 読む場所 | 何が分かるか |
|---|---|
| Summary | その版の目的。自分のネットワーク（メインネットか、テストネットか）に関係があるか |
| Upgrade Notes | 更新で何が変わるか（データベース、必要な環境、設定） |
| Update Priority | 自分のような利用者に、どれだけ急ぐ更新か |
| Known Issues | 既知の不具合。自分の環境に当てはまるか |
| Binaries | 入れるファイルと、署名（PGP）の置き場所 |

### 3-2. v8.2.2 から v8.3.x：書き方の違い

v8.2.2のUpgrade Notesは、更新以外の作業が不要で、データベースの移行もない、という内容だった。一方、v8.3.0には、確認が要る項目が並んでいる。

| 項目 | 公式の案内 | 自分の環境での見方 |
|---|---|---|
| データベース | 起動時に、自動で schema v32 に移行する | 自動で行われる。戻すときだけ、手順が要る（6節） |
| glibc | ビルド済みのLinuxバイナリは、glibc 2.34以上が必要 | Ubuntu 24.04は対応している。確かめ方は3-3 |
| MEV-Boost | 古いビルダーAPIへの切り替えをやめ、新しい方だけを使う。最新版のMEV-Boostを使うこと | 1.12を使用中。調べた範囲で、最新版だった |
| 通信 | partial data columns が、メインネットでも既定で有効 | 更新後の通信量の変化との関係は、まだ確認していない |
| 優先度 | メインネットのステーキング利用者は、ビーコンノードが High、バリデータクライアントが Medium | セキュリティ修正を含むため、急ぐ側 |

v8.3.1は、**優先度が高い版**だった。侵害されたeMudhra認証局に対応するため、Lighthouseが信頼する証明書を更新している。すべてのネットワークの、すべての利用者に、できるだけ早い更新が勧められている。特に、HTTPSを使う構成（チェックポイント同期、web3signer、VCとBNの接続など）では、早い更新が勧められている。

これが、この章の出発点の問い（「このサーバーに影響はあるのか。対策はあるのか」）に、直接つながる。ニュースの事故に対して、**Lighthouseの側に、対策の版が出ていた**。自分の構成が、実際に影響を受ける条件に当てはまるかは、確認していない。

> 💡 **用語：schema（スキーマ）。** データベースの、中身の並べ方の版である。版が上がると、古い版のソフトは、新しい形のデータベースを読めない。だから、「戻す」ときは、データベースの形を先に戻す。

### 3-3. glibc の確認

```bash
ldd --version | head -1
```

**なぜ打つか。** glibcは、Linuxのプログラムが共通で使う部品である。新しいバイナリは、2.34以上でないと動かない。入れる前に、自分の環境の版を確かめる。

```
ldd (Ubuntu GLIBC 2.39-0ubuntu8.9) 2.39
```

末尾の`2.39`が、glibcの版である。条件の2.34以上を満たしている。かっこの中の`2.39-0ubuntu8.9`は、Ubuntuが付けた修正番号で、比較には使わない。

> 💡 実際の作業では、このコマンドは先に打たず、更新ログの表示から見当を付けて、新しい版を解凍し、**入れ替える前に、版の表示を試して**確かめた（5節）。条件の確認は、入れる前に、直接確かめるほうが確実である。

### 3-4. schema v32 は、ログに出たか

起動のログには、`Merging blob info and data column info into data info`という行と、データベースを引き継いで再開した記録（`resume`）が出た。一方、「schema v32」という文言そのものは、見ていない。

公式の案内には、schema v32の内容として、blobとdata columnの保存情報を1つにまとめる変更が書かれている。ログの行と、内容は対応していると見ている。ただし、文言そのものを確認したわけではない。

### 3-5. v8.3.2 の「メインネットは更新不要」の意味

v8.3.2のページには、メインネットの利用者は更新不要、と書かれている。理由は、この版が、Hoodi（テストネット）で予定されていたフォークを無効にするための版だからである。

ただし、同じページには、v8.2.x以前から上げる場合は、v8.3.0の更新の注意も読むこと、とある。私の環境は、v8.2.2からだったので、**「不要」は、v8.3.2で新しく変わった分についての話で、v8.3.0の更新の注意は、そのまま当てはまる**、と読んだ。

> 💡 **優先度の表は、「その版で新しく直った分」についての表である。** 版を何段か飛ばして更新するときは、間の版の案内も、読む。

> この読み方は、公式のページに書かれた2点（「メインネットは更新不要」と「v8.2.x以前から上げる場合は、v8.3.0の案内も読む」）を、合わせて解釈したものである。

## 4. 署名の確認：ダウンロードしたファイルは、本物か

### 4-1. なぜ確認するのか

aptで入れるソフトは、署名の確認が、裏で自動で行われる。手動のソフトは、自分でダウンロードして置くので、この確認を、自分で行う。

PGPの署名が何を証明するのか、sha256との違い、公開鍵暗号の考え方は、第4部 第12章（セキュリティアップデート対応）で扱った。本章では、メインネットでの実際の出力と、その読み方を示す。

> 💡 **リリースごとに、検証の方法が違うことがある。** 第12章で書いたとおり、sha256が提供される版と、PGPの署名が提供される版がある。今回のv8.3.2は、バイナリが、Sigma Primeの署名の鍵で署名されている、とリリースページに書かれていた。

### 4-2. 本体と署名を取得する

```bash
mkdir -p ~/lh-upgrade && cd ~/lh-upgrade && curl -LO https://github.com/sigp/lighthouse/releases/download/v8.3.2/lighthouse-v8.3.2-x86_64-unknown-linux-gnu.tar.gz && curl -LO https://github.com/sigp/lighthouse/releases/download/v8.3.2/lighthouse-v8.3.2-x86_64-unknown-linux-gnu.tar.gz.asc
```

**なぜ打つか。** 本体（`.tar.gz`）と、署名（`.asc`）の2つが要る。片方だけでは、確認できない。作業用のフォルダ`~/lh-upgrade`に置く。`mkdir -p`は、フォルダがなければ作る指定である。第12章では`wget`を使ったが、`curl -LO`でも、同じ結果になる。

```
100 29.9M  100 29.9M    0     0  29.6M      0  0:00:01  0:00:01 --:--:--  112M
...
100   833  100   833    0     0   1872      0 --:--:-- --:--:-- --:--:--  1872
```

（進み具合の表示のうち、完了した行だけ示した。）

| 表示 | 意味 |
|---|---|
| 1つ目：`100 29.9M` | 本体が、約29.9MB、最後まで取得できた |
| 2つ目：`100 833` | 署名が、833バイト、取得できた |

```bash
ls -lh ~/lh-upgrade
```

**なぜ打つか。** 2つのファイルが、そろっているか、大きさが、上の表示と合っているかを確かめる。

```
-rw-rw-r-- 1 <user> <user> 30M Oct 25 01:46 lighthouse-v8.3.2-x86_64-unknown-linux-gnu.tar.gz
-rw-rw-r-- 1 <user> <user> 833 Oct 25 01:46 lighthouse-v8.3.2-x86_64-unknown-linux-gnu.tar.gz.asc
```

> 💡 ファイルの時刻は、UTCで表示される。日本時間は、9時間進める。

### 4-3. 公式の鍵を取り込む

```bash
gpg --keyserver hkps://keyserver.ubuntu.com --recv-keys 15E66D941F697E28F49381F426416DC3F30674B0
```

**なぜ打つか。** 鍵のサーバーから、Sigma Primeの公開鍵を取得して、サーバーの鍵の一覧に追加する。署名の確認に要る。鍵の番号（40桁）を指定するのは、似た名前の偽の鍵を、取り込まないためである（第12章の3-3）。**打つ前に、リリースページの番号と、見比べる。**

今回は、すでに取り込み済みだった。

```
gpg: key 26416DC3F30674B0: "Sigma Prime <security@sigmaprime.io>" not changed
gpg: Total number processed: 1
gpg:              unchanged: 1
```

| 表示 | 意味 |
|---|---|
| `not changed`、`unchanged: 1` | すでに取り込み済みで、変更はなかった。**エラーではない** |
| （初回は）`imported: 1` | 新しく取り込んだ |

### 4-4. 署名を確かめる

```bash
gpg --verify lighthouse-v8.3.2-x86_64-unknown-linux-gnu.tar.gz.asc lighthouse-v8.3.2-x86_64-unknown-linux-gnu.tar.gz
```

**なぜ打つか。** 署名のファイル（`.asc`）と、本体（`.tar.gz`）を、突き合わせる。書く順番は、署名、本体の順である。

```
gpg: Signature made Thu 22 Oct 2026 11:51:26 PM UTC
gpg:                using RSA key 15E66D941F697E28F49381F426416DC3F30674B0
gpg: Good signature from "Sigma Prime <security@sigmaprime.io>" [unknown]
gpg: WARNING: This key is not certified with a trusted signature!
gpg:          There is no indication that the signature belongs to the owner.
Primary key fingerprint: 15E6 6D94 1F69 7E28 F493  81F4 2641 6DC3 F306 74B0
```

| 表示 | 意味 |
|---|---|
| **`Good signature from "Sigma Prime …"`** | **公式の鍵で署名され、書き換えられていない。これが決め手** |
| `using RSA key 15E66D94…` | 署名に使われた鍵。リリースページの番号と、同じか見比べる |
| `Primary key fingerprint: 15E6 6D94 …` | 鍵の指紋。**空白を除くと**、公式の番号と同じ |
| `WARNING: This key is not certified…` | 鍵の持ち主を、自分で保証していない、という注意。**署名が悪いという意味ではない**（第12章の3-4） |

> 💡 **失敗の見え方：`BAD signature`。** これが出たら、**先に進まない。** ダウンロードし直して、もう一度確かめる。

### 4-5. この確認で、分かること、分からないこと

| | 内容 |
|---|---|
| 分かること | 通信の途中で、ファイルが差し替えられていないこと。公式の鍵で署名されたものであること |
| 分からないこと | 公式の開発や公開の仕組みそのものが乗っ取られ、**正規の経路から**悪意のある版が出た場合 |

2026年10月に、AI関連のソフトLiteLLMで、ソフトを公開する自動の仕組み（リリースの仕組み）が乗っ取られ、悪意のある版が、**公式の配布所**に並んだ。開発者のログイン情報（認証トークン）が盗まれ、正規の仕組みが、名前が1文字違うだけの偽の置き場（リポジトリ）に向けて動かされた。悪意のある版は、公式の配布所に、2時間前後、置かれていた。

> 💡 **用語：公式の配布所。** PyPIは、プログラミング言語Pythonのソフトを配る、公式の配布所である。スマホのアプリストアのようなものである。Dockerのレジストリは、Dockerというソフトで「箱詰めされたソフト」を配る、配布所である。LiteLLMの悪意のある版は、この2か所に並んだ。どちらも、ふだん、「公式から入れた」と安心して使う場所である。

**正規の経路から出たものは、見た目では、正規のものと区別できない。** そのため、署名の確認は、ひとつの確認として、リリースノートを読むこと（3節）や、入れ替える前に、実行できるかを確かめること（5節）と、組み合わせる。

## 5. 退避、解凍、動作確認、入れ替え

### 5-1. 全体の流れ

手動のソフトの入れ替えは、aptのように、1つの命令では済まない。次の順に、1つずつ進める。

| 順 | 内容 | 本章の節 |
|---|---|---|
| 1 | 署名を確かめる（ダウンロードしたファイルが、本物か） | 4節 |
| 2 | サービスを止める（`node_stop`） | 第3章・第5章 |
| 3 | 今の版を記録する | 5-2 |
| 4 | 今のバイナリを退避し、新しいものを解凍し、**版の表示だけ試して**、実行できるかを確かめる | 5-3 |
| 5 | 入れ替える | 5-4 |
| 6 | aptの更新（Gethなど）と、サーバーの再起動 | 第5章 |

> 💡 **停止のあとで、署名の確認は行わない。** 署名の確認は、停止の前（サービスが動いているうち）に済ませる。停止している間は、署名が止まっているので、時間を無駄にしない。

### 5-2. 今の版を記録する

```bash
lighthouse --version | head -1
```

**なぜ打つか。** 入れ替える前の版を、記録する。入れ替えたあとの確認と、戻すときの目印になる。

```
Lighthouse v8.2.2-e423a66
```

### 5-3. 退避、解凍、入れる前の動作確認

```bash
cp /usr/local/bin/lighthouse ~/lh-upgrade/lighthouse-v8.2.2.bak && cd ~/lh-upgrade && tar -xzf lighthouse-v8.3.2-x86_64-unknown-linux-gnu.tar.gz && ./lighthouse --version | head -1
```

**なぜ打つか。** 4つの動作を、続けて行う。`&&`は、「前の命令が、成功したら、次へ進む」という意味で、途中で失敗すれば、そこで止まる。

| 順 | 命令 | 意味 |
|---|---|---|
| 1 | `cp /usr/local/bin/lighthouse ~/lh-upgrade/lighthouse-v8.2.2.bak` | **今のバイナリを、作業用のフォルダに退避**する。問題があれば、これを戻す |
| 2 | `cd ~/lh-upgrade` | 作業用のフォルダに移動する |
| 3 | `tar -xzf lighthouse-v8.3.2-….tar.gz` | 新しい`.tar.gz`を**解凍**する。中に、`lighthouse`という実行ファイルが入っている（`x`は取り出す、`z`は圧縮の形式、`f`はファイルの指定） |
| 4 | `./lighthouse --version \| head -1` | 解凍した新しい版で、**版の表示だけ試す**（サービスは、起動しない） |

```
Lighthouse v8.3.2
```

**4の意味**：`./`は、「今いるフォルダの中の`lighthouse`」という意味である。`/usr/local/bin`の、今の版ではなく、解凍した新しい版を、1回だけ起動して、版を表示させる。表示すると、すぐに終わる。**入れ替える前に、新しい版が、この環境で実行できるかを、確かめる。**

| 結果 | 意味 |
|---|---|
| `Lighthouse v8.3.2` | 新しい版が、起動できて、版を答えた。**3-3で見た、glibcの条件も満たしている**（今回は、これが出た） |
| `GLIBC_2.34 not found` | glibcが古い。**入れ替えず**、ここで止まる（今の版は、そのまま残っている）。今回は、出なかった |
| `cannot execute` | 実行できない。ファイルが壊れているか、CPUの種類が違う。**入れ替えず**、止まる。今回は、出なかった |

> 💡 **「入れてから確かめる」のではなく、「入れる前に、実行できるかだけ確かめる」。** ここで失敗しても、`/usr/local/bin`の中身は、まだ、変わっていない。署名を止めている時間を、短くするための順番である。

> 💡 **確かめられるのは、「実行できるか」だけである。** `./lighthouse --version`は、版を表示して、すぐに終わる。ビーコンノードや署名役は、起動していない。ノードとして正しく動くか、データベースの移行が成功するかは、サービスを起動したあと（第5章の5節）に、初めて分かる。

> 💡 **退避先は、`/usr/local/bin`の外にした。** 第12章では、`/usr/local/bin/lighthouse.v8.1.3.bak`に退避した。今回は、作業用のフォルダ`~/lh-upgrade`にまとめた。作業の終わりに、フォルダごと片づけやすい。

> 💡 **長い命令は、1行で打つ。** `&&`でつないだ命令は、前の命令が成功したときだけ、次へ進む。途中で失敗すれば、そこで止まり、先の命令は、動かない。停止している間は、署名が止まっているので、1つずつ貼るより、1行のほうが、時間を無駄にしない。**貼る前に、入力欄が空であることを確かめる。** 前の入力が残っていると、命令がつながってしまう。

### 5-4. 入れ替える

```bash
sudo cp ~/lh-upgrade/lighthouse /usr/local/bin/lighthouse && lighthouse --version | head -1
```

**なぜ打つか。** 新しい`lighthouse`を、サービスが使う場所（`/usr/local/bin/`）に置く。続けて、置いた版を、確認する。`/usr/local/bin`は、一般ユーザーが書き込めない場所なので、`sudo`が要る。

```
[sudo] password for <user>:
Lighthouse v8.3.2
```

| 表示 | 意味 |
|---|---|
| `[sudo] password for …:` | `sudo`の確認。**ログイン用のパスワードを入力する**（画面には、表示されない） |
| `Lighthouse v8.3.2` | **`/usr/local/bin`の、置いた版が、v8.3.2になった**（`./`を付けていないので、今度は、ここの版を表示している） |

> 💡 **`Text file busy`と出たら。** 動いているプログラムの上には、上書きできない。Lighthouseが、まだ動いている可能性がある。サービスが、止まっているかを確かめる（`node_stop`の表示、`inactive (Safe)`）。今回は、出なかった。

> 💡 **5-3の4と、5-4の確認の違い。** 5-3の`./lighthouse`は、**解凍した新しい版**を、5-4の`lighthouse`は、**置いた版**を、表示している。どちらも`v8.3.2`と出て、初めて、確認が、2回取れる。

### 5-5. 入れ替えたあとの、持ち主と権限

第12章では、入れ替えのあとに、`chown root:root`と`chmod 755`を打った。今回は、`cp`で、**すでにあるファイルに上書き**したので、打たなかった。上書きでは、元のファイルの持ち主と権限が、そのまま残ると見ていた。確かめた。

```bash
ls -l /usr/local/bin/lighthouse
```

**なぜ打つか。** バイナリの持ち主と、権限を確かめる。

```
-rwxr-xr-x 1 root root 105018160 Oct 25 01:58 /usr/local/bin/lighthouse
```

| 表示 | 意味 |
|---|---|
| `-rwxr-xr-x` | 権限（755）。持ち主は、読み・書き・実行。ほかは、読み・実行 |
| `root root` | 持ち主と、グループ |
| `Oct 25 01:58` | 最後に書き換わった時刻（UTC）。日本時間では10:58。入れ替えの作業の時刻と合う |

`root root`の755で、入れ替えの前と同じ状態だった。**`cp`の上書きでは、持ち主と権限が、そのまま残る**と確認できた。

次に、サービスを**動かすユーザー**を確かめた。

```bash
systemctl show geth lighthouse lighthouse-vc mev-boost -p Id -p User
```

**なぜ打つか。** サービスごとに、どのユーザーの権限で動いているかを表示する。`-p Id -p User`は、「名前と、ユーザーだけを見せる」という指定である。

```
User=ethereum
Id=geth.service

User=ethereum
Id=lighthouse.service

User=ethereum
Id=lighthouse-vc.service

User=ethereum
Id=mev-boost.service
```

| 表示 | 意味 |
|---|---|
| `User=ethereum` | このサービスは、`ethereum`という一般ユーザーの権限で動く |
| `Id=…service` | サービスの名前 |
| 空行 | サービスの区切り |

> 💡 **表示の順番は、指定した順番ではない。** `Id`を先に書いても、`User`が先に出た。ソフトが決めた順番で出るので、気にしなくてよい。

> 💡 **「持ち主」と「動かすユーザー」は、別の話である。** 持ち主（`root`）は、バイナリを**書き換えられる**人。動かすユーザー（`ethereum`）は、プログラムが**動くときの権限**。`ethereum`は、バイナリを実行できても、書き換えはできない。そのため、万が一、サービスが乗っ取られても、バイナリ自体は改ざんされない（第12章の4-2）。

### 5-6. 退避したファイルの扱い

退避した`lighthouse-v8.2.2.bak`は、**すぐには消さない。** 数日から2週間ほど、安定して動くのを確かめてから、削除する（第12章の「今後の課題」と同じ）。解凍した`lighthouse`、ダウンロードした`.tar.gz`と`.asc`は、数日後に消す。

**なぜ打つか。** `-b -1`は、「1つ前の起動（再起動の前）」の記録、という指定である。署名役は、停止の最初に止まるので、**停止の時刻**が、ここに残っている。`-u`はサービスの指定、`-n 6`は、最後の6行だけ、という指定である。

Oct 25 01:56:18 <host> systemd[1]: Stopping lighthouse-vc.service - Lighthouse Validator Client (Mainnet)...
Oct 25 01:56:18 <host> lighthouse[978]: … INFO  Shutting down..  reason: Success("Received SIGTERM")

| 表示 | 意味 |
|---|---|

| Head | 1,561 / 14 | 14票の遅れ。6に、通常の揺れ（約8票）が加わった形 |
| Att. Efficiency | 99.49% | 良好 |
| Slashings | 0 | 問題なし |

**検算**：1,569 + 6 ＝ 1,575、1,561 + 14 ＝ 1,575。合計が、7日分と一致する。

### 9-3. 欠測の内訳：6 ＝ 3 ＋ 3

| 更新 | 停止から再開まで | 欠測 |
|---|---|---|
| 前回（第5章） | 約21分 | 3エポック |
| 今回 | 約23分 | 3エポック |
| 合計 | | **6**（画面の数字と一致） |

前回と今回の間は、毎日の画面が、225 / 0（見逃しゼロ）だった。**6のうち、更新の停止以外の欠測は、入っていない。**

**エポックの番号でも、3になる。** 停止したエポックを `N` とする。再開後の最初の署名は、`N+4`のエポックだった。その間の `N+1`、`N+2`、`N+3` の3エポックが、欠測である。

> 💡 **欠測の数は、時間の長さではなく、自分の番が何回あったかで決まる。** 今回の停止は、前回より、約2分長かった。それでも、欠測は、同じ3エポックだった（第5章の6-3）。

### 9-4. どの窓で、何を見るか

| 見る窓 | 目的 |
|---|---|
| 24時間 | 毎朝の確認。今日の状態 |
| 7日 | 更新の影響の確認。複数回の更新を、並べて比べる |

**更新のあとは、毎朝の24時間の数字を見たうえで、翌日以降に、7日の窓も、1回見る。** 7日の窓も、1週間たつと、欠測が外れる。**気づいたことは、手元に記録しておく。**

> ⚠️ 画面には、報酬の金額も写っている。**公開する記録には、使わない**（これまでの章と同じ方針）。エポック番号も、そのままは載せない。

## 10. 失敗談：手動のソフトの新しい版に、気づけていなかった

| | 内容 |
|---|---|
| きっかけ | 10月に、セキュリティ事故のニュースが続いた。「このサーバーに影響はあるのか」を確かめるため、サーバーのソフトを棚卸した |
| 気づいたこと | 7つのソフトのうち、4つが、aptの管理外だった。版を公式のリリースページと見比べると、Lighthouseが、v8.2.2のままだった。公式には、v8.2.3、v8.3.0、v8.3.1と、新しい版が出ていた |
| 原因 | gethは、aptで更新が一覧に出る。Lighthouseは、**自分で取りに行くしかない**。**自分で見張る仕組みがなく、更新の連絡は、コミュニティからの知らせに頼っていた**（第4部 第12章では、コミュニティのDiscordの連絡で、更新できた） |
| もう1つの見落とし | AIアシスタント（Claude）に調べてもらったときも、検索の要約だけで、最新版を見落としかけた。公式のリリースページを、直接見る習慣にした（3節） |
| 対策 | GitHubのReleases通知を、設定した（2節）。公式のリリースページを、直接読む（3節） |
| 学び | ニュースは、棚卸を始める、よい合図になる。ただし、**ニュースや、人からの連絡が出てから動く**のでは、遅れる。手動のソフトには、連絡がなくても気づける仕組みを、作っておく |

> 💡 この失敗は、運が悪かったのではなく、**自分で見張る仕組みがなかった**ために起きた。第4部 第12章（7月）では、コミュニティの連絡を受けて、Lighthouseを更新できた。今回は、その連絡ではなく、ニュースをきっかけに、自分で棚卸して、気づいた。次は、ニュースや連絡がなくても、気づけるようにする。

## まとめ

```
① 更新には、aptで入るものと、手で入れるものの2種類がある。
   「保留中の更新は0件」でも、手動のソフトに新しい版がないとは限らない
② 手動かどうかは、置き場所（/usr/local/bin）と、dpkg -S で分かる
③ 手動のソフトは、GitHubのReleases通知で見張る。
   版は、ソフト自身に聞いて、公式のリリースページと見比べる
④ 公式のリリースページは、検索の要約ではなく、直接読む。
   Summary、Upgrade Notes、Update Priority、Known Issues の順
⑤ 優先度の表は、「その版で新しく直った分」の表。
   版を飛ばして上げるときは、間の版の案内も読む
⑥ 署名の確認は、ひとつの確認。正規の経路から出たものは、
   見た目では区別できないので、リリースノートや動作確認と組み合わせる
⑦ 入れ替える前に、解凍した新しい版で、版の表示を試して、実行できるかを
   確かめる。長い命令は、&&でつないで、1行で打つ
⑧ 持ち主（root）と、動かすユーザー（ethereum）は別の話。
   cp の上書きでは、持ち主と権限が残る
⑨ 戻すには、データベースを先に戻す必要がある場合がある。
   退避したバイナリだけでは、戻せないことがある
⑩ 時刻は、計算より、ログ。停止から再起動、最初の署名までを、
   前回と同じ区間で比べる
⑪ 通知は、2回とも、停止の約16分後に鳴った。復旧は、再開の10〜12分後
⑫ 欠測は、24時間の窓だと翌日に消える。更新の影響は、7日の窓でも見る
```

この章で、いちばん学んだのは、**ニュースがきっかけで、気づいた**ことだった。手動のソフトは、自分から見に行かない限り、新しい版に気づけない。気づくための仕組み（Releases通知）を作り、公式のページを直接読む習慣にした。

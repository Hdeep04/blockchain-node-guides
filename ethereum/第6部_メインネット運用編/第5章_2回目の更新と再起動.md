| 実施日 | 2026年10月20日 |
| 対象 | geth 1.17.8、カーネル 6.8.0-147、grafana、tailscale ほか |

## はじめに：同じ手順でも、2回目に出てきたこと

第3章で、初めての更新と再起動の手順を決めた。「中身を見てから、止める」「署名役から順に止める」「`-y`を付けず、画面で確かめる」である。

2回目は、同じ手順で進めた。大筋は、前回と同じだった。ただ、**前回になかったことが、4つ出てきた。**

1. 手を入れていないのに、カーネルが入っていた。
2. 更新の一部を、別の作業に分けた。
3. 停止の待ち時間を変えるために、これまでと違う方法で設定を直した。そして、1回目は反映されなかった。
4. 署名が止まっていた時間を、前回と比べたが、比べ方が、そろっていなかった。

本章は、その前回との差の記録である。アラートの動きは、第4章で扱った。

## 1. 更新の中身：手を入れていないのに、カーネルが入っていた

更新の前に、中身を見る（第3章の1節）。

```bash
apt list --upgradable
```

**なぜ打つか。** 保留中の更新の、パッケージ名と、新旧の版を見る。`node_check`の件数だけでは、何が入るのか分からない。

### 1-1. 件数の動き

| 日付 | 保留中の更新 | 主な内容 |
|---|---|---|
| 10/14 | 14件 | gethの一式（5）、カーネル（5）、tailscale、open-iscsi（2）、sosreport |
| 10/16 | 14件 | カーネルが消え、apparmor（2）、tzdata（2）、open-vm-tools が加わった |
| 10/20 朝 | 16件 | grafana、snapd が加わった |
| 10/20 作業の直前 | 18件 | git、git-man が加わった。tailscale を含む |

6日の間にも、更新は、少しずつ増えた。**作業の直前に、もう一度、中身を見る**のは、そのためである。朝の一覧と、作業の直前の一覧が、同じとは限らない。

### 1-2. 手を入れていないカーネル

10/14の一覧には、カーネル（6.8.0-146 → 147）が入っていた。更新はせず、様子を見ることにした。ところが、10/15の朝、`node_check`の再起動の欄が、**NO から YES に変わっていた。**

```bash
cat /var/run/reboot-required.pkgs
```

**なぜ打つか。** Ubuntuは、再起動が必要になったとき、その原因のパッケージ名を、このファイルに書き残す。

```
linux-image-6.8.0-147-generic
linux-base
```

原因は、カーネルだった。自分では更新していないので、Ubuntuの自動のセキュリティ更新が入れたと見ている。ただし、自動更新の設定は、確認していない。

> 💡 **「更新しない」と決めても、入るものがある。** カーネルは、入れただけでは、動いているカーネルは切り替わらない。再起動して、初めて切り替わる。だから、「入っている」のに「古いカーネルで動いている」状態が、再起動までの間、続く。

「再起動が必要」の表示が出たあとは、緊急性を見て、日を決めた。このカーネルは、通常の定期的な更新で、緊急の告知は、見つからなかった。そこで、geth 1.17.8の更新と、**1回の作業にまとめる**ことにした。再起動を1回にすれば、署名の欠測も1回で済む。

## 2. 更新を「分ける」：tailscale を別の作業にした

保留中の更新には、tailscale（1.102.4 → 1.104.1）が入っていた。tailscaleは、サーバーに入るための道（SSH）を支えるソフトである。これを更新すると、その最中に、SSHが一瞬切れる可能性がある。

**署名を止めている最中に、サーバーに入れなくなる。** これが、いちばん避けたい状態である。そこで、tailscaleだけを、別の作業に分けた。

```bash
sudo apt-mark hold tailscale
```

**なぜ打つか。** `apt-mark hold`は、パッケージに「更新しない」という印を付ける。この印があると、`apt upgrade`は、そのパッケージを飛ばす。

```
tailscale set on hold.
```

### 2-1. 確認の画面での見え方

更新の確認画面（4節）に、次の表示が出た。

```
The following packages have been kept back:
  tailscale
...
17 upgraded, 0 newly installed, 0 to remove and 1 not upgraded.
```

| 表示 | 意味 |
|---|---|
| `kept back`（tailscale） | 印が効いて、飛ばされた |
| `17 upgraded` | 更新されるのは17件。tailscaleは含まれない |
| `1 not upgraded` | 更新されなかったのが1件。この1件が、tailscale |
| `0 to remove` | 削除されるものは、ない（第3章と同じ確認） |

> 💡 **`kept back`と`deferred due to phasing`は、別物である。** 第3章のsosreportは、Ubuntuが更新を段階的に配っていて、順番が来ていないために、保留された（phasing）。今回のtailscaleは、自分で付けた印のために、保留された。表示の言葉が違う。

### 2-2. 外し忘れに注意

印を付けたままにすると、tailscaleは、ずっと更新されない。別の作業で更新する前に、印を外す（8節）。**付けたら、外す日を決める。** 今回は、同じ日の、署名が安定したあとに、外した。

grafanaも、別の作業にする案を考えた。通知の仕組みの本体だからである。しかし、更新に含めて、更新のあとに、通知が届くかを確かめる形にした。結果は、第4章で扱ったとおり、通知は届いた。

## 3. 今までと違うやり方：上書き用ファイル

この作業の前に、gethの「停止の待ち時間」を、既定の90秒から、10分（600秒）に延ばした。gethは、止める合図を受けると、メモリ上のデータをディスクに書き出して、終わろうとする。この書き出しが、90秒で終わらないと、強制的に止められる。強制停止になると、次の起動で、データの確認に時間がかかるおそれがある。待ち時間は、あくまで「上限」で、早く終われば、すぐに止まる。

### 3-1. これまでの方法と、今回の方法

| | これまで | 今回 |
|---|---|---|
| 方法 | `sudo vi /etc/systemd/system/geth.service`で、設定ファイルの**本体を直接**書き換える | `sudo systemctl edit geth`で、**上書き用の小さなファイル**（`override.conf`）を追加する |
| 元のファイル | 書き換わる | そのまま残る |
| 元に戻すとき | 書き換えた行を、手で戻す | `override.conf`を消せば戻る |
| 読み込み直し（`daemon-reload`） | 自分で打つ | 保存して閉じると、自動で行われる |

どちらも、正しい方法である。上書き用ファイルは、元に戻しやすい。

> 💡 **用語：drop-in（上書き用ファイル）。** systemdは、`geth.service.d/`というフォルダの中のファイルを、本体の設定に**重ねて**読む。本体は、そのまま残る。

### 3-2. 1回目：反映されなかった

最初は、systemctl edit geth を打った。既定のエディタ（nano）が開いたが、慣れていないので、閉じて、viで開き直した（コマンドは3-3）。viでは、次の説明が出た。

```
### Anything between here and the comment below will become the contents of the drop-in file
（この間に書いた内容が、上書き用ファイルになる）
### Edits below this comment will be discarded
（この下に書いた内容は、捨てられる）
```

入れた2行（`[Service]`と`TimeoutStopSec=600`）を、**いちばん下**に書いて保存した。反映されているかを確かめた。

```bash
systemctl show geth -p TimeoutStopUSec
```

**なぜ打つか。** `systemctl show`は、systemdが**いま覚えている値**を表示する。ファイルに書いただけでなく、systemdがその値を読み込んだことまで確かめられる。

```
TimeoutStopUSec=1min 30s
```

90秒のままだった。続けて、設定の全体を表示した。

```bash
systemctl cat geth
```

**なぜ打つか。** 設定ファイルと、上書き用ファイルの中身を、続けて表示する。上書き用ファイルがあれば、`# /etc/systemd/system/geth.service.d/override.conf`という見出しが出る。

見出しは、出なかった。**入れた内容は、保存されていなかった。** 「この下に書いた内容は、捨てられる」の下に書いたためである。

この前後に、nanoを閉じる操作の途中で、ホームに、コマンドの一部を名前にした、誤ったファイルが1つできた。中身は、設定ファイルの写しで、秘密の情報は入っていなかった。確認して、削除した。原因は、確認していない。

### 3-3. 2回目：viで、説明行の間に書く

1回目と同じ、viで開き直した。今回は、説明行の間に書く。

```bash
sudo EDITOR=vi systemctl edit geth
```

**なぜ打つか。** `EDITOR=vi`は、「このコマンドだけ、エディタにviを使う」という指定である。普段のエディタの設定は、変わらない。

viには、「見るモード」と「入力するモード」がある。次の順に操作した。

1. 開いた直後は、見るモード。`j`を2回押して、2つの説明行の間の空行まで下がる。
2. `i`を押して、入力するモードにする（左下に`-- INSERT --`と出る）。
3. 2行を入力する。
4. `Esc`を押して、入力するモードを終える。
5. `:wq`と打って、Enterを押す（`w`は保存、`q`は終了）。

間違えたときは、`Esc`のあとに`:q!`で、保存せずに閉じられる。

```
Successfully installed edited file '/etc/systemd/system/geth.service.d/override.conf'.
```

### 3-4. 確かめる

`systemctl cat geth`の最後に、次の見出しと中身が出た。

```
# /etc/systemd/system/geth.service.d/override.conf
[Service]
TimeoutStopSec=600
```

```bash
systemctl show geth -p TimeoutStopUSec
```

```
TimeoutStopUSec=10min
```

600秒が、反映された。

> 💡 **「起動しているから、直接直せないのか」という疑問。** 起動中でも、本体の直接編集はできる。どちらの方法でも、設定を読み込み直す操作が要る。そして、**起動中のgethには、影響しない。** 新しい待ち時間は、次に止めるときから使われる。

> 💡 **確かめるときは、2つのコマンドを使い分ける。** 見出しの有無で「ファイルが入っているか」を見るのが`systemctl cat`、値で「systemdが読み込んだか」を見るのが`systemctl show`である。今回、1回目は、両方で、反映されていないと分かった。

## 4. 止める・更新する・再起動する：第3章との差分

手順は、第3章と同じである。ここでは、差分だけを書く。

### 4-1. 更新の前の確認

第3章と同じく、4つのサービスが、再起動後に自動で立ち上がる設定かを確かめた。

```bash
systemctl is-enabled geth lighthouse mev-boost lighthouse-vc
```

結果は、4つとも`enabled`だった。更新の中身（1節）は、直前にもう一度見た。

### 4-2. 通知は、止めなかった

第4章の7節のとおり、Grafanaの通知は、止めなかった。作業の前に、Contact pointの「Test」で、通知の経路だけを確かめた。

### 4-3. 止める

```bash
node_stop
```

第3章と同じスクリプトである。止める前に、ブロック提案の予定を確かめる。

```
 現在のスロット: <slot>（エポック: <epoch>）
 ✓ 現在のエポックにブロック提案の予定はありません。安全に停止できます。
```

4つとも`inactive (Safe)`になった。停止の正確な時刻は、表示を控えていないので、通知の時刻（11:05）からの逆算で、**11:03ごろ**とする。

### 4-4. 更新する

```bash
sudo apt upgrade
```

`-y`は付けず、確認の画面を見た。

```
The following packages have been kept back:
  tailscale
...
17 upgraded, 0 newly installed, 0 to remove and 1 not upgraded.
Need to get 459 MB/464 MB of archives.
```

| 前回との差 | 内容 |
|---|---|
| `newly installed`が0 | 前回（第3章）は、新しいカーネルが7件、新規に入った。今回は、カーネルがすでに入っているので、0 |
| `kept back` | 2節の印の効果 |
| `0 to remove` | 前回と同じ。削除されるものはない |

更新の最中の表示は、次のとおりだった。

- **`apparmor.postinst: 148: [: Illegal number: yes`**：前回（第3章の5-2）と**同じ警告**が、また出た。直後に`Reloading AppArmor profiles`と続き、処理は進んだ。2回続けて出ているので、この環境では、更新のたびに出る警告のようである。原因は、調べていない。
- **grafanaは、更新の中で、自動的に再起動された**（`Restarting grafana-server service... OK`）。前回と同じである。
- **`Generating /boot/initrd.img-6.8.0-147-generic`**：新しいカーネル（147）の、起動用のファイルが作られた。
- **needrestart**が、再起動すべきサービスの一覧を表示した。これから、サーバー全体を再起動するので、1つずつ手で再起動する必要はない。

### 4-5. 再起動する

```bash
sudo systemctl reboot
```

再起動の予告の表示は、UTCの02:06:48（JSTの11:06:48）だった。SSHは、ここで切れた。予定どおりの動きである。

## 5. 再起動後の確認

SSHが切れたので、数分待ってから、再接続した（前回と同じ）。

### 5-1. 新しいカーネルで起動したか、サービスは立ち上がったか

```bash
uname -r
systemctl is-active geth lighthouse mev-boost lighthouse-vc
geth version | head -3
```

**なぜ打つか。** パッケージを入れただけでは、動いているものが新しい版とは限らない。再起動のあとに、実際に動いているカーネルとgethの版を確かめる。`is-active`は、サービスが、いま動いているかを調べる（4-1の`is-enabled`は、自動で起動する**設定**かを見た）。

```
6.8.0-147-generic
active
active
active
active
Version: 1.17.8-stable
```

新しいカーネル（147）で起動し、4つのサービスが自動で立ち上がり、gethは1.17.8になった。

### 5-2. `node_check`で見る

| 項目 | 更新前（10:42） | 再起動の直後（11:09） | 署名の再開後（11:28） |
|---|---|---|---|
| 4つのサービス | active | active | active |
| sync_distance | 0 | 0 | 0 |
| ピア（Lighthouse / Geth） | 206 / 50 | 82 / 34 | 193 / 45 |
| メモリ使用 | 20Gi | 11Gi | 9.3Gi |
| Swap | 5.7Gi | 0B | 0B |
| 直近の署名（[5]） | あり | **空** | 11:24:26の署名 |
| 再起動の要否 | YES | NO | NO |
| 保留中の更新 | 16件 | 0件 | 0件 |
| ディスクの空き | 363G | 369G | 369G |

- **[5]が空**なのは、異常ではない。署名役が、署名せずに、様子見の最中だからである（次の節）。
- **ピア数**は、再起動の直後に減り、20分ほどで、元に近い水準に戻った。
- **メモリとSwap**は、再起動でリセットされた（前回と同じ）。
- **ディスクの空き**は、再起動のあとに増えた。前回（383G → 388G）も同じ動きだった。原因は、調べていない。
- **保留中の更新が0件**なのは、tailscaleに「更新しない」印を付けているためである。8節で、別に更新する。

### 5-3. 署名役の様子見

```bash
journalctl -u lighthouse-vc --no-pager -n 15
```

**なぜ打つか。** 署名役のログの、最新の15行を見て、様子見（Doppelganger Protection）の最中かを確かめる。

| ログの行 | 意味 |
|---|---|
| `Connected to beacon node(s) ... synced: 1` | 署名役が、ビーコンノードにつながっていて、同期済みと確認している |
| `Listening for doppelgangers ... doppelganger_detecting_validators: 1` | 「同じ鍵で、別の場所から署名している者がいないか」を、聞き耳を立てて確認中 |
| `All validators inactive` | 確認が終わるまで、署名を出さずに待っている（`inactive`は、鍵が無効という意味ではない） |

二重署名（スラッシング）を防ぐための安全装置で、**この間に署名しないのが、正しい動作**である。

### 5-4. 署名の再開

```bash
journalctl -u lighthouse-vc --no-pager -n 100 | grep "Successfully published attestations" | tail -n 3
```

**なぜ打つか。** 署名の成功ログだけを抜き出す。1行でも出れば、再開している。ログの時刻はUTCなので、JSTは9時間進める。

最初の署名は、UTCの02:24:26（JSTの11:24:26）だった。第4章のとおり、Telegramの復旧の通知は、その約10分後に届いた。署名の再開は、通知ではなく、ログで判断した。

## 6. 署名が止まっていた時間：前回との比較

結論から言うと、今回の途切れは、前回より少し短く、欠測のエポック数は同じ3だった。ただし、比べるときに、測る区間（どこからどこまで）をそろえる必要があった。

### 6-1. 前回の数字と、そのまま比べられない

第3章に、「署名の途切れは約30分37秒」と書いた。今回の途切れは、約21分である。並べると、今回のほうが、約9分短いように見える。

しかし、この2つの数字は、**測り始めの時刻が違う**。

| | どこから | どこまで | 結果 |
|---|---|---|---|
| 第3章（10/2） | 更新前の**最後の署名** | 再開後の**最初の署名** | 約30分37秒 |
| 今回（10/20） | **停止（`node_stop`）の時刻** | 再開後の**最初の署名** | 約21分 |

第3章は、止める前の最後の署名から測っている。今回は、止めた時刻から測っている。**最後の署名から、止めるまでの間にも、時間がある**（前回は約7分）。だから、第3章の数字のほうが、長く出る。

今回は、更新前の最後の署名の時刻を、控えていない。だから、第3章の測り方では、今回を測れない。そこで、前回の記録を、今回と同じ測り方（停止から最初の署名まで）にそろえて、比べた。

### 6-2. 測る区間をそろえた比較

| 項目 | 10/2（第3章） | 10/20（今回） |
|---|---|---|
| 停止（`node_stop`） | 22:19ごろ | 11:03ごろ |
| 再起動 | 22:22（旧カーネルの終了） | 11:06:48（コマンド） |
| 最初の署名 | 22:42:37 | 11:24:26 |
| **停止から最初の署名まで** | 約24分 | 約21分 |
| **再起動から最初の署名まで** | 約21分 | 約18分 |
| 欠測のエポック | 3 | 3 |

- 今回の停止の時刻は、通知の時刻（11:05）からの逆算である。「ごろ」と付けているのは、そのためである。
- 前回の「停止から最初の署名まで」は、22:19ごろから22:42:37までで、約24分になる。今回は、約21分。**3分ほど、短かった。**

### 6-3. 欠測は、同じ3エポック

署名は、1エポック（約6.4分）に1回である。止まっていた時間の長さではなく、**その間に、自分の番が何回あったか**で、欠測の数が決まる。

beaconcha.inのSummary（直近24時間）を、作業の約50分後（11:56）に見た。

| 項目 | 10/3朝（前回） | 10/20 11:56（今回） |
|---|---|---|
| Source | 222 / 3 | 222 / 3 |
| Target | 222 / 3 | 222 / 3 |
| Head | 221 / 4 | 219 / 6 |
| Att. Efficiency | 98.56% | 98.33% |
| Missed rewards | 0.000027 ETH | 0.000031 ETH |

SourceとTargetの3票は、欠測の3エポックと一致する。Headが、前回より2票多いのは、普段の揺れ（1日に1〜3票）の範囲だと見ている。

> 💡 この表の今回の列は、作業の約50分後の値である。翌朝の確定値は、9節で見る。

### 6-4. 学び：比べる前に、「どこから、どこまで」をそろえる

| | 内容 |
|---|---|
| 起きたこと | 第3章の「約30分37秒」と、今回の「約21分」を並べると、今回のほうが、約9分短く見えた |
| 原因 | 測り始めが違った。第3章は「止める前の最後の署名」から、今回は「止めた時刻」から測っていた。この2つの間には、約7分ある |
| そろえると | 前回も「止めた時刻から、最初の署名まで」で測ると、約24分。今回は約21分。**差は、約3分** |
| 学び | 数字を比べる前に、**「どこから、どこまで」をそろえる**。そろえないと、差が、実際の3倍ほどに見える |
| 次回のために | 作業の前に、直近の署名の時刻を、1回控えておく。そうすれば、第3章の測り方でも、今回の測り方でも、比べられる |

## 7. 作業のあとの確認：入口が増えていないか

署名が再開したあと、第6部 第2章の「作業のあと」の確認を行った。更新や設定の変更のあとに、**外から入れる入口が、増えたり変わったりしていないか**を見る。今回は、grafanaやsnapdなども更新したので、確かめる意味があった。

```bash
sudo ss -tlnp
```

**なぜ打つか。** `ss -tlnp`は、サーバーが、どの入口で、外からの接続を待ち受けているかを、一覧にする。`sudo`を付けると、どのプログラムが待ち受けているかも出る。

```bash
sudo ufw status verbose
```

**なぜ打つか。** UFWは、入口の「門番」である。どの入口を許可しているかを、確かめる。

基準値（第2章）は、外に開いているのが**9000、30303、22、3000だけ**で、ほかは`127.0.0.1`（サーバー自身）だけで待ち受けている、というものだった。

### 7-1. `ss`の結果

| 待ち受け | 状態 | 見方 |
|---|---|---|
| 22（sshd） | 全体向け（`0.0.0.0`と`[::]`） | 基準どおり。誰が入れるかは、UFWが決める |
| 3000（grafana） | 全体向け（`*`） | 基準どおり |
| 9000（lighthouse）、30303（geth） | 全体向け | 基準どおり。ブロックチェーンのネットワークとつながる入口 |
| 6060、5064、5062、5052、5054、18550、9100、9090、8545、8546、8551 | すべて`127.0.0.1` | サーバー自身からだけ。外から触れない |
| tailscaledの高い番号、systemd-resolvedの53 | Tailscale自身の入口、名前解決の内部の入口 | 想定内 |

**新しい番号は、見当たらなかった。**

### 7-2. UFWの結果

| 表示 | 意味 |
|---|---|
| `Status: active` | 門番が動いている |
| `Default: deny (incoming)` | 許可していない着信は、すべて拒否 |
| `22/tcp on tailscale0` | SSHは、Tailscaleの経路からだけ許可 |
| `30303`、`9000`（tcpとudp） | gethとlighthouseの入口。どこからでも許可 |
| `(v6)`の行 | 同じルールの、IPv6版 |

3000（Grafana）は、UFWの許可の一覧にない。Grafanaは、Tailscale経由で使っており、基準値（第2章）と同じ状態だった。

> 💡 **`ss`と`ufw`は、組み合わせて読む。** `ss`は「待ち受けている入口」、`ufw`は「通してよい入口」を示す。全体向けに開いている入口が、UFWの許可と、基準値の両方に合っていれば、増えていない。

## 8. Tailscaleの更新：別の作業として

署名が安定したあと、別の作業として、tailscaleを更新した。正確な時刻は、控えていない。

### 8-1. 準備

サーバーにモニターとキーボードをつなげる状態か、ログインのパスワードが分かるかを、先に確かめた。万が一、Tailscaleが戻らなくなったときの、最後の手段である。tmuxは、使わなかった。これまでの更新で、SSHが切れたことがなかったためである。

### 8-2. 更新

```bash
sudo apt-mark unhold tailscale
```

**なぜ打つか。** 2節で付けた「更新しない」印を、外す。

```
Canceled hold on tailscale.
```

```bash
sudo apt install --only-upgrade tailscale
```

**なぜ打つか。** `--only-upgrade`は、「すでに入っているものだけを、新しい版に更新する」という指定である。ほかのパッケージには、触れない。

```
1 upgraded, 0 newly installed, 0 to remove and 0 not upgraded.
...
No services need to be restarted.
```

`0 to remove`と`0 not upgraded`を確かめてから、進めた。**SSHは、切れなかった。**

### 8-3. 予想が外れた

「tailscaleを更新すると、SSHが一瞬切れる」と予想して、作業を分けた。実際は、切れなかった。理由は、確認していない。一瞬だけ止まって、SSHの接続が持ちこたえたのかもしれない。

**予想が外れても、分けた判断は、間違いではない。** 切れる可能性が、あるかないかは、やってみるまで分からなかった。署名を止めている最中に、入れなくなる危険を避けられた。

### 8-4. 版を確かめる：クライアントと常駐は別

```bash
tailscale version
```

```
1.104.1
  tailscale commit: ...
  long version: 1.104.1-...
```

これは、コマンド側（クライアント）の版である。**動いている常駐側の版は、出ていない。**

```bash
tailscale version --daemon
```

**なぜ打つか。** `--daemon`を付けると、いま実際に動いている常駐プログラム（tailscaled）の版も、表示される。更新のあと、常駐側が再起動されず、古い版のまま動いていることもあるため、ここで確かめる。

```
Client: 1.104.1
  ...
Daemon: 1.104.1-t7f4efe814-g8da26756c
```

クライアントと常駐の、両方が1.104.1だった。

```bash
tailscale status
```

**なぜ打つか。** 更新のあとも、tailnet（自分の端末のつながり）が保たれているかを確かめる。第2章の基準値は、3台（PC、Mac、サーバー）である。3台が見えた。

> 💡 **版の確認は、2段階で行う。** 最初の`tailscale version`だけでは、常駐側の版が分からない。今回、私は「`daemon version`も出る」と思い込んでいた。出力に、その行はなかった。**出力を見て、思い込みに気づけた。**

## まとめ

```
① 同じ手順でも、2回目に、新しく出てくることがある。更新の中身は、
   作業の直前に、もう一度見る（6日で、14件から18件に増えた）
② 「更新しない」と決めても、カーネルのように、自動で入るものがある。
   入っても、再起動するまでは、古いカーネルで動いている

⑤ 反映の確認は、2つのコマンドで行う。systemctl catは「ファイルが
   あるか」、systemctl showは「systemdが読み込んだか」
⑥ 前回の数字と比べるときは、測る区間（どこからどこまで）をそろえる。更新の前の最後の署名の
   時刻を、作業の前に控えておく
⑦ 署名の途切れは、停止から約21分、再起動から約18分。欠測は、前回と

   クライアントと常駐の、2段階で確かめる
```

2回目で、いちばん学んだのは、手順よりも、**比べ方**だった。前回の数字を、そのまま今回と比べると、今回のほうが短く見えた。しかし、数え始めの時刻が違っていた。比べる前に、同じ区間（どこからどこまで）を測ったものかを確かめる。そして、次の作業のために、直近の署名の時刻を、控えておく。

## はじめに：ニュースは毎回違うが、確認の順番は同じ

2026年10月、ソフトウェアのセキュリティ事故が、立て続けにニュースになった。第6章では、そのうち「手動のソフトの更新」を扱った。本章は、その続きである。

ニュースの見出しは、毎回違う。「緊急パッチ」「重大な脆弱性」「深刻度9.8」。見出しが強いほど、焦る。しかし、**確認の順番は、毎回、同じ3つの質問**で足りる。本章では、その3つの質問と、結果の残し方（3点セット）を、実際に動かした記録で示す。

## 1. 3つの質問

| # | 質問 | 知りたいこと | 確かめる道具 |
|---|---|---|---|
| 1 | **入っているか** | そのソフトや部品が、このサーバーに入っているか。入っていれば、どの版か | `which`、`dpkg -l`、`--version`、`uname -r` |
| 2 | **外から届くか** | インターネットから、そのソフトに、通信が届くか | `ss -tlnp`、`ufw status verbose` |
| 3 | **直す方法が出ているか** | 修正版や、回避策が出ているか。出ているなら、自分の環境に届いているか | 公式のページ、`apt list --upgradable` |

**3つの答えが、そろって初めて、必要な対応が決まる。** 見出しの強さ（Critical、9.8）では、決めない。

### 1-1. 質問1「入っているか」

```bash
uname -r
cat /etc/os-release
```

**なぜ打つか。** カーネルの脆弱性のニュースが出た。まず、「自分のサーバーのカーネルは、何か」を知る必要がある。`uname -r`は、いま動いているカーネルの版を表示する。`/etc/os-release`は、OSの名前と版を表示する。

**読み方。**

- `6.8.0-147-generic` のように出れば、Ubuntu 24.04の標準カーネルである。公式のページは、OSの版ごとに、行が分かれている。**自分の版の行を見る**。
- `6.8.0-` で始まらない場合は、別の系統（HWEなど）で、公式のページの行も、別になる。

> 💡 「入っていない」を確かめるときは、**何も出ない**ことが、証拠にならない場合がある（エラーを隠していないか、絞り込みの条件が、正しいか）。節2で、確かめ方を示す。

### 1-2. 質問2「外から届くか」

```bash
sudo ss -tlnp | grep -v "127.0.0"
sudo ufw status verbose
```

**なぜ打つか。** 入っていても、外から届かないなら、緊急度は下がる。`ss -tlnp`は、待ち受けている通信の一覧で、`grep -v "127.0.0"`は、**サーバーの内側だけ**の待ち受けを、除く。`ufw status verbose`は、ファイアウォールが、何を許可しているかを表示する。

**読み方。**

| 見るもの | 意味 |
|---|---|
| `*:30303`、`0.0.0.0:9000` | 外からも届き得る待ち受け（P2Pのポート） |
| `22` が `tailscale0` 経由だけ許可 | SSHは、Tailscaleの中だけ。インターネット側からは届かない |
| 許可の行にないポート（例：監視の画面） | ファイアウォールが遮断。外からは届かない |

**この環境の答え。** 外から届くのは、ファイアウォールが許可したP2Pの2つのポート（30303、9000）だけだった。

### 1-3. 質問3「直す方法が出ているか」

```bash
apt list --upgradable 2>/dev/null | grep linux-image
```

**なぜ打つか。** 修正版のカーネルが、**自分の環境に届いたか**を見る。公式のページが「修正版あり」と書いても、aptに出るのは、別の話である。

**読み方。** 何も出なければ、カーネルの更新は、まだ届いていない。`linux-image-…` の行が出て、版が、公式のページの修正版以上なら、届いている。

> ⚠️ **「出ている」と「届いた」は、別。** 公式の試験用の置き場（`-proposed`）に出ても、通常の更新には、まだ出ない。確かめるのは、公式のページと、自分のサーバーの、両方である。

### 1-4. 答えの組み合わせで、対応が決まる（目安）

| 質問1 入っているか | 質問2 外から届くか | 質問3 直す方法 | 対応 |
|---|---|---|---|
| いいえ | — | — | 対応なし。証拠を残す |
| はい | いいえ | — | 緊急度は低い。通常の更新で足りる |
| はい | はい | まだ届かない | 暫定処置と、見張り（毎朝、更新欄を見る） |
| はい | はい | 届いた | 更新する（再起動が要るかを確かめる） |

### 1-5. 結果の残し方：3点セット

ニュースごとに、**リスク（自分に当てはまるか）、対策（何をしたか）、証拠（コマンドの出力と日付）**を、1行ずつ残す。

| ニュース | リスク | 対策 | 証拠 |
|---|---|---|---|
| カーネルの脆弱性 | 外から届くP2Pのポートで、対象のカーネルが動いていた | 暫定処置を入れ、修正版が届いたら更新 | 公式ページのStatus、`uname -r`、日付 |

**なぜ残すか。** あとで、「あのとき、何を確かめたか」を、思い出せるようにするため。秘密は、含めない（番号、IP、残高は、書かない）。

## 2. 「入っていない」を、コマンドで確かめる

要点：「入っていない」は、**何も出ないこと**では、確かめられない。2つの方法で確かめ、**結果と日付**を残す。

### 2-1. 何を確かめるか

2026年10月21日ごろ、PHPの緊急セキュリティリリースが、ニュースになった。質問1（入っているか）の答えは、**このサーバーに、PHPが入っているか**である。

### 2-2. 確かめる

```bash
for c in php node nodejs gitlab-ctl; do echo "== $c : $(command -v $c || echo 見つからない)"; done; dpkg -l | awk '/^ii/ && $2 ~ /^(php|nodejs|gitlab)/ {print $2, $3}' | head -5; echo "（以上）"
```

**なぜ、この1行か。**

| 部分 | 何をするか | なぜ要るか |
|---|---|---|
| `command -v php` | `php`というコマンドが、**実行できる場所**にあるかを探す | 入れ方に関わらず、実行できるかが分かる |
| `dpkg -l` と `awk` | aptで入れたパッケージのうち、名前が`php`などで始まるものを探す | 入れた記録が残っているかが分かる |
| `echo "（以上）"` | 最後に、目印の文字を出す | **コマンドが、最後まで動いた**ことが分かる |

**読み方（2026年11月12日の出力）。**

```
== php : 見つからない
== node : 見つからない
== nodejs : 見つからない
== gitlab-ctl : 見つからない
（以上）
```

- 4行とも「見つからない」。
- `dpkg`の行（パッケージ名と版）が、**1行も出ていない**。
- 最後に`（以上）`が出ている。

この3つがそろえば、**このサーバーには、PHP、Node.js、GitLabは、入っていない**。

### 2-3. 「何も出ない」は、証拠として弱い

| 何も出ない原因 | 防ぐ方法 |
|---|---|
| コマンドが、途中で失敗した（打ち間違い、権限の不足） | 最後に目印（`（以上）`）を出す。出なければ、最後まで動いていない |
| aptを使わない入れ方（手で展開、別の管理ツール）で、入っている | `command -v`（実行できる場所）と、`dpkg`（aptの記録）を、**両方**見る |
| エラーを、画面に出さないようにしている（`2>/dev/null`） | 結果が空のときは、エラーを隠さない形でも、もう一度打つ |


### 2-4. ほかのニュースも、同じ型

| ニュース | 確かめたこと | 結果（2026年11月12日） |
|---|---|---|
| PHPの緊急セキュリティリリース | `command -v php`、`dpkg -l`（`php*`） | 入っていない |
| Node.jsのセキュリティリリース | `command -v node`、`dpkg -l`（`nodejs*`） | 入っていない |
| GitLabの緊急パッチ | `command -v gitlab-ctl`、`dpkg -l`（`gitlab*`） | 入っていない |

10月に、同じ方法で確かめ、11月12日に、もう一度確かめた。**入れていないことは、日が経っても、変わらない。** ただし、確かめた**その日の出力**を残す。

### 2-5. この節の範囲

確かめたのは、**バリデータのサーバー**だけである。手元のPCなど、ほかの端末は、本章では扱わない。

### 2-6. 3点セット

| ニュース | リスク | 対策 | 証拠 |
|---|---|---|---|
| PHPの緊急セキュリティリリース | サーバーにPHPが入っているか | 入っていないことを確認 | 上のコマンドの出力と、日付 |

## 3. eMudhra認証局の鍵の問題

要点：OSの証明書を更新したあとは、**サービスを再起動し、更新の時刻と、サービスの起動時刻を、並べて**確かめる。

### 3-1. 何が起きたか

2026年10月、eMudhra社の中間証明書の鍵が、危うくなっていることが示された。Ubuntuは、10月20日に、セキュリティ通知USN-8944-1を出し、OSが信頼する認証局の一覧から、`emSign ECC Root CA - G3`を外した。質問1（入っているか）の答えは、**サーバーの一覧に、その認証局が、残っているか**である。

### 3-2. 質問1：OSの証明書の一覧を見る

```bash
dpkg -l ca-certificates | tail -n 1
ls /etc/ssl/certs | grep -i -E "emsign|comodo"
```

**なぜ打つか。** `ca-certificates`は、OSが信頼する認証局の一覧である。1行目は、その版を、2行目は、問題の認証局の名前が、一覧に残っているかを、見る。

**読み方（2026年11月12日の出力）。**

```
ii  ca-certificates 20260816ubuntu0.24.04.2 all  Common CA certificates
COMODO_ECC_Certification_Authority.pem
COMODO_RSA_Certification_Authority.pem
emSign_ECC_Root_CA_-_C3.pem
emSign_Root_CA_-_C1.pem
emSign_Root_CA_-_G1.pem
```

- `emSign_ECC_Root_CA_-_G3.pem`の名前が、一覧に、**ない**。USN-8944-1の対象の認証局は、外れている。
- `emSign_ECC_Root_CA_-_C3.pem`は、残っている。**`C3`と`G3`は、別の認証局**で、名前が似ているので、読み間違えない。

### 3-3. 質問3：直す方法が出ているか

| 場所 | 直す方法 |
|---|---|
| Ubuntu | `ca-certificates`の更新（USN-8944-1、10月20日） |
| 各ソフト | リリースノートに、この件の対応が書かれている（例：Prometheus 3.15.1、3.13.5）。Lighthouseは、第6章の3-2 |

### 3-4. 更新のあと、サービスを再起動して、時刻を並べる

**更新のあとは、サービスを再起動し、起動した時刻が、証明書の一覧の更新の時刻より新しいことを、確かめる。** 確かめるコマンドは、次のとおり。

```bash
ls -l --time-style=long-iso /etc/ssl/certs/ca-certificates.crt
for u in geth lighthouse mev-boost lighthouse-vc prometheus; do echo "$u : $(systemctl show -p ActiveEnterTimestamp --value $u)"; done
```

**なぜ打つか。** 1行目は、証明書の一覧の**最終更新の時刻**。2行目は、各サービスの**起動した時刻**。2つを並べて、起動のほうが新しいかを見る。

**読み方（2026年11月12日の出力、UTC）。**

| 見るもの | 時刻 |
|---|---|
| 証明書の一覧の最終更新 | 11/7 06:52 |
| prometheus の起動 | 11/7 12:24 |
| geth、lighthouse、mev-boost、lighthouse-vc の起動 | 11/9 12:48 |

すべてのサービスの起動が、一覧の更新より**新しい**。起動のほうが古いサービスがあれば、再起動する。

### 3-5. 3点セット

| ニュース | リスク | 対策 | 証拠 |
|---|---|---|---|
| eMudhra認証局の鍵の問題 | 問題の認証局を、信頼したままになる | OSの`ca-certificates`を更新し、サービスを再起動 | `dpkg -l`の版、一覧の名前、更新時刻とサービスの起動時刻、日付 |

## 4. カーネルの脆弱性：公開から修正まで

要点：ニュースの強さ（深刻度9.8）では、動かない。**3つの質問の答えで、動く。** 修正が出るまでの間、何をしたか、いつ外したかを、日付で残す。

### 4-1. 何が起きたか

2026年10月15日、Linuxカーネルの脆弱性（CVE-2026-98432）が公開された。公式（Ubuntu）の説明では、**IPv4のTCP接続の処理に関わる**もので、深刻度は9.8（Critical）、認証なしで、ネットワーク越しに、攻撃される可能性がある。

### 4-2. 3つの質問と、その答え（2026年11月2日〜3日）

| 質問 | 確かめたこと | 答え |
|---|---|---|
| 1 入っているか | `uname -r`、`cat /etc/os-release` | Ubuntu 24.04、カーネル`6.8.0-147-generic`。**対象** |
| 2 外から届くか | `ss -tlnp`、`ufw status verbose` | 外から届くTCPのポートは、P2Pの2つ（30303、9000）。**届く** |
| 3 直す方法が出ているか | 公式のCVEページのStatus、`apt list --upgradable` | Statusは**作業中**（目標は`6.8.0-149`）。更新の一覧に、カーネルは、**出ていない** |

答えは、「入っていて、外から届き、修正は、まだ届かない」。1-4 の表では、**暫定処置と、見張り**の行に当たる。

### 4-3. 修正が出るまでの間にやったこと

| 日付 | やったこと | 根拠 |
|---|---|---|
| 11/2 | IPv4オプション付きのTCPを遮断するルールを入れた | コミュニティの案内。公式（UbuntuのCVEページ）にも、同じ考え方の対処が載っていた（11/3に確認。「リスクを下げるが、完全には防がない」と明記） |
| 11/2 | MPTCPの無効化を、設定ファイルに書いた | コミュニティの案内 |
| 11/4 | `sysctl -p`で、今の値にも反映した | 値が`1`のままだと、これから作られる待ち受けも、MPTCPになるため（4-5） |

公式のブログ（11/2付）は、**修正は、テスト用の置き場（`-proposed`）にある**と書いていた。通常の更新には、まだ出ていない。

### 4-4. 修正が届いた

| 日付 | 出来事 |
|---|---|
| 11/7 | 通常の更新（`noble-updates`）に、`6.8.0-149.149`が出ているのを確認した。名前を指定して導入し、再起動した（停止は約20分） |
| 11/7 | 再起動のあと、MPTCPで待ち受けるものは、0個になった（再起動の前は11個） |
| 11/10 | 公式のCVEページが更新され、24.04は「**修正済み（6.8.0-149.149）**」になっていた（11/12に確認。11/7の確認では、まだ作業中だった） |
| 11/12 | 暫定のルールを外した。入れてから外すまで、`pkts`（遮断した通信の数）は、**0のまま**だった |

**ここで、2つの「届く」を区別する。**

- 修正が、通常の更新に**出た**（11/7に確認）。
- 公式のページが、「修正済み」と**表示した**（11/12に確認）。

自分のサーバーでは、前者のほうが、先だった。公式の表示は、遅れて追いついた。**確かめるのは、公式のページと、自分のサーバーの、両方である。**

**自動更新が、何を入れるか。** 自動更新の設定（`/etc/apt/apt.conf.d/50unattended-upgrades`）は、`noble`と`noble-security`だけを対象にしていた。`noble-updates`は、対象に入っていない。今回のカーネルは、`noble-updates`にだけ出たので、**自動では入らず、自分で導入した**。再起動も、自動では行われない設定である。

### 4-5. 書いただけでは、効かない（MPTCPの無効化）

```bash
echo 'net.mptcp.enabled = 0' | sudo tee /etc/sysctl.d/90-mptcp-off.conf && sysctl net.mptcp.enabled
sudo sysctl -p /etc/sysctl.d/90-mptcp-off.conf && sysctl net.mptcp.enabled
sudo ss -Mln | grep -c LISTEN
```

**3つの「状態」は、別である。**

| 見るもの | コマンド | 何を示すか |
|---|---|---|
| 設定ファイル | `cat /etc/sysctl.d/90-mptcp-off.conf` | 次の起動から効く値 |
| 今の値 | `sysctl net.mptcp.enabled` | いま新しく作るものに効く値 |
| 動いているもの | `sudo ss -Mln` | すでに動いているプロセスの実際の状態 |

実際の出力。ファイルを書いた直後の「今の値」は、`1`のまま。`sysctl -p`のあとは`0`。ただし、動いているgethの待ち受けは、再起動までMPTCPのままで、`ss -Mln`は11個だった。11/7の再起動のあとは0個。11/12にも、今の値`0`、設定ファイル`0`、待ち受け0個を、確かめた。

systemdの`daemon-reload`（ユニットファイルを書く → 読み込ませる → サービスを再起動する）と、同じ型である。

### 4-6. 3点セット

| ニュース | リスク | 対策 | 証拠 |
|---|---|---|---|
| カーネルの脆弱性 | 外から届くP2Pのポートで、対象のカーネルが動いていた | 暫定処置（11/2〜11/12）、修正版の導入と再起動（11/7） | 公式CVEページのStatus、`uname -r`、日付 |

## 5. 台帳：入れたものと、外したものを、1行ずつ残す

要点：暫定処置は、**入れた日、外す条件、外した日**を残す。ニュースごとの結果は、3つの質問の答えと、証拠を、1行で残す。秘密は、含めない。

### 5-1. 暫定処置の台帳（カーネルの件）

| 設定 | 入れた日 | 外す条件 | 状態 |
|---|---|---|---|
| IPv4オプション付きTCPの遮断（iptables） | 11/2（11/7の再起動で消え、同じ夜に入れ直した） | 公式が、「修正済み」と表示する | **11/12に削除** |
| MPTCPの無効化（設定ファイル） | 11/2（11/4に、今の値へ反映） | 決めていない。このノードは、MPTCPを使わない | 残している |

入れたときと、外すときの、実際のコマンドは、次のとおり。外すときは、入れたときと**同じ条件**を、`-D`で指定した。

```bash
# 入れたとき（11/2）
sudo iptables -I INPUT 1 -p tcp -m u32 --u32 '0>>24&0x0f=6:15' -j DROP

# 外したとき（11/12）：-I を -D に変え、同じ条件を指定する
sudo iptables -D INPUT -p tcp -m u32 --u32 '0>>24&0x0f=6:15' -j DROP

# 入れた直後と、外したあとの、両方で、一覧を見る
sudo iptables -L INPUT -v -n --line-numbers | head -6
```

**入れたルールの意味。**

| 部分 | 意味 |
|---|---|
| `-I INPUT 1` | 受信のルールの、**先頭**に入れる |
| `-p tcp` | TCPの通信だけが対象 |
| `-m u32 --u32 '0>>24&0x0f=6:15'` | IPヘッダの長さの欄が6〜15のもの。つまり、**IPオプション付き**のパケット（オプションがない通常の通信は、5） |
| `-j DROP` | 該当するものを、捨てる |

> ⚠️ **このコマンドは、記録として載せている。そのまま使うものではない。**
>
> 1. **もう不要である。** 修正版のカーネル（6.8.0-149）が入り、公式が「修正済み」と表示したので、このルールは、役目を終えた。
> 2. **効果は、公式には確認されていない。** コミュニティの案内から入れた。公式（UbuntuのCVEページ）にも、同じ考え方の対処が載っていたが、「リスクを下げるが、完全には防がない」と明記されている。

## 6. まとめ、今後の課題

### 6-1. まとめ

```
① ニュースの見出しの強さ（深刻度9.8など）では、動かない。
   3つの質問（入っているか／外から届くか／直す方法が出ているか）で動く
② 「入っていない」は、2つの方法で確かめる。実行できる場所（command -v）と、
   aptの記録（dpkg -l）。最後に目印を出して、最後まで動いたことも確かめる
③ 外から届くかは、ss -tlnp と ufw status verbose。
   この環境は、P2Pの2つのポート（30303、9000）だけ
④ 修正が「出た」、自分のサーバーに「届いた」、公式が「表示した」は、別。
   公式のページと、自分のサーバーの、両方で確かめる
⑤ 自動更新は、セキュリティ更新だけを入れる設定だった。
   今回のカーネルは、通常の更新に出たので、自分で入れた
⑥ 暫定処置は、入れた日、外す条件、外した日を、台帳に残す。
   外すときは、入れたときと同じ条件を、-Dで指定する。
   入れたあとと、外したあとの、両方で、一覧を見る（head -6）
⑦ 設定は、書いただけでは、効かない。
   設定ファイル、今の値、動いているもの、の3つは別
⑧ 証明書の更新のあとは、サービスを再起動し、起動時刻が、
   更新の時刻より、新しいことを確かめる
⑨ 公式の通知は、原文で読む。名前の似たものを、取り違えない
   （emSignの G3 と C3、CVE-2026-98432 と CVE-2026-109518）
⑩ 結果は、3点セット（リスク、対策、証拠）か、1行メモで、日付つきで残す
```

この章で、いちばん学んだのは、**ニュースが、立て続けに出ても、確認の順番は、同じ**ということだった。3つの質問に、コマンドで答え、結果を日付つきで残す。短い期間に、5つのニュースがあったが、台帳の1行ずつで、足りた。

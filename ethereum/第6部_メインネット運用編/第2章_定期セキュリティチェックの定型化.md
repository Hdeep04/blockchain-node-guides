# 第6部・メインネット運用編 第2章 定期セキュリティチェックの定型化 — 「入口」を、順番に確かめた日

> **UFWの表示だけでは、壁の全体は見えない**

---

| 項目 | 内容 |
|---|---|
| 位置づけ | 第5部 第19章 第6節の課題（ネットワーク面の定期確認、発信の絞り込み、正体不明の通信の裏取り）に、実際の確認手順で答える記録。確認を、週次・月次の定型にまとめる |
| 実施日 | 2026年10月1日（Activationから3日目） |

> 💡 **用語：Tailscale と tailnet。** Tailscaleは、インターネット越しでも、自分の端末同士を、暗号化した専用の回線でつなぐVPNのサービスである。同じアカウントでログインした端末が、1つの仲間として登録され、**その仲間の集まり全体を、tailnet（テイルネット）と呼ぶ**。登録された端末には、`100.`で始まる専用のアドレスが、1台ずつ割り当てられる。自宅のLANが「家の中の端末の集まり」であるのと同じように、tailnetは、場所を問わない、自分専用のLANと考えてよい。本章では、サーバー、自分のPC、ノートPCの3台が、tailnetの仲間である。`tailscale0`は、tailnetの通信が出入りする、サーバー上の仮想の出入口の名前である。

> ⚠️ 本章は機密情報を一切含みません。通信の相手先のIPアドレス、Tailscaleの端末名とアドレス、whoisに載っていた担当者の連絡先は、載せていません。出力は `<peer>`・`<tailnet_ip_server>`・`<tailnet_ip_pc>` などに置き換えています。

> 💡 **時刻の読み方。** `last`などのログの時刻は、サーバーのUTCで表示される（JST = UTC + 9時間）。

## はじめに：何を、どの順で確かめるか

第5部 第19章で、通信量を調べている途中に、クラウド事業者のサーバー宛て（ポート80）の、ごく小さい単発の通信が見えた。翌日あらためて確認したが、同じ通信は見当たらず、正体は確認できないままだった。`ss`も`nethogs`も、**今の瞬間しか見せない**ためである。

この件をきっかけに、「本番を動かし始めた今、定期的に何を確認すればよいか」を、整理することにした。確認の対象は、次の4つの観点に分けられる。

| 観点 | 問い | 使うもの |
|---|---|---|
| 発信 | 今、サーバーは、誰と話しているか | `ss -tnp state established` |
| 待ち受け | 外から入れる口は、どれか | `ss -tlnp` |
| 壁 | ファイアウォールは、設計どおりか | `ufw status verbose`、`iptables -S ts-input` |
| 入れる人 | 誰が、ログインしたか。誰が、入れる状態か | `last -a`、`tailscale status` |

以下、この順に、実際の出力と読み方を記録する。

---

## 1. 発信の確認：今、誰と話しているか

> 💡 **用語：ポート、TCPとUDP、プロセス。** **ポート**は、1台のサーバーが、複数の通信を同時にさばくための、窓口の番号である。同じ建物でも、窓口の番号が違えば、別の用件になる。たとえば、SSHは22番、Gethの通信は30303番を使う。**TCP**は、相手とつながって、確実に届ける方式、**UDP**は、つながりを作らず、手早く送る方式である。**プロセス**は、動いているプログラムのことで、`geth`や`lighthouse`が、それにあたる。

```bash
sudo ss -tnp state established
```

**なぜ打つか。** `ss`は、サーバーが今張っている通信の接続を、一覧で見せるコマンドである。`-t`はTCP、`-n`は名前に変換せず数字のまま、`-p`は、どのプロセスが接続を持っているかを表示する。`state established`で、実際に確立している接続だけに絞る。「誰が、誰と」話しているかが、プロセス名と宛先の組で見える。

出力は、次のようになった（抜粋、相手先は置き換え）。

```
Recv-Q Send-Q  Local Address:Port        Peer Address:Port    Process
0      36      <tailnet_ip_server>:22    <tailnet_ip_pc>:<p>  users:(("sshd",...))
0      0       <lan_ip>:9000             <peer>:<port>        users:(("lighthouse",...))
0      96      <lan_ip>:<port>           <peer>:30303         users:(("geth",...))
0      0       [<ipv6>]:<port>           [<tailscale_srv>]:443 users:(("tailscaled",...))
0      0       127.0.0.1:<port>          127.0.0.1:9090       users:(("prometheus",...))
```

### 1-1. 読み方

| プロセス | 相手 | 判断 |
|---|---|---|
| lighthouse | 世界中のノード（自分の9000番に接続） | Ethereumの P2P通信。想定どおり |
| geth | 世界中のノード（30303番まわり） | 同上 |
| sshd | Tailscale内のアドレス（自分のPC） | 自分のログイン。次の「4」で裏を取る |
| tailscaled | Tailscaleのサーバー（443番など） | VPN自身の通信 |
| prometheus、grafana、node_exporter、lighthouse・gethの内部連携 | `127.0.0.1`同士 | サーバー内部の通信。外には出ない |

**宛先が、クラウド事業者ばかりに見える**のは、Ethereumでは普通である。多くのノード運用者が、クラウドで動かしているためである。個々の宛先を見るのではなく、**「プロセス」と「宛先」の組が、想定どおりか**を見る。

`Recv-Q`は、受け取ったが、まだ処理していないデータの量、`Send-Q`は、相手に送る途中のデータの量である。0〜数百バイトなら、通信中というだけで、詰まってはいない。

## 2. 待ち受けポートの確認：外から入れる口は、どれか

```bash
sudo ss -tlnp
```

**なぜ打つか。** `-l`は、接続を待ち受けている口（LISTEN）を表示する指定である。どのポートを、どのプロセスが、開けているかが分かる。

結果は、次のとおりだった（抜粋）。

| 待ち受けの範囲 | ポート | プロセス | 役割 |
|---|---|---|---|
| 全インターフェース（`0.0.0.0`、`*`） | 9000 | lighthouse | P2P |
| 同上 | 30303 | geth | P2P |
| 同上 | 22 | sshd | SSH |
| 同上 | 3000 | grafana | ダッシュボード |
| `127.0.0.1`のみ | 8545、8546 | geth | RPC（HTTP、WebSocket） |
| 同上 | 8551 | geth | Engine API（gethとlighthouseの連携） |
| 同上 | 18550 | mev-boost | MEV-Boost |
| 同上 | 9090、9100、6060 | prometheus、node_exporter、geth | 監視用 |
| 同上 | 5052ほか | lighthouse | 内部用 |

### 2-1. 読み方

- **重要な口（RPC、Engine API、MEV-Boost、監視）は、すべて`127.0.0.1`限定**である。外に出ていない。
- `0.0.0.0`や`*`は、「全部の入口で待ち受ける」設定で、LANやインターネット側からも**届きうる**ことを意味する。**実際に届くかは、ファイアウォール次第**である。
- `ss -tlnp`の`-t`はTCPのみである。Lighthouseの発見通信などのUDPは、この一覧には出ない。

22番と3000番が全インターフェースで待ち受けているのが、気になった。次の節で、ファイアウォールが、実際にどう止めているかを確かめた。

## 3. 壁の確認：UFWとiptables

### 3-1. UFW

```bash
sudo ufw status verbose
```

**なぜ打つか。** ファイアウォール（UFW）の、既定の方針と、許可しているルールの一覧が出る。

```
Status: active
Default: deny (incoming), allow (outgoing), disabled (routed)

To                         Action      From
22/tcp on tailscale0       ALLOW IN    Anywhere
30303/tcp                  ALLOW IN    Anywhere
30303/udp                  ALLOW IN    Anywhere
9000/tcp                   ALLOW IN    Anywhere
9000/udp                   ALLOW IN    Anywhere
（IPv6の同じ5行は省略）
```

| 項目 | 意味 |
|---|---|
| `deny (incoming)` | 許可していない着信は、すべて拒否。基本が「閉じる」方針 |
| `22/tcp on tailscale0` | SSHは、Tailscale経由のみ許可。自宅LANやインターネットからは入れない |
| 30303、9000（tcp・udp） | P2P用。ノードとして必要な口 |
| `allow (outgoing)` | **発信は、制限していない**。第5部 第19章の「発信を絞る設計」の課題そのもの |

**3000番（Grafana）の許可ルールは、ない。** 全インターフェースで待ち受けていても、LANやインターネットからは、UFWが止めている。開いている口は、P2Pの2つだけで、ノードとして必要最小限である。

### 3-2. Tailscaleが、自分で足しているルール

ところが、ここで疑問が出た。UFWに3000番の許可がないのに、Tailscale経由では、Grafanaを開けている。UFWの表示に出ていない、**別のルール**が、働いているはずである。

> 💡 **用語：UFWとiptables。** Linuxのファイアウォールの本体は、カーネルの中にある、通信を許可・拒否する仕組み（iptablesなど）である。UFWは、その仕組みを、簡単な書き方で操作するための**窓口**にすぎない。UFWで書いたルールも、中では、iptablesのルールになる。一方、Tailscaleのようなソフトは、UFWを通さず、**自分でiptablesにルールを足す**ことがある。この場合、そのルールは、UFWの表示には出てこない。

```bash
sudo iptables -S ts-input
```

**なぜ打つか。** iptablesの、実際のルールを見る。`-S`は、ルールを、設定したときの書き方のまま、一覧にする指定である。`ts-input`は、Tailscaleが作った、**着信用のルールの組（チェーン）**の名前で、ここだけを表示する。

> 💡 **用語：チェーン。** ルールを束ねた「組」のことである。通信が1つ来るたびに、**上のルールから順に**、条件に合うかを照らしていく。最初に合ったルールの動作（許可、または破棄）が、その通信に適用される。

出力は、次の5行だった。

```
-A ts-input -s <tailnet_ip_server>/32 -i lo -j ACCEPT
-A ts-input -i tailscale0 -j ACCEPT
-A ts-input -p udp -m udp --dport 41641 -j ACCEPT
-A ts-input -s 100.115.92.0/23 ! -i tailscale0 -j RETURN
-A ts-input -s 100.64.0.0/10 ! -i tailscale0 -j DROP
```

呪文のように見えるが、**部品に分けると、読める**。

#### 部品の意味

| 部品 | 意味 |
|---|---|
| `-A ts-input` | `ts-input`の組に、このルールを**追加**（Append）する |
| `-s ○○` | 通信の**送り元**（source）が、○○のアドレス、または範囲である |
| `-i ○○` | 通信が**入ってきた入口**（インターフェース）が、○○である |
| `!` | 否定。「〜**以外**」の意味 |
| `-p udp`、`--dport 41641` | 方式がUDPで、**宛先のポート**が41641番である（`-m udp`は、UDPの条件を使うための付属の指定で、気にしなくてよい） |
| `-j ACCEPT` | **許可**する |
| `-j DROP` | **黙って破棄**する（相手には、何も返さない） |
| `-j RETURN` | この組では判断せず、**元の流れに戻す**（ここでは、許可も破棄もしない） |
| `lo` | サーバー**自身の内部**の入口（ループバック）。外の通信ではない |
| `tailscale0` | **tailnetの通信が入ってくる**、仮想の入口 |

#### アドレスの後ろの「/32」「/23」「/10」

アドレスの後ろの数字は、**範囲の広さ**を表す。数字が大きいほど狭く、小さいほど広い。

| 表記 | 範囲の広さ |
|---|---|
| `/32` | **1つのアドレスだけ**（サーバー自身） |
| `/23` | 512個のアドレスの範囲 |
| `/10` | 約420万個のアドレスの範囲 |

`100.64.0.0/10`は、`100.64.0.0`から`100.127.255.255`までの、広い範囲である。Tailscaleが、tailnetの端末に配る、**アドレスの置き場所**として使っている。Tailscaleを使う、すべての環境で、同じ範囲が使われる。この文字列は、**特定の環境を示すものではない**。

#### 5行の読み方

| 行 | 読み方 |
|---|---|
| 1行目 | 送り元が**サーバー自身**で、内部の入口（`lo`）から来た通信は、**許可**する。サーバーが、自分のtailnetアドレス宛てに出す通信を、通すための行 |
| **2行目** | **`tailscale0`から入ってきた通信は、ポートを問わず、すべて許可**する。条件が、入口の名前だけで、ポートの指定がない |
| 3行目 | UDPの41641番宛ての通信は、**許可**する。Tailscale同士が、直接つながるための専用のポートで、`tailscale status`の`direct`は、この仕組みによる |
| 4行目 | 送り元が`100.115.92.0/23`の範囲で、`tailscale0`**以外**から来た通信は、ここでは**判断せず、次に回す**。5行目の「破棄」から、この範囲だけを外すための行。この範囲は、ChromeOS（Chromebook）が、本体のOSと、その中のLinuxの仮想環境をつなぐために使う範囲で、Tailscaleは、tailnetのアドレスをここから配らない。ChromeOSの内部通信を、なりすましと誤って破棄しないための例外で、Ubuntuのサーバーには関係がない（Tailscaleの公開ソースコードの記述による） |
| 5行目 | 送り元が`100.64.0.0/10`の範囲で、`tailscale0`**以外**から来た通信は、**破棄**する |

#### 5行目は、何を防いでいるのか

5行目は、**なりすましの防止**である。

tailnetの端末は、`100.64.0.0/10`の範囲のアドレスを、持っている。もし、自宅LANの中や、インターネットの向こうの誰かが、送り元を「`100.○○`」と**偽って**、サーバーに通信を送ってきたら、どうなるか。その通信は、tailnetの入口（`tailscale0`）からは入ってこない。LAN側などの、別の入口から入ってくる。

5行目は、**「tailnetのアドレスを名乗っているのに、tailnetの入口から来ていない」通信を、破棄する**。本物のtailnetの端末は、必ず`tailscale0`から入ってくるので、偽の通信だけが落ちる。2行目の「`tailscale0`から入る通信は、すべて許可」という、広い許可が、安全に成り立つのは、この5行目があるからである。

### 3-3. ここから分かること

**tailnetに入っている端末からは、サーバーの待ち受けポート（SSH、Grafanaを含む）の、すべてに届く。** UFWで22番だけをTailscale限定にしても、tailnetの内側からは、それ以外のポートも見える。

つまり、このサーバーの守りの境界は、UFWだけではない。**「tailnetに、誰が入れるか」が、もう1つの境界**である。tailnetに入れるのは、同じアカウントでログインした端末だけである。今回の確認で、守る対象が、サーバーの設定から、**入れる端末とアカウント**へ広がった。

なお、このルールと、UFWの、どちらが先に判定されるかという**順序までは、本章では確認していない**。確認できたのは、UFWに許可のない3000番に、Tailscale経由ではつながっているという事実と、上の5行の中身である。

なお、Grafanaは、tailnet内の端末から見える状態なので、管理者パスワードが、初期のままでないことも、あわせて確認した。

## 4. 入れる人の確認：ログイン履歴とtailnetの端末

### 4-1. ログイン履歴

```bash
last -a | head -10
```

**なぜ打つか。** いつ、どこから、誰がログインしたかの記録が出る。自分の操作以外が混じっていないかを見る。

```
<user> pts/0   Wed Sep 30 22:50   still logged in   <tailnet_ip_pc>
<user> pts/0   Wed Sep 30 13:47 - 13:51  (00:03)    <tailnet_ip_pc>
<user> pts/0   Tue Sep 29 23:16 - 23:31  (00:15)    <tailnet_ip_pc>
...
```

10行すべて、同じユーザーが、同じ接続元（Tailscale内のアドレス）から入っていた。時刻はUTCなので、JSTは+9時間である。たとえば`Sep 30 22:50`は、JSTでは10/1の7:50で、そのときの`node_check`の時刻と合っていた。

`last`は、**ログインに成功した記録**である。攻撃の失敗は、`fail2ban`の「Banned」の数や、`lastb`で見る。

### 4-2. tailnetの端末

```bash
tailscale status
```

**なぜ打つか。** tailnetにつながっている端末の一覧と、状態が出る。接続元のアドレスが、自分のPCのものか、**一覧と照らして確定**できる。

結果は、4台だった。サーバー、自分のPC、ノートPC、そして、**111日間オフラインのままの端末**である。最後の1台は、以前、別の用途で使ったVMで、すでに削除していた。

**VMを消しても、tailnet上の登録は残る。** 登録が残ると、その端末の認証情報が、有効なまま残る。使わない入口を、残しておく理由はない。管理画面から端末を削除し、`tailscale status`で、3台になったことを確認した。

## 5. 裏取り：プロセスと、宛先の持ち主

第19章で残した、ポート80の通信を、あらためて確かめた。

```bash
sudo ss -tnp state established '( dport = :80 )'
```

**なぜ打つか。** 宛先のポートが80の接続だけを、抜き出す。持ち主のプロセスが、一緒に出る。

結果は、1本だった。持ち主は`tailscaled`で、宛先はIPv6のアドレスだった。次に、その宛先の持ち主を、調べた。

```bash
whois <宛先のアドレス>
```

**なぜ打つか。** そのアドレスを割り当てられた組織が分かる。`NetName`と組織名に、Tailscale Inc.と出た。

| 確認したこと | 結果 |
|---|---|
| 接続の持ち主（プロセス） | tailscaled |
| 宛先の持ち主（whois） | Tailscale Inc. |

**プロセスと、宛先の持ち主の両方が、説明のつく相手**だった。`ss`で「誰が」、`whois`で「誰と」を確かめる、2段階の裏取りである。

> ⚠️ `whois`の出力には、担当者の氏名・電話番号・メールアドレスが含まれる。公開する文書には、そのまま載せない。載せるのは、「組織名が出た」という結果だけにする。

### 5-1. 分かったことと、分からないこと

分かったのは、**今この瞬間のポート80の通信は、すべて説明がつく**ことである。

分からないのは、第19章の通信と、同じものだったかである。当時の通信は、プロセス名が表示されず、確認した時には、すでに終わっていた。**同じ種類のものだった可能性はあるが、確認できていない。** 「そうだろう」で閉じず、次に出たときに、プロセスと宛先が事実として残る仕組みを作る（今後の課題）。

## 6. 定期チェックの定型

ここまでの確認を、**変わる速さ**に合わせて、頻度に振り分けた。ポートやファイアウォールのルールは、自分が変更しない限り、変わらない。変わったときだけが異常なので、見る頻度は低くてよい。

| 頻度 | 確認すること | コマンド／場所 |
|---|---|---|
| **毎日** | サービス稼働、fail2ban、Tailscale、再起動の要否、保留中アップデートの件数 | `node_check` |
| **週次**（10分程度） | ログイン履歴 | `last -a \| head -10` |
| | アップデートの**中身**（geth、lighthouse、openssh、tailscale、カーネルが含まれていないか） | `apt list --upgradable` |
| | tailnetの端末一覧（見知らぬ端末がないか） | `tailscale status` |
| | 発信の接続先（P2P以外に、知らないプロセスや宛先がないか） | 定期記録の集計（今後の課題） |
| | geth・lighthouseのセキュリティリリースの有無 | 公式の告知 |
| **月次**（30分程度） | 待ち受けポート | `sudo ss -tlnp` |
| | ファイアウォール | `sudo ufw status verbose` |
| | tailnetの端末整理、Grafanaのパスワード | 各管理画面 |
| | バックアップの復元テスト | 第5部 第18章の仕組み |
| **作業のあと** | アップデートや設定変更の直後に、待ち受けポートとUFWを見直す | `ss -tlnp`、`ufw status` |

アップデートの中身を見る習慣は、第3章で扱う。

### 6-1. 「正常な状態」を、先に保存する

出力を目で読んで判断するのではなく、**基準値との差分だけを見る**形にする。今回の確認結果が、そのまま基準値になる。

| 項目 | 基準値（2026年10月1日） |
|---|---|
| 外に開いているポート | 9000、30303（P2P）、22（SSH）、3000（Grafana待ち受け）。ほかは`127.0.0.1`のみ |
| UFWのルール | 着信は原則拒否。22はtailscale0のみ。9000と30303をtcp・udpで許可 |
| tailnetの端末 | 3台 |
| Grafanaのパスワード | 変更済み |

## 7. この確認の限界

- **`ss`は、瞬間の写真**である。数秒で終わる通信は写らない。
- **`ss -t`は、TCPのみ**である。UDPの通信は、含まれない。
- **`last`は、成功したログインだけ**である。
- **通信の中身は、見ていない。** プロセスと宛先が分かるだけで、何を送ったかまでは分からない。

だからこそ、発信の接続先を、**定期的に記録として残す**仕組みが、次に必要になる。次に同じ通信が出たとき、記録から、プロセスと宛先を、事実として追えるようにする。

---

## 8. まとめ

```
① 確認は、「発信」「待ち受け」「壁」「入れる人」の
   4つの観点に分けると、順番に確かめやすい
② ssは「プロセス」と「宛先」の組で見る。宛先がクラウド事業者ばかりに
   見えるのは、Ethereumでは普通
③ 重要な口（RPC、Engine API、MEV-Boost、監視）は、127.0.0.1限定。
   外に開いているのは、P2Pの2つ、SSH、Grafanaの待ち受けだけ
④ UFWの表示だけでは、壁の全体は分からない。tailnetに入った端末は、
   待ち受けポートの全てに届く。守りの境界は、「tailnetに誰が入れるか」
   にも、ある
⑤ 正体の確認は、プロセス（ss）と、宛先の持ち主（whois）の、
   両面で行う。ただし、過去の通信と同じとは、言い切れない
⑥ 確認は、変わる速さに合わせて、毎日・週次・月次に分ける。
   正常な状態を、基準値として保存し、差分だけを見る
```

UFWの設定を確かめただけでは、見えていなかった壁があった。**守る対象が、サーバーの設定だけでなく、「tailnetに誰が入れるか」にも広がった**ことが、この章のいちばんの収穫である。
